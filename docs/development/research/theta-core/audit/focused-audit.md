## Parser: actual Node and upward edges

- **Avoidable runtime upward edge:** `src/parser/theta-document.ts:29` imports `inertSystemNoteChannel` from `../extension/system-note-channel`. It is used for snippet lexing at `:927–932`. The actual no-op factory already lives in `src/diagnostics/system-note.ts:206–212`. **Concrete refactor:** import that same factory directly from diagnostics; no replacement factory or behavior invention is needed. This removes this particular parser-to-extension edge, not every other upward edge in the wider runtime.
- **Type-only upward edge:** `src/parser/theta-ast.ts:4` imports `SystemNoteChannelDeps` from the extension module; `ParseThetaDocumentDeps.systemNote` exposes it at `:888`. Repointing that type to `diagnostics/system-note` removes the declaration-path leak. The contract itself still has host-shaped `pi`, `ui`, and diagnostic-delivery fields (`src/diagnostics/system-note.ts:143–149`), but no Pi package import.
- **Real Node runtime dependency:** `src/parser/schema-lowering.ts:28` imports `createHash`; `canonicalHash` actually calls synchronous SHA-256 over canonical text (`:104–108`), and `schemaSlug` slices the digest (`:113–115`). One shortest path is document `:35` → frontmatter `:44` → system-param-types `:6` → schema-lowering. Root service injection does not intercept this hash. Browser/non-Node extraction needs a synchronous compatible hash implementation or an explicit hash seam; Node-targeted extraction can retain it unchanged.
- **Real but narrow Node path dependency:** document `:67` imports `thetaDefaultName`; callable-set imports `node:path` at `src/parser/callable-set.ts:36` and uses `posix.basename` in `thetaDefaultName` at `:564–565` (and on-disk-name checking at `:551`). A portable POSIX-basename helper is a possible leaf refactor, preserving suffix semantics.
- **Ordinary third-party parser dependency:** frontmatter imports `yaml` at `src/parser/frontmatter.ts:27–33`, calls `parseDocument` at `:477` and `:529`. This is not Pi, AJV, or TypeBox coupling; retain it or deliberately replace the frontmatter parser.

## Executor / effect host: hidden parser loading, useful host seams

- The executor's direct AST imports are **type-only** (`src/runtime/statement-executor.ts:64–75`), not an executable dependency on the document parser. The hidden runtime path instead begins with its tool-call defect imports (`:81`):

  `statement-executor:81 → tool-call:38 → parser/tool-call-static-checks:22 → type-layer-checks:86 → local-binders:5 → theta-document`

  `tool-call.ts:38–45` re-exports executable parse-time checks alongside runtime carriers; static-checks imports a union splitter from the broad type-layer module; local-binders imports the executable `callWithClauseValues` document helper. Consequently runtime defect imports load frontmatter/YAML, Node path handling, and the parser's extension channel. **Concrete refactors:** separate runtime defect/carrier exports from parser compatibility re-exports; put small AST walkers such as `callWithClauseValues` (`theta-document.ts:134–140`) in a lower leaf. Moving only the union-splitter import to `annotation-compat` is not sufficient: that file itself imports runtime `PRIMITIVE_NAMES` back from `type-layer-checks` (`src/parser/annotation-compat.ts:4`).
- A second independent runtime path imports **Node crypto merely to obtain a JSON-Pointer helper**: executor `:81` → tool-call `:53` → wire-form-depth-walk `:42` → schema-lowering `:28`. The imported symbol is `encodePointerSegment`, not hashing. Moving pointer escaping into a dependency-light shared leaf would separate this concern; changing a type import would not, because this is an executable helper import.
- **Actual type-only extension leak:** `src/runtime/statement-executor-types.ts:23` imports `ParForLaneHooks` from `extension/execution-status/types`; it appears as `ExecuteBodyDeps.statusLanes` at `:234`. Its shape is only `open(total,width)` plus handle `claim/settle/close` (`src/extension/execution-status/types.ts:362–371`). Moving the interface into a runtime/seam contract and having the extension implement it is a small concrete extraction refactor, not a Pi-runtime removal.
- Effect host similarly reaches tool-call/parser through its executable import at `src/runtime/effectful-statement-host.ts:72`. It has another independent upward path: effect host `:65` → query-tool-loop `:62` → runtime-event-channel `:16` → extension channel. Here a **pure** `computeMasked` consumer loads a module that also imports and calls delivery (`src/runtime/runtime-event-channel.ts:122`, `:307–331`). Separating event shapes/pure builders from note delivery, or injecting delivery in the latter helpers, addresses a real module boundary leak.
- **Reuse through existing adapters is viable at these seams:** `StatementEvalHost` already supplies `evaluatePure`, `checkpointFor`, and `runEffect` (`src/runtime/statement-executor-types.ts:67–83`). The effect host injects query/tool/invoke resolvers rather than constructing Pi sessions (`src/runtime/effectful-statement-host.ts:141–163`); the query loop's driver is a structural interface (`src/runtime/query-tool-loop.ts:155–169`); `InvokeChild.drive()` is structural (`src/runtime/invoke-cancellation.ts:86–97`). `createEffectfulStatementHost` performs dispatch through these collaborators (`:646–741`). These are adapter examples, **not evidence that the current whole import closure is isolated**. Tool lowering retains Pi-shaped semantics: only text content is joined (`src/runtime/tool-call-execute.ts:102–116`, `:154–165`), so a different host must adapt tool results accordingly.
