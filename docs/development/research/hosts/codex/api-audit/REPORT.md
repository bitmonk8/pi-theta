## Executive conclusion

**Do not describe current Codex as merely a CLI with MCP and skills.** This release has (1) stable, default-on lifecycle hooks, (2) an app-server protocol with start/steer/interrupt, structured final output, raw history injection, direct MCP calls and standalone sandboxed process execution, and (3) stock TUI support for a **shared app-server daemon / explicit remote endpoint**. Source explicitly supports rejoining already-loaded threads on the **same app-server**.

However, **none of these is a pi-style general in-process TypeScript extension API**. The official npm SDK is a `codex exec` child-process wrapper, not an attachment/control handle into the user's existing TUI. Plugins bundle skills/MCP/apps/hooks; there is no inspected arbitrary plugin module with `registerCommand`, tool-registry mutation and host-session callbacks. Dynamic tools are experimental and declared at **thread creation**, not per turn.

A deterministic Theta evaluator could orchestrate app-server as a custom client/worker host, including real tool results/history entries without asking an LLM to impersonate execution. A **same-session sidecar** is also plausible for a TUI already backed by an accessible shared daemon, but requires runtime qualification of multi-client event/approval routing and hook/turn reentrancy. It is **not** supported merely by knowing a saved session ID or spawning another SDK run.

## Integration classes — keep distinct

| Class | Released capability | Qualification |
|---|---|---|
| Existing stock TUI: lifecycle callback | Command and MCP-tool hooks execute at native lifecycle boundaries | S; meaningful deterministic native integration, but constrained hook outputs, not full loop ownership |
| Existing stock TUI: independent session controller | Shared daemon / remote app-server permits clients to rejoin a loaded ordinary thread | S for design; U for complete Theta lifecycle and approval ownership; unavailable as generic attach into an embedded-only TUI |
| Isolated worker orchestration | SDK spawns `codex exec`; app-server starts/resumes its own threads | S+A; strong baseline for worker adapter, not proof of existing-session integration |
| Custom frontend / embedding | App-server JSON-RPC; internal Rust in-process client used by TUI and exec | S; external protocol versus internal Rust API have different compatibility/distribution costs |
| External launcher | Shell command/plugin invokes Theta process | Possible but by itself proves neither native turn control nor shared transcript/approval semantics |

### Shared daemon is the important existing-session caveat

[`tui/src/lib.rs:1028-1056`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/tui/src/lib.rs#L1028-L1056) chooses explicit remote, reusable implicit local daemon, or embedded runtime. Local daemon connection failure can fall back to embedded; explicit remote remains authoritative. The [released daemon README](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-daemon/README.md#L1-L29) documents Unix control socket, lifecycle, shared inherited environment, and marks the **daemon lifecycle experimental**. It warns per-client environment isolation is not supplied. Thus local TUI plus sidecar may share a live runtime **only when actually connected to the same server**.

[`thread_processor.rs:4498-4620`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/request_processors/thread_processor.rs#L4498-L4620) `resume_running_thread` finds an existing `ThreadManager` thread and preserves rejoin semantics. It rejects replacing history on a running thread, and can ignore conflicting resume overrides when other subscribers still observe it. Parent-owned V2 children have additional direct-input restrictions. Reusing disk history via a **different** app-server is not this code path and must not be advertised as attaching to the running TUI.

## Official TypeScript SDK: a worker API, not an interactive-host plugin API

* [`sdk/typescript/src/exec.ts:94-105,173-175,203-216`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/sdk/typescript/src/exec.ts#L94-L105): constructs **`exec --experimental-json`**, adds `resume <threadId>` for later calls, spawns native binary, writes prompt then closes stdin. Published `sdk/package/dist/index.js:178,267` contains the same command/spawn design. **S+A**.
* [`thread.ts:65-115`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/sdk/typescript/src/thread.ts#L65-L115) streams parsed JSONL, captures thread ID and usage. `run()` collects agent messages/items, throws for `turn.failed` (`119-141`).
* [`turnOptions.ts`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/sdk/typescript/src/turnOptions.ts) offers final `outputSchema`, cancellation signal and cyber-program option, **not dynamic tool definitions or host callbacks**. No arbitrary per-turn tool dispatch interface found in SDK.
* [`events.ts:34-84`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/sdk/typescript/src/events.ts#L34-L84) defines terminal `turn.completed`, `turn.failed`, and fatal `error`, plus item events. Cancellation uses Node child-process `signal` (`exec.ts:203-206`), not app-server `turn/interrupt`. Nonzero exit/signal throws and generator cleanup kills child (`exec.ts:230-264`). Do not promise cancellation returns an ordinary completed-turn result.
* Important defensive adapter requirement: `Thread.run()` returns after generator exhaustion even if no `turn.completed` was seen (`thread.ts:119-141`). A strict orchestration adapter should require a terminal observable, not equate Promise resolution/EOF with semantic success. This is source observation, not a reproduced defect.
* Node >=18, ESM, Apache-2.0; exact CLI dependency in **published** package. SDK executable override permits a pinned native binary. Default environment inherits process environment unless an explicit SDK environment is supplied (`exec.ts:183-192`). Avoid accidentally sharing unrelated host configuration.

## App-server control and output

### Turns, completion, cancellation

[`protocol/common.rs:1057-1080`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/common.rs#L1057-L1080) registers `turn/start`, experimental `turn/settings/update`, `turn/steer`, `turn/interrupt`. [`v2/turn.rs:170-369`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L170-L369) defines their fields. `turn/steer` requires `expectedTurnId`; interrupt identifies both thread and turn. Start response reports a turn, **not completed work**. `turn/completed` carries full turn (`turn.rs:564-570`); statuses are `completed`, `interrupted`, `failed`, `inProgress` (`33-38`). Correlate by IDs, inspect final status/error, and do not confuse item completion or interrupt acknowledgment with turn completion. **S**, no end-to-end reliability guarantee asserted without transport/disconnect testing.

### Structured final output is real but is not a deterministic execution engine

`TurnStartParams.output_schema` is explicitly “JSON Schema used to constrain the final assistant message for this turn” (`turn.rs:272-276`). SDK serializes schema to a temporary file and passes `--output-schema` (`thread.ts:74-88`, `exec.ts:142-144`); [SDK README:53-84](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/sdk/typescript/README.md#L53-L84) documents plain schema and Zod conversion targeting OpenAI. Validate parsed output independently; do not use structured model text to simulate Theta instructions or tool execution. Schema constraint concerns the final response, not all intermediate messages or tool calls. **S**.

### Dynamic tools: genuine callback/result channel, but thread-scoped and experimental

[`v2/thread.rs:145-151`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L145-L151) puts `dynamicTools` on **`thread/start`**, tagged `experimental("thread/start.dynamicTools")`. No `dynamicTools` field exists on inspected `TurnStartParams`/`TurnSteerParams`; no general tools/set endpoint found in released request enum. Thus **not evidence for dynamic per-turn tool replacement in an existing conversation**.

[`common.rs:1827-1831`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/common.rs#L1827-L1831) defines server request **`item/tool/call`**. [`v2/item.rs:1663-1690`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/v2/item.rs#L1663-L1690) includes thread/turn/call IDs, optional namespace, tool name and JSON arguments; response has `contentItems` and `success`, including text/image/audio content. [`dynamic_tools.rs:18-55`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/dynamic_tools.rs#L18-L55) submits actual `Op::DynamicToolResponse`. This is **real host-executed tool result carriage**, not just assistant prose. It remains a **model-selected call**, not a client method that deterministically invokes any built-in tool. Handle invalid responses, errors and turn-transition cancellation explicitly (`dynamic_tools.rs:23-34,59-109`). **S**.

### Deterministic native operations versus model-selected tools / approvals

* **`command/exec`** directly executes argv in server sandbox **without creating thread or turn**: [`v2/command_exec.rs:21-26,30-127`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/v2/command_exec.rs#L21-L127). Supports cwd/env, PTY, stdin/output streaming, timeout/output cap, follow-up write/resize/terminate. Final response comes after output deltas and contains exit code/stdout/stderr. This can power deterministic shell operations, but is **not the current turn's model shell tool invocation**, nor automatically the same approval UX/transcript path. No approval-policy/reviewer or thread ID field is present on this request. Do not equate sandbox execution with interactive approval integration.
* **`mcpServer/tool/call`** directly calls a configured thread MCP tool: [`v2/mcp.rs:201-226`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/v2/mcp.rs#L201-L226). Handler loads thread, checks direct input eligibility, then `thread.call_mcp_tool`: [`mcp_processor.rs:679-700`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/request_processors/mcp_processor.rs#L679-L700). Real deterministic dispatch, but **not a universal built-in-tool executor**, and exact approval/transcript parity remains U.
* Native model tool approval requests are separate server requests (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`; [`common.rs:1795-1810`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/common.rs#L1795-L1810)). Turn/thread permission settings and reviewer selection exist; implementing app-server frontend means handling these requests, not only reading notification text.
* **`turn/start.toolOutput`** is an additional real non-user input path: [`turn.rs:153-163,197-199`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L153-L199). Handler prohibits nonempty normal input alongside it, requires tool name, creates `ResponseItem::FunctionCallOutput` with name/namespace/body (no call ID), optionally retains it, and starts a turn: [`turn_processor.rs:544-553,600-622`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/request_processors/turn_processor.rs#L544-L622). This is useful result injection, **not proof a native tool actually ran**, not a pending tool response replacement, and not a general execute-tool method.

## History, compaction and raw context

* `thread/read.includeTurns`, `thread/turns/list`, `thread/items/list` and cursors are typed APIs; full-history hydration is deprecated for paginated threads: [`v2/thread.rs:1705-1788`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L1705-L1788). Transcript/UI history is not automatically identical to current model context after compaction.
* **`thread/inject_items`** explicitly appends raw Responses API items **without starting a user turn**, not marked experimental in the released request enum: [`common.rs:888-893`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/common.rs#L888-L893); body schema is thread ID and JSON item array (`thread.rs:1725-1737`). Core implementation records context then `inject_client_response_items`, and checkpoints preparation: [`core/src/codex_thread.rs:829-875`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/core/src/codex_thread.rs#L829-L875). Strong evidence for machine-owned context insertion, but exact permitted item shapes, UI display and concurrent ordering need probes.
* `thread/compact/start` exists (`common.rs:734` and `thread.rs:1173-1180`), with `thread/compacted` notification (`common.rs:2030`). Native pre/post compact hooks exist. This proves native compaction initiation/observation, **not a callback allowing replacement of Codex's compaction algorithm or arbitrary history reset**.

## Stock CLI hooks and plugins

### Hooks are shipped, stable, default-on — but constrained

[`features/src/lib.rs:1345-1350`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/features/src/lib.rs#L1345-L1350): `hooks` is **Stable**, `default_enabled:true`. Do not rely on older claims that Codex has only a post-turn `notify` hook.

[`config/src/hook_config.rs:35-60,163-200`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/config/src/hook_config.rs#L35-L60) enumerates **PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, SessionStart, SessionEnd, UserPromptSubmit, SubagentStart, SubagentStop, Stop, Interrupt**. Config supports matcher groups, command timeout/asynchrony/status and context limits. Native hook inputs include session ID, cwd, transcript path and event payload; UserPromptSubmit includes prompt (`hooks/src/schema.rs:566-582`). Config-layer hooks JSON/TOML discovery and managed/trust policy are real (`hooks/src/engine/discovery.rs:94-164`); do not assume untrusted project hooks silently run.

**Supported handlers:** external commands and MCP-tool handlers. Although schema includes `prompt`/`agent`, released loader **skips both as unsupported**: [`discovery.rs:585-658`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/hooks/src/engine/discovery.rs#L585-L658). MCP handlers are not supported for SessionEnd. Deterministic command/MCP hooks can launch a real Theta evaluator without invoking any model.

**Output boundaries:** [`hooks/src/engine/output_parser.rs:1-72,121-237`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/hooks/src/engine/output_parser.rs#L121-L237):

* UserPromptSubmit can block and add context; it does not return a replacement prompt plus an arbitrary turn-control object.
* PreToolUse supports denial/context and `updatedInput` when permissionDecision is allow, not changing tool name or returning arbitrary tool result. Unsupported decisions/output can fail open; this is not a blanket fail-closed policy boundary.
* PermissionRequest can allow/deny; PostToolUse can block/add context, not replace completed tool output with arbitrary successful data.
* Stop can prevent stopping and supply continuation reason (`hooks/src/events/stop.rs:479-505`), but continuation is a prompt fragment to Codex, **not deterministic evaluation of a Theta program**.
* PreCompact's “block” decision is unsupported (released test `hooks/src/events/compact.rs:406-419`). Interrupt output is only a system message (`output_parser.rs:70-73`). Do not infer arbitrary compaction/cancel replacement from an event name.

These are useful **native existing-session integration points**, but they do not alone provide one-call `prompt`/await-success, temporary per-turn tool registry, native built-in deterministic invocation, arbitrary UI rendering or registered slash commands. A hook that blocks a Theta invocation and hands it to a daemon sidecar is an **integration design inference**, with reentrancy, lifecycle and failure semantics still to prove.

### Plugins are bundles, not arbitrary in-process extensions

[`plugin/src/manifest.rs:8-25`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/plugin/src/manifest.rs#L8-L25) declares paths for **skills, onboarding skill, MCP servers, apps, hooks** and presentation metadata. [`hooks/src/declarations.rs:11-31`](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/hooks/src/declarations.rs#L11-L31) projects plugin-bundled native hook handlers. Stock slash commands are a Rust enum (`tui/src/slash_command.rs:12-90`), including /hooks and /daemon; no inspected manifest runtime entry point registers arbitrary deterministic slash handlers. Skills/prompt content is model input, not a deterministic language interpreter. A plugin package can distribute a command/MCP bridge, but that alone is not pi-like control of the current host agent loop. **S** for schema; negative API conclusion bounded to inspected release.

## Recommended feasibility verdict and remaining gates

**Strong yes (source):** isolated app-server orchestration/custom frontend; structured turns, native terminal statuses, cancel, real dynamic-tool results at thread creation, direct shell/MCP operations and context injection. SDK provides a simpler worker path with fewer controls.

**Qualified / requires targeted proof:** native same-existing-TUI-session Theta integration via lifecycle hook plus shared daemon sidecar. This release makes that a serious option, not merely theoretical shell launching. Demonstrate (a) TUI and adapter really share one app-server/thread, (b) no duplicate cold resume process, (c) prompt hook blocks language text before the model and evaluator executes it deterministically, (d) turn terminal/cancel/event routing and concurrent human input are safe, (e) approvals remain on intended native UX, (f) results land in correct history/context, (g) plugin/hook install/trust and daemon version pins are explicit.

**No demonstrated parity:** general stock CLI in-process extension registering Theta slash commands, replacing tool sets per turn, invoking arbitrary built-in tools deterministically through the same native model-tool/approval path, or replacing compaction. A fork/custom frontend can supply missing control but must be named as such.

All yes/no statements above concern **0.163.0 inspected artifacts/source**, not a live host acceptance test. Parent is handling protocol probes; this audit deliberately does not duplicate them.
