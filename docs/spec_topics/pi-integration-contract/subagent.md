# Subagent

**Conversation drive — subagent mode.** A subagent-mode invocation runs the **whole callee** — interpreter included — inside a **spawned child `pi` process**, not only its conversation. Where the predecessor design (RFC 0005) kept the interpreter in the parent and remoted only the `AgentSession` over RPC, this design moves the callee's interpreter into the child: the child runs Pi's full startup extension discovery, the callee executes against the child's own host session, and the parent no longer drives a remote session for any subagent invocation. One child process is launched per subagent-mode invocation, at the point the pre-spawn model guard ([PIC-62](#pic-62) below) admits the invocation. The child is launched as:

```
pi --theta <dirs> --mode json -p "/<slug>" --no-session [--tools <name1,name2,…>]
```

The child runs the callee under the **subagent-root regime** ([PIC-58](#pic-58) below) — the invocation regime of a `mode: subagent` theta that is itself the root theta of its own process. Params are marshalled structurally ([PIC-60](#pic-60)), the callee's final value returns to the parent as a single machine-readable envelope on the child's stdout ([PIC-59](#pic-59)), and the child's own host agent loop backs both model-facing and code-side extension-tool reach ([PIC-64](#pic-64)). No executable tool definition crosses any process boundary. The Pi surface consumed here — the CLI flags above, the `--mode json` event stream, and the reserved-key stdout envelope line — is verified against the installed Pi (`pi --help` and `docs/rpc.md`) at v0.80.10 and re-audited on each Pi minor bump per [Pi version bump procedure](./version-bump-intro.md#pi-version-bump-procedure) below.

<a id="subagent-launch-contract-differences"></a>
**Launch-contract differences from the RFC 0005 remote-session driver.** This design reuses RFC 0005's launcher — executable resolution, ambient-suppression flags, `--no-session`, the trust rule, env inheritance, teardown, kill semantics, orphan handling, and spawn-failure diagnostics — and retires only the RPC *drive contract*. The differences are:

| Concern | RFC 0005 (remote session) | This design (remote theta) |
|---|---|---|
| Child mode | `--mode rpc`, long-lived, multi-turn | `--mode json -p "/<slug>"`, one invocation per process |
| Interpreter | parent | child |
| `--tools` | callable-set allowlist for the session | **not required for correctness** — the child theta enforces its own callable set; MAY be passed as defence-in-depth |
| `--system-prompt` | resolved `system:` | same, consumed by the subagent-root regime ([PIC-58](#pic-58)) |
| Params | parent interpolates into per-query text | marshalled structurally ([PIC-60](#pic-60)) |
| Result | per-query `agent_end` payloads extracted parent-side | one final-value envelope on stdout ([PIC-59](#pic-59)) |

<a id="subagent-executable-resolution"></a>
**Executable resolution.** The runtime resolves the child executable by re-launching the running process from its own invocation, via a two-rung ladder — the mechanism proven by pi-config's `subagent` extension (`getPiInvocation()`):

1. **Entry-script rung.** When `process.argv[1]` names an existing file, spawn `process.execPath` (the Node/Bun binary) with that script as its first argument. The child is the exact same binary + entry script as the parent. The existence check carries an obligation the ladder cannot discharge itself: it MUST answer **false** for a path inside a compiled binary's own embedded filesystem. Such a path is one the running process can stat but no spawned child can open, and it is not an entry script the binary can run — it is a stray leading positional argument, which a host reads as the child's prompt instead of the callee. A check that answered true there would select rung 1 for a deployment where only rung 2 is runnable.
2. **Compiled-binary rung.** When `process.argv[1]` is unusable and `process.execPath` is not a generic runtime (`node` / `bun`), Pi itself is the executable — spawn `process.execPath` directly.

There is **no `PATH` fallback** — a deliberate divergence from the prior art. A `PATH`-resolved `pi` may be a different version or install than the parent, silently violating the pinned wire contract; a spec-governed language construct cannot tolerate that risk. If both rungs fail, resolution fails **closed at load time**: the theta does not register and the diagnostic (`theta/load/subagent-executable-unresolved`, see [Diagnostics — `theta/load/*`](../diagnostics/code-registry-load.md)) names the reason. The rung-1 existence check runs at **probe time** (see [Step 0 — Capability probe](./capability-probe.md#entry-capability-probe) above), not at first spawn. Parent `execArgv` (Node flags) is **not** forwarded to the child; the contract records this as accepted — a child that needs a Node flag its parent carried is out of scope for theta 1.0.

<a id="subagent-root-regime"></a><a id="pic-58"></a> **PIC-58. Subagent-root regime.** The **subagent-root regime** is the invocation regime of a `mode: subagent` theta that is the root theta of its own child `pi` process. A naive child launch of a `mode: subagent` callee would be circular — the theta runtime inside the child would see `mode: subagent` and spawn *another* child — so the child MUST instead drive the root theta against the process's own host session (prompt-mode driver mechanics) while applying the subagent-mode frontmatter contract:

- **Driver selection.** The regime, not the frontmatter `mode:`, selects the driver: the child runs the root theta's queries against its own host session with the prompt-mode conversation drive ([Conversation drive — prompt mode](./conversation-drive.md)), even though the theta is `mode: subagent`.
- **`system:` delivery.** The resolved-and-interpolated frontmatter `system:` is installed as the child session's system prompt, delivered via `--system-prompt <text>` at launch.
- **Active-set protocol (degenerate).** The callable set governs the child session's active tools for each query window through the prompt-mode `pi.setActiveTools` snapshot/restore protocol ([Tool-registration lifetime and visibility](./tool-registration-lifetime.md)), degenerate here: there is no pre-existing user state to restore for, so the snapshot is the child session's empty/default ambient set and the restore is a no-op of consequence.
- **Env-marker selection rule.** The regime is selected by the environment marker `PI_THETA_SUBAGENT_ROOT=<slug>`, set **only by the parent launcher** and **never authorable from a `.theta` file**. A theta author cannot request the regime; it is invisible to the language surface. This marker subsumes RFC 0005's `PI_THETA_SUBAGENT_CHILD` marker and carries its duties (watcher suppression, no-recursion guard, parent-PID carriage for the [orphan-prevention](#subagent-orphan-prevention) watchdog) alongside regime selection.
- **`theta/parse/system-on-prompt-mode` does not fire.** The callee is still `mode: subagent`, so its `system:` frontmatter is valid on its own terms; the regime drives it against a host session but does not reclassify it as `mode: prompt`. The parse diagnostic that rejects `system:` on a prompt-mode theta ([Parameters and Frontmatter](../frontmatter.md)) MUST NOT fire under this regime — this is a regime-scoped carve-out mirroring the `subagent fn` `with { system: … }` precedent.
- **No-recursion guarantee.** The regime applies **only to the process root**. A nested `mode: subagent` callee invoked *by* this theta (via `invoke(...)` or a `.theta`-callable call) spawns its own child `pi` process in the normal way; the marker is set per child launch and governs only that child's own root theta, so no recursion of the regime occurs within a single process.

<a id="subagent-launch-contract"></a>
**Launch contract.** The child inherits the parent's **full environment** and runs with the forwarded `ctx.cwd` as its working directory, so parent and child read the identical settings, profiles, and credential sources. Argv and the marshalled channels are assembled from the same inputs the subagent invocation consumes:

| Subagent-invocation input | Child-process carrier |
|---|---|
| the parent's discovery-root union (the active roots, [Discovery — Discovery roots](../discovery/discovery-sources.md#discovery-roots)) | `--theta <dirs>` — **one** flag, all roots joined with `path.delimiter` per the discovery CLI-source convention ([Discovery — Discovery sources](../discovery/discovery-sources.md)); omitted when the root set is empty; inherits the CLI source's accepted delimiter-collision caveat (a root path containing the delimiter itself cannot be escaped) |
| resolved-and-interpolated frontmatter `system:` | `--system-prompt <text>` (consumed by the subagent-root regime, [PIC-58](#pic-58)); emitted newline-prefixed so the value is read as text and never as a path — see [*`--system-prompt` is emitted as text*](#subagent-system-prompt-text) below |
| the callee slug | `-p "/<slug>"` (one invocation per process) |
| the theta's callable set (`tools:` allowlist) | `--tools <name1,name2,…>` — **optional** defence-in-depth; the child theta enforces its own callable set regardless |
| empty callable set | `--no-tools` when `--tools` is passed at all (the CLI's explicit empty active set) |
| `.theta` callables in `tools:` | resolved child-side by name, plus content-hash verification (see [*`.theta` callable content-hash verification*](#subagent-theta-callable-hash) below) |
| the theta's resolved `model` | `--provider <p> --model <id>` (reference only, re-resolved by the child; see [*Model marshalling*](#subagent-model-marshalling) below) |
| already-typed `params` values | marshalled structurally on `PI_THETA_PARAMS` / `PI_THETA_PARAMS_FILE` (see [PIC-60](#pic-60)) |
| the per-chain invoke-depth counter | marshalled as wire-level data on an environment variable (see [Invocation — Invocation depth bound](../invocation.md#inv-4)) |
| in-memory / ephemeral transcript | `--no-session` (no session file written) |
| empty skills / prompts / themes / context files | the host dialect's **ambient-isolation** flag group (Pi: `--no-skills --no-prompt-templates --no-themes --no-context-files`; Oh-My-Pi: `--no-skills --no-rules`) — see [*Host CLI dialect*](#subagent-host-cli-dialect) below |
| full extension discovery is the point | (no extension-discovery opt-out by default — extensions load in the child; the opt-in [test-harness extension pin](#subagent-extension-pin) below prefixes the dialect's **disable ambient extension discovery** flag plus `-e <dir>`, i.e. `-ne -e <dir>` on Pi and `--no-extensions -e <dir>` on Oh-My-Pi) |
| project-local trust inference | the host dialect's **project-trust** / **withhold-project-trust** flag group per the trust rule (Pi: `--approve` / `--no-approve`; both arms inexpressible — and therefore empty — on Oh-My-Pi) — see [*Isolation and trust*](#subagent-isolation-and-trust) and [*Host CLI dialect*](#subagent-host-cli-dialect) below |
| forwarded `ctx.cwd` | child working directory |
| regime selection | `PI_THETA_SUBAGENT_ROOT=<slug>` (parent-launcher only; [PIC-58](#pic-58)) |

<a id="subagent-host-cli-dialect"></a>
**Host CLI dialect (intent-level flag groups).** Four of the argv elements above are named as **intents**, not as fixed flag spellings, because the hosts that run a theta do not share a flag vocabulary. Each intent is supplied by the running host's **CLI dialect**, selected from the host's own `CONFIG_DIR_NAME` constant read off the loaded SDK module — `.omp` selects the Oh-My-Pi dialect, and every other value (including an absent one) selects the authored Pi dialect, so an unrecognised host behaves exactly as it did before the dialect seam existed. There is no environment override for the selection: it could only weaken isolation, and on a host that loads a project `.env` into the environment it would also be repository-writable.

| Intent | Pi spelling | Oh-My-Pi spelling |
|---|---|---|
| disable ambient extension discovery (the [extension pin](#subagent-extension-pin)'s first half) | `-ne` | `--no-extensions` |
| ambient isolation (no non-theta instruction sources) | `--no-skills --no-prompt-templates --no-themes --no-context-files` | `--no-skills --no-rules` |
| project trust (trust project-local files in the child) | `--approve` | *(inexpressible — empty)* |
| withhold project trust (least privilege) | `--no-approve` | *(inexpressible — empty)* |

**An intent the running host cannot express is an EMPTY flag list, never a substitute borrowed from a different control.** Oh-My-Pi exposes no prompt-template or theme opt-out, so a child there inherits those ambient sources and the isolation guarantee weakens accordingly; the isolation that *is* expressible is expressed, and that host's `--no-rules` is an ambient-instruction source Pi has no counterpart for, belonging to the same intent as `--no-context-files`. A Pi-spelled argv is not a safe default on the other host: Oh-My-Pi rejects unknown flags outright and exits before any session starts, which the parent observes only as a child exit without an envelope ([PIC-59](#pic-59)), whereas Pi absorbs unrecognised flags into its extension-flag map, so a mis-spelled group degrades to no isolation at all rather than to a diagnostic.

**Project trust is inexpressible on Oh-My-Pi in both directions.** That host has no project-trust flag, and its similarly-named `--auto-approve` / `--approval-mode` govern **tool-call approval** — a different control with a different blast radius — so neither trust arm is mapped onto them: Pi's pair sets its own project-trust override ("trust project-local files for this run" / "ignore project-local files for this run"), while mapping it onto tool-call approval would both over-grant (auto-approving every write and exec) and wrongly restrict (an always-ask mode denies write and exec in a headless child that has no UI to prompt). A child on Oh-My-Pi therefore keeps that host's own default posture toward project-local files, in **both** trust directions — a documented limitation of running on that host, not a silent substitution.

<a id="subagent-control-plane-authentication"></a>
**Control-plane authentication (inherited `PI_THETA_*` values).** The `PI_THETA_*` variables in the launch contract form its **control plane**: they select the process regime, supply callee params with the binder bypassed, seed the invoke-depth ceiling, carry the callable-hash tamper check, and — under the opt-in [extension pin](#subagent-extension-pin) below — name a file to load as an extension. Each is written by a pi-theta parent launcher at spawn, but the environment is not a channel this extension can treat as parent-authored on every host: a host may populate it from files found in the working directory (Oh-My-Pi loads `<cwd>/.env` before any provider lookup), and the variable names are ordinary env keys. Every control-plane read therefore authenticates the carriage first: inherited values are honoured only when `PI_THETA_SUBAGENT_PARENT_PID` equals the reading process's **real parent pid** — a per-run, externally-assigned value a file written ahead of time cannot state. A genuine child always authenticates, because its launcher writes that variable beside the others (`buildSubagentChildEnv` spreads its own markers last). On a mismatch — including the ordinary top-level session, where no launcher wrote anything — the **whole control plane is dropped** and every value is re-derived per launch: no regime selection, no marshalled params or hashes, no pin. The gate **narrows the channel rather than closing it** — a writer able to observe the live process tree can still name the pid; what it removes is the write-a-file-and-wait case. A process that tops a chain by hand (a test harness setting the extension pin) authenticates the same way: it writes the parent-pid carriage beside its values — its own `ppid` when the extension composes in-process, its own `pid` into the env of a host process it spawns.

<a id="subagent-system-prompt-text"></a>
**`--system-prompt` is emitted as text.** A non-empty resolved `system:` value MUST be passed newline-prefixed (a single leading `\n`); an empty value MUST be passed exactly as-is. Both hosts path-coerce this argument — one stats the value and reads the named file when it exists, the other opens any newline-free value as a file and falls back to the literal only on a read failure — while the value itself is the theta's frontmatter `system:` text after `${param}` interpolation, whose params come from model output on the binder path. Reading it as a path would therefore install file bytes as the child's system prompt and relay them to the parent in the return envelope. A leading newline defeats both coercions at once, because no path can contain a newline, and a leading blank line is semantically inert in a system prompt. The empty value is left untouched: both hosts read a falsy value as "no CLI system prompt" and fall back to their built-in default, which is what a theta that declares no `system:` intends, and prefixing it would install a one-blank-line prompt and silently discard that default.

<a id="subagent-child-stdio"></a>
**Child stdio.** The child is spawned with **stdin already closed** (`stdio: ["ignore","pipe","pipe"]`) — the same treatment the acceptance harness applies to the outer `pi -p` process it spawns. Pi's json/`-p` startup reads any non-TTY stdin **to EOF before the argv prompt is processed** (piped stdin is prompt input; EOF is the input-complete/start gate), so a parent-held open pipe that nothing writes to or closes deadlocks the pair: the parent awaits the return envelope while the child waits at startup for stdin EOF (bug 0002 — the shipped 0.9.0–0.11.0 spawn config did exactly this, and every real subagent invocation on the `-p` surface hung until externally killed). The child needs no stdin: the prompt rides argv, params ride [PIC-60](#pic-60)'s env/temp-file channel, and stdin is not a control channel either — cancellation is [PIC-66](#pic-66)'s child kill, and stdin-EOF was never an exit signal (see [PIC-65](#pic-65) orphan prevention).

<a id="subagent-extension-pin"></a>
**Child extension identity (opt-in pin).** By default the child argv carries no `-e`/`-ne`: full ambient extension discovery in the child is the point of this design (see [*Isolation and trust*](#subagent-isolation-and-trust)), and on an ordinary operator install ambient discovery re-finds the same installed theta build that is running the parent. That default presupposes parent and child resolve to the *same build* — a parent/child version-skew hazard when the parent runs from an explicitly-pinned extension (a test harness's working tree) while the machine also carries an installed theta: the child silently binds the stale ambient build, emits no envelope (or the wrong wire shape), and the invocation fails closed with nothing naming the skew (bug 0002, defect 2). For that case the launcher honours an explicit opt-in knob: when the environment variable `PI_THETA_SUBAGENT_EXTENSION_PIN` names a Pi extension entry directory, the assembled child argv is prefixed with `-ne -e <dir>`, pinning the child to exactly that build. The pin is a control-plane variable and is honoured only through the [authenticated read](#subagent-control-plane-authentication): a harness that sets it must write the parent-pid carriage beside it, or the pin is silently dropped and the child falls back to ambient discovery — the exact skew the knob exists to prevent. The acceptance harness sets both in the spawned host's env — the pin to the working tree's `extensions/` (mirroring the `-ne -e` pin it already applies to the outer process) and the carriage to its own pid — and each launcher along the chain re-writes both for its own child, so every process in the tree under test binds the same build. Absent the knob — the production default — behaviour is unchanged (ambient discovery).

<a id="subagent-tools-allowlist-suppression"></a>
**`--tools` / `--no-tools` allowlist suppression (defence-in-depth).** Because the child runs the whole callee, the child theta's own callable set is authoritative for both model-facing and code-side reach; the parent-passed `--tools` allowlist is **not required for correctness** and serves only as defence-in-depth against the child's session inheriting Pi's default built-ins. When the allowlist is passed, three behavioural sub-properties the CLI-flag surface does not encode in its argument type carry the isolation intent: (1) an explicit non-empty `--tools` list restricts the child session's active tool set to exactly those names; (2) `--no-tools` yields an empty active set distinct from omission; and (3) omitting both `--tools` and `--no-tools` re-enables Pi's default `read` / `bash` / `edit` / `write` built-ins — which is why the launch contract passes `--no-tools` for an empty callable set rather than omitting the flag. These are re-validated on each Pi minor bump per item (am) of the *Editorial-review checklist for unpinned host presuppositions* under [Pi version bump procedure](./version-bump-intro.md#pi-version-bump-procedure) below. Built-in Pi tools are selected by name; the child registers them natively at startup, so no per-tool built-in materialisation crosses the boundary.

<a id="subagent-theta-callable-hash"></a>
**`.theta` callable content-hash verification.** A `.theta` callable name in the callee's `tools:` resolves against the **child's own** registry: the theta extension loads in the child and discovers the same `.theta` / `.thetalib` files from disk. A file edit between parent load and child spawn would make the child silently run a callee the parent never validated — a silent-divergence failure mode, and racy under parallel siblings. Because this design moves the whole callee into the child, the parent-load/child-load skew window widens from the model-facing `.theta` callables to the **whole callee file**: the parent records, at load time, a **content hash of the transitive closure of the root callee `.theta` plus every `.thetalib` import it (and its callable-set `.theta` entries) transitively reach**, and marshals those hashes to the child. The hash carrier (`PI_THETA_SUBAGENT_CALLABLE_HASHES`) is **named on every launch** — carrying this launch's map, or explicitly cleared (absent in the child, not present-and-empty) when this launch marshals none — for the same layering reason [PIC-60](#pic-60) names both params carriers on every launch: the launching process is itself frequently a subagent child still carrying the map of the invocation that launched *it*, and an inherited map reaching a grandchild would verify the caller's callable names against that child's own discovery. The child verifies each hash after its own parse and **refuses the invocation on mismatch** with a precise diagnostic (`theta/runtime/subagent-callable-hash-mismatch`, fail-closed — see [Diagnostics — `theta/runtime/*`](../diagnostics/code-registry-runtime.md)). Full content marshalling (running the child on copies of the parent-loaded sources) is the recorded escalation only if hashing proves insufficient; it is rejected as the default for its disproportionate machinery.

<a id="pic-60"></a> **PIC-60. Marshalled-params channel (binder bypass).** The parent already holds the callee's **already-typed** param values (from the slash binder, an `invoke(...)` caller's typed arguments, or a `tools:` `tool.execute` object). Routing them through the slash string `-p "/<slug> …"` would re-enter the binder — a model turn — and lose typing, so the runtime MUST marshal them structurally as canonical JSON per the theta's `params:` schema and the child MUST validate the received JSON against **the same schema** before running the callee. The channel is **dual**, keyed on a pinned size threshold chosen conservatively under the tightest platform environment-block cap with headroom for the inherited environment (order of **8 KB** payload; Windows caps the entire environment block at ~32 KB):

- **Below the threshold** the JSON travels as the environment variable `PI_THETA_PARAMS=<canonical JSON>`.
- **At or above the threshold** the JSON is written to a **0600** temp file whose path travels as `PI_THETA_PARAMS_FILE`; the child reads and **deletes** it, and the parent's per-invocation `finally` deletes it as a backstop. This is the same temp-file mechanism the return-value envelope names as its escalation (see [PIC-59](#pic-59)), built once for both directions.
- **Both carriers are named on every launch.** The parent's env patch MUST name **both** `PI_THETA_PARAMS` and `PI_THETA_PARAMS_FILE` on every launch — the chosen one carrying its value, the unused one explicitly cleared (absent in the child, not present-and-empty). The patch is layered over the launching process's own inherited environment, and that process is itself frequently a subagent child still carrying the carrier of the invocation that launched *it*, while the child's read prefers the inline carrier and returns before it ever consults the file carrier. A single-key patch therefore cannot clear an inherited sibling: a callee whose own params crossed the threshold would silently run on the inline payload it inherited from its caller instead of on its own, with no refusal anywhere on the path. Clearing the unused carrier is what makes the parent's channel choice authoritative for the child.

Env-only with a size guard is rejected — it would silently narrow the language ("params that fit in an env var") for an implementation reason no author should have to know about. Stdin delivery is rejected — Pi's `-p` mode has its own stdin conventions (its startup reads any non-TTY stdin to EOF as prompt input, per *Child stdio* above), an extension consuming stdin inside a `pi` child is an unprobeable host-behaviour dependency, and the child's stdin is spawned **closed** — there is no stdin channel into the child at all (see the launch contract and [PIC-65](#pic-65)). The **binder is skipped entirely** on the marshalled path: binder inference remains exclusive to human slash invocation ([Slash-Command Argument Binding](../binder.md)), unchanged. Because the binder is unreachable for that theta, the load-time binder-model precondition ([Binder model](../binder/binder-model-and-context.md#binder-model)) MUST NOT be enforced against it: the child's load pass registers the marked root theta whatever its [binder-bypass class](../binder/binder-bypass-and-envelope.md#binder-bypass), and the exemption is scoped to that one theta so it coincides exactly with the dispatch that skips the binder. A received-params payload that fails to parse as JSON, or that fails schema validation against the callee's `params:` schema, refuses the invocation with `theta/runtime/subagent-params-validation-failed` (fail-closed — see [Diagnostics — `theta/runtime/*`](../diagnostics/code-registry-runtime.md)); the failure surfaces to an `invoke` parent through the return envelope as `Err(InvokeInfraError { cause: "validation", ... })`.

<a id="subagent-return-envelope"></a><a id="pic-59"></a> **PIC-59. Return-value envelope.** The child theta's final value MUST reach the parent with `Result` fidelity. The child runtime emits a **single machine-readable envelope** as one JSONL line with the reserved top-level key `theta_result` on stdout, alongside the `--mode json` event stream; the parent matches the reserved key and ignores every other line:

```json
{"theta_result": {"v": 1, "ok": …}}
{"theta_result": {"v": 1, "err": {"kind": "query", "variant": {…}}}}
```

Requirements:

- **`Ok` values** serialise per the runtime value model (JSON-representable by construction).
- **Every `Err` variant** an in-process subagent invocation could surface is representable in the pinned envelope schema: every `QueryError` variant, `CodeToolError`, the `InvokeInfraError` causes, and panics routed as internal-error (`kind: "invoke_infra", cause: "internal_error"`). The envelope schema is **pinned in this contract** and its `err` arm mirrors the `QueryError` union declared in [Errors and Results — QueryError variants](../errors-and-results/queryerror-variants.md#queryerror-variants).
- **Versioning + skew detection.** The envelope schema is **versioned**; parent and child assert compatibility on the reserved version field **`v`** carried inside the `theta_result` payload (`{"theta_result": {"v": <version>, …}}`, as shown above). Because the same installed theta extension serves both sides, skew arises only from a concurrent upgrade — it is **detected, not tolerated**: a version the parent does not recognise refuses with `theta/runtime/subagent-envelope-schema-skew`. A line carrying the reserved key that does not parse against the pinned schema refuses with `theta/runtime/subagent-envelope-parse-failed`.
- **Fail-closed child-exit-without-envelope.** A child that exits without emitting an envelope (crash, kill, timeout) MUST map to `Err(InvokeInfraError { cause: "internal_error", ... })` with the exit detail — **never a fabricated value** — and emit `theta/runtime/subagent-exit-without-envelope` (see [Diagnostics — `theta/runtime/*`](../diagnostics/code-registry-runtime.md)). The companion `theta/runtime/subagent-child-crashed` records the crash exit detail for operator triage on this path.
- **Marked-root registration refusal.** When the child's load pass does not register the marked root slug — for any load- or parse-time reason — the argv `-p "/<slug>"` is no longer a command, the theta runtime is never entered, and no channel the parent reads carries the refusal. The load pass MUST emit the envelope itself, carrying `Err(InvokeInfraError { cause: "load_failure", ... })` whose `message` names the refused root slug and, when a refusing diagnostic is attributable to that theta's file, that diagnostic's code and message; otherwise the message states that no load diagnostic names it. That second arm is reachable two ways: a refusal may carry no file at all (the [entry capability probe](./capability-probe.md#entry-capability-probe)'s unresolved-executable refusal, the [callable-hash mismatch](#subagent-theta-callable-hash)), and the child's discovery walk may have found no file for the slug. `callee_path` carries the theta's discovered path, degrading to the bare slug in that no-file case. Emitting the envelope does not stop the host from processing the argv prompt — that handling belongs to the host, outside this contract — but the parent settles on the envelope as soon as it is written.

Sharing stdout with the event stream is safe by construction: the envelope writer (the theta runtime in the child) and Pi's event writer are the same process, and Node serialises same-process stream writes, so the reserved-key line cannot be split mid-write. **Implementation pin (Pi v0.80.10):** in `--mode json` / `-p` Pi's `takeOverStdout()` reassigns the extension-visible `process.stdout.write` to route to **stderr** (so stray extension stdout cannot corrupt the event channel), while Pi's own event writer keeps a captured raw handle to fd 1. The envelope writer must therefore emit to **fd 1 directly** (`fs.writeSync(1, line)`, one atomic newline-terminated syscall — Windows-safe), NOT through `process.stdout.write`; emitting through the extension API would land the envelope on stderr where the parent's stdout scan never sees it. Stray lines from other extensions can still appear in the stream but cannot corrupt the envelope, and the parent ignores every non-`theta_result` line. A dedicated extra file descriptor is rejected (nonstandard, platform-sensitive on Windows spawn contexts, no atomicity gained). A temp-file handoff (parent-supplied path, atomic write + rename, 0600, read after exit) is the recorded escalation on two named triggers — envelope payloads too large for single-line handling, or observed stream corruption in practice — and if engaged serves the params channel symmetrically ([PIC-60](#pic-60)), one mechanism for both directions. The parent-side subagent contract reduces to **envelope consumption**: the parent launches, awaits the envelope, and maps `ok`/`err` to `Ok`/`Err`.

<a id="subagent-host-loop-dispatch"></a><a id="pic-64"></a> **PIC-64. Code-side extension-tool dispatch and permission surface.** Code-side calls (`<name>(args)`) resolve per the theta's callable set against a **host session that carries an agent loop** — the process's backing host session, present in **both** modes: in **subagent mode** the callee runs under the subagent-root regime inside the spawned child `pi` process; in **prompt mode** the theta drives the user's live host session in the parent process. A third context dispatches through whichever of those two sessions backs its process: an **inline `subagent fn` body** ([Functions — FN-6](../functions.md#fn-6)) runs in-process and off-session — its private conversation offers the model no tools, so the body holds no model-facing extension-tool reach of its own — and its code-side extension-tool calls dispatch through the process's backing host session exactly as the enclosing theta's own code-side calls do: the child's private, discarded session inside a subagent-root child; the user's live session in the parent, with the prompt-mode *Accepted cost* below applying. FN-6's isolation is scoped to the body's conversation — its queries, its transcript, its return value — not to this dispatch channel: the fabricated turn is a mechanical artefact of the rung-2 bridge mechanism, not a leak of the body's conversation; this contract accepts the identical artefact for the enclosing theta's own calls, and rung 1 below — preferred automatically when available — retires the fabricated turn entirely. The resolution is the same in every context:

- **built-ins** — direct `execute` dispatch, unchanged;
- **`.theta` callables** — unchanged (a nested subagent-mode callee spawns its own child per [PIC-58](#pic-58)'s no-recursion rule);
- **extension tools** — **host-loop dispatch**: the runtime registers a theta-controlled provider whose stream function authors the `tool_use` itself, carrying the code-supplied arguments verbatim; the host agent loop (which holds every registered tool's `execute`) runs the call and appends the tool result; the runtime reads the result back and returns it to code. Arguments are deterministic, zero model tokens are spent, and **no executable definition is ever obtained by theta code** — documented Pi APIs only. Host-loop dispatch's costs — a fabricated turn in the transcript and a temporary session-model switch — land in whichever host session backs the dispatch, for the enclosing theta's own calls and for an inline `subagent fn` body's calls alike: inside a subagent-root child the child's **private, discarded session** (never the user's — the whole child process, inline bodies included, touches no user session); in the parent the **user's live session** (accepted and not suppressed, per *Accepted cost* below).

**Accepted cost (prompt mode).** Parent-side the dispatch lands in the user's live session: each code-side call injects a fabricated user message plus a `tool_use` and a tool-result card into the transcript and thrashes the persisted session model (`model_select` fires twice per call — the bridge model in, the prior model restored out). Neither is hidden or suppressed — [SLSH-2](../slash-invocation.md#slsh-2) pins that prompt-mode tool calls render as ordinary, user-visible Pi tool-call cards in the transcript and are not suppressed, so the fabricated cards appear in the user's own transcript by construction. The cost applies identically when the code-side call sits inside an inline `subagent fn` body — the body's conversation-scoped isolation (FN-6) does not suppress the dispatch channel. This transcript pollution and model thrash in the user's session is the **accepted** cost of the zero-token code channel; per-call latency is negligible next to a real model turn. It is stated here so it is not read as a defect. Subagent mode confines the identical costs to the child's private, discarded session (`--no-session`), touching no user session.

**Code-side dispatch ladder (fail-closed).** Extension-tool code-side dispatch resolves against a probe-asserted, fail-closed ladder:

1. **Preferred rung (first-class direct executable definition):** an upstream `pi.getToolDefinition` on the extension API — a clean registry read that would replace host-loop dispatch without changing the process architecture of either mode. The runtime records this rung as **available** when `typeof pi.getToolDefinition === "function"` **and** a rung-1 dispatcher is wired (a non-gating optional-capability record — *not* one of the six [Step 0](./capability-probe.md#entry-capability-probe) checks [PIC-5](./capability-probe.md#pic-5) closes; its absence selects rung 2, never a load refusal) and prefers it **automatically** when available, in both parent and child. The dispatcher conjunct keeps registration and dispatchability in agreement: the same record drives both the load-time rung-3 refusal and runtime routing, so a bare SDK surface with no dispatcher behind it must not be recorded available. Requested upstream, so far refused; when it lands — SDK surface and dispatcher together — it slots in as the top rung in both contexts. *Non-normative.* A one-line `getToolDefinition` delegation on `ExtensionAPI` would let the code-side path collapse to a registry read and retire the parent-side host-loop machinery entirely (no bridge provider, no transcript pollution); theta 1.0 neither specifies nor requires that upstream change — the ladder simply prefers rung 1 whenever it appears.
2. **Current rung:** host-loop dispatch (above).
3. **No rung available:** a theta whose code calls an extension tool **refuses to register** with `theta/load/extension-tool-unreachable` (fail-closed — see [Diagnostics — `theta/load/*`](../diagnostics/code-registry-load.md)), naming the tool and the reason; the runtime never silently falls through. The refusal is a hard, probe-asserted gate rather than a silent degrade: under `pi -p` an un-registered slug falls through to the ordinary agent and *looks* like it worked, so a precise diagnostic — not silent absence — is the only safe outcome. A code-side call whose tool resolved only at the **model-facing** rung (admitted for `@`-query reach but with no code-side execution rung established) raises a precise `CodeToolError`, never a fabricated value. The load-time refusal walks the theta's own body (its direct and local-`fn` code-side call sites, `subagent fn` bodies included); a code-side extension-tool call inside an imported `.thetalib` `fn` cannot arise, since a `.thetalib` fn naming a caller-scoped extension tool fails its standalone parse with `theta/parse/unknown-identifier` and un-registers the importer first, and the runtime host-loop rung remains the fail-closed floor for any path that bypasses the load check.

**Host-loop wiring (pinned by the shipped implementation, Pi v0.80.10).** The rung-2 mechanism resolves these otherwise-open contract details as follows (verified end-to-end by the RFC-0006 prototype and wired in `src/extension/production-host-loop-dispatch.ts`): (a) the theta-controlled provider is registered via `pi.registerProvider` under a **per-dispatch unique name** (`theta-host-loop-bridge-<nonce>`) with a dummy literal `apiKey` (so the bridge model is selectable with no network call) and a required dummy `baseUrl`, and torn down via `pi.unregisterProvider` after the turn; (b) the code-supplied request is encoded as a marker-prefixed user message the provider's two-state `streamSimple` decodes and authors as the `tool_use` with the arguments **verbatim**, keyed on the dispatch nonce so unrelated turns are tolerated; (c) the fabricated turn is awaited on the **`agent_settled` event, armed before `sendUserMessage`** in both modes; arming on `agent_settled` rather than `waitForIdle()` is load-bearing specifically in the subagent-mode child leg, where `waitForIdle()` alone returns before the `-p`/print-mode turn even starts and so is insufficient (the parent prompt-mode leg arms the same event before the same call); (d) the tool result is read back from `ctx.sessionManager.getEntries()` by matching the newest `toolResult` message whose `toolName` equals the dispatched name (its `isError` is preserved to code); (e) the dispatched tool is installed as the sole active tool for the turn via the PIC-17 `pi.setActiveTools` snapshot/restore protocol, and the session model is switched to the bridge and **restored in a `finally`** (never left installed, incl. the abort path); (f) concurrent code-side dispatches are serialised, since the session-model switch is a shared session resource. The rung is establishable wherever a real host session with an agent loop and the required Pi surfaces is present — inside the subagent-root child (subagent mode) **and** in the parent against the user's live host session (prompt mode); the (a)–(f) wiring is identical in both, the only difference being which session backs the dispatch (the child's private `--no-session` session vs. the user's live session, per *Accepted cost* above). A context with no host session or missing Pi surfaces keeps the rung unavailable (fail-closed → rung 3). An inline `subagent fn` body is not such a context: it dispatches through the process's backing host session, so its rung availability is the process's own — refusal tracks rung availability, never the process regime, the frontmatter mode, or the enclosing construct.

**Permission surface.** Code-side dispatch of extension tools introduces **no new permission gate**, deliberately. The model-turn checkpoint it removes was already removed by the language itself: since RFC 0002, theta code calls `bash` with fully computed arguments, and `bash` is the maximal capability — an extension tool cannot do to the machine anything `bash` cannot. The effective gates are the existing ones, **one consistent rule across prompt and subagent modes**: (1) the author's `tools:` declaration — a theta calls only what its frontmatter declares, readable by any operator; (2) the operator's extension-install and trust decisions — applied to the user's live session directly in prompt mode, and inherited by the child via the necessity-inference trust rule (`--approve`, see [*Isolation and trust*](#subagent-isolation-and-trust)) in subagent mode; (3) fail-closed registration (rung 3 above). Per-tool capability annotations are rejected (author burden encoding a distinction with no security rationale); runtime approval prompts are rejected (they destroy the channel's purpose — deterministic, unattended orchestration — and a headless subagent child has nobody to ask). Because code-side dispatch travels through the host agent loop, any tool-execution permission machinery Pi itself ever adds sits in the path automatically — **host-loop routing is the seat for any future Pi-level tool-permission gate**, and theta needs no gate of its own for a future Pi gate to apply.

<a id="subagent-model-marshalling"></a>
**Model marshalling.** The model crosses the boundary as a **reference** (`--provider <p> --model <id>`), never as a live object, and **credentials are never marshalled**: with full env inheritance and a shared agent dir, parent and child read the identical config universe, so credential skew is structurally impossible. Explicit credential marshalling (`--api-key`, env injection) is rejected: the parent cannot extract auth from Pi's extension API, and argv/env secrets are a security regression. One case has no prior-art cover: a theta with `model:` absent inherits the caller's *live session model*, state that exists only in the parent session. For that path the parent marshals its live session model as the `--provider`/`--model` reference, and the child **re-resolves** it against its own (identical) config universe. The child confirms — from its own model registry, without any RPC round-trip — that the reference resolved to the intended model and **fails the invocation** with a precise diagnostic (`theta/runtime/subagent-model-preflight-mismatch`) naming expected vs. resolved when it did not; the failure surfaces to the parent through the return envelope. Credential failures are not pre-flightable without a provider call and surface through the child's own [provider-error mapping](./provider-error-mapping.md#provider-error-mapping) into the envelope.

<a id="subagent-pre-spawn-model-guard"></a><a id="pic-62"></a> **PIC-62. Pre-spawn model guard and child-side model resolution.** The `model` reference marshalled to the child is the theta's resolved model — the theta's frontmatter `model:`, or the model inherited at invocation time when `model:` is absent (resolution owned by [Parameters and Frontmatter — `model`](../frontmatter.md)). The guard has two obligations:

1. *Resolved value not `undefined` (parent-side).* When resolution yields `undefined` — frontmatter `model:` absent and the inherited `ctx.model` is `undefined` — the runtime MUST NOT spawn the child; it fails the invocation with `theta/runtime/subagent-model-unresolved` (see [Diagnostics — `theta/runtime/*`](../diagnostics/code-registry-runtime.md#thetaruntime-runtime-panics-runtime-defect-surface-and-delivery-failures)). The check runs per invocation, after `ctx.model` is captured and before the spawn, and behaves identically at the slash-command, `tools:` `tool.execute`, and `invoke(...)` entry points.
2. *Child-side resolution confirmation.* The child re-resolves the marshalled reference against its own model registry and, per [*Model marshalling*](#subagent-model-marshalling) above, fails with `theta/runtime/subagent-model-preflight-mismatch` on mismatch — reported to the parent through the return envelope rather than over any RPC state surface. The re-resolution key is the **fully-qualified `provider/id`** form, assembled from both halves of the marshalled reference (`--provider <p> --model <id>`), not a bare model id: a bare id is not a unique key in a registry that serves one model through several providers (a first-party endpoint beside a gateway), where it matches more than one available model and therefore resolves to none — a total non-resolution reported as a mismatch against the intended reference. The code's Message template is unchanged (see [Diagnostics — `theta/runtime/*`](../diagnostics/code-registry-runtime.md)).

Both failures are terminal for that invocation — the runtime does not retry — and surface through the same per-surface channels as the runtime-defect surface in [Errors and Results — Runtime panics](../errors-and-results/error-model.md#runtime-panics): a `theta-system-note` on the slash/prompt surface, and `Err(InvokeInfraError { kind: "invoke_infra", cause: "subagent_model_unresolved", ... })` (or `cause: "subagent_model_preflight_mismatch"`) to an `invoke` parent.

<a id="subagent-isolation-and-trust"></a>
**Isolation and trust.** The in-process clean room (empty resource loader, zero extensions) is rebuilt from the launch contract's **ambient-isolation** intent plus `--no-session` (Pi spells that group `--no-skills --no-prompt-templates --no-themes --no-context-files`; see [*Host CLI dialect*](#subagent-host-cli-dialect) above), audited at the Pi pin to reproduce the empty-member behaviour. On a host that expresses only part of the group the child inherits the unexpressed ambient sources, and the guarantee below weakens by exactly those sources. Two deliberate dispositions:

- **Extension ambience is accepted and stated.** Full extension discovery in the child is the point of this design, and loaded extensions contribute more than tools (system-prompt appends, handlers, providers). The isolation guarantee is stated spec-side as: *no user/project context (files, skills, templates) is inherited; installed extensions' contributions are present, as in any Pi session.* This is a spec-visible weakening, stated rather than hidden. Curated loading (`--no-extensions` + explicit `-e` per the `sourceInfo` of each declared tool) is the recorded escalation if extension ambience proves contaminating.
- **Project-local trust is inherited by necessity-inference.** The launcher supplies the **project-trust** intent **iff** the callable set contains a tool whose `pi.getAllTools()` source scope is **project-local** — the parent could only have admitted that tool because the operator already trusted its extension in the parent session, so the child inherits a decision already made — and the **withhold-project-trust** intent otherwise (least privilege). A tool whose source scope the host does not publish contributes no trust, the same conservative answer a name absent from the snapshot gets (see [Capability inventory — Tool registration and gating](./capability-inventory-items.md#sdk-cap-tool-registration-gating)). Pi spells the two intents `--approve` / `--no-approve`; on Oh-My-Pi both are inexpressible, so the inference still runs but emits no flag and the child keeps that host's own default posture toward project-local files — a documented limitation of running there, per [*Host CLI dialect*](#subagent-host-cli-dialect).

<a id="subagent-untyped-query-ok-extraction"></a>
**Query mechanics run in the child.** Every query the subagent callee issues — untyped and typed alike — executes **inside the child** against its own host session, using the same prompt-mode conversation-drive mechanics the [prompt-mode driver](./conversation-drive.md) pins (untyped-query trailing-turn extraction, the `stopReason: "error"` transport short-circuit, the typed-query two-phase free-phase / forced-respond loop, and respond-repair). The parent runs **no** per-query extraction and holds no session handle; it only consumes the final-value envelope ([PIC-59](#pic-59)). The typed-query forced-respond turn runs off-session in the **child** through pi-ai's `complete()` free function, so its provider errors are classified by the child's own [Provider error mapping](./provider-error-mapping.md#provider-error-mapping) — the mapping table follows the interpreter into the child. The child transcript is ephemeral (`--no-session`): the spec mandates the transcript stays private to the theta and is discarded when the theta returns; `--no-session` + the child session being **process-private** (never Pi's user-facing UI) is the mechanism, and user-visible behaviour is specified in [Slash-Command Invocation — User-visible streaming](../slash-invocation.md#slsh-2). Each subagent-mode invocation gets its own child process, its own captured `tools:` table, and its own derived `AbortSignal`; sibling invocations triggered by parallel tool calls do not share mutable state.

<a id="subagent-error-fidelity"></a>
**Error fidelity.** Typed error values (`QueryError`) are reconstructed in the parent from the child's `theta_result` envelope rather than from live in-process objects, with expected fidelity loss of **zero**: the child runs the identical query machinery the in-process path ran, and every `Err` variant it can produce is representable in the pinned envelope schema ([PIC-59](#pic-59)). The [Provider error mapping — subagent `QueryError` audit](./provider-error-mapping.md#subagent-queryerror-audit) tables every variant the child surfaces and its envelope encoding. Two child-lifecycle failure classes are pinned there, both mapping to the fail-closed internal-error path rather than a fabricated value: **child crash / nonzero exit without an envelope** (`theta/runtime/subagent-exit-without-envelope`, with `theta/runtime/subagent-child-crashed` recording the crash detail) and **envelope corruption** (`theta/runtime/subagent-envelope-parse-failed` / `theta/runtime/subagent-envelope-schema-skew`). Extending the envelope (richer child→parent state) is held in reserve only if the audit exposes a gap; degraded fidelity without the audit is rejected.

<a id="subagent-cli-wire-pins"></a>
*CLI-flag and wire pins.* The Pi-owned surfaces this design consumes by name are pinned to the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin) on `@earendil-works/pi-coding-agent`, on the same footing as the other consumed Pi surfaces on this page — and, unlike a `.d.ts` type, are **not** `typeof`-probable, so they are re-audited by editorial review at bump time rather than by the SDK surface-inventory literal-read assertion:

- **Consumed CLI flags:** `--theta`, `--mode json`, `-p`, `--no-session`, `--system-prompt`, `--tools`, `--no-tools`, `--provider`, `--model`, `--no-skills`, `--no-prompt-templates`, `--no-themes`, `--no-context-files`, `--approve`, `--no-approve` (verified via `pi --help` at v0.80.10). Their semantics — chiefly the `--tools` / `--no-tools` suppression sub-properties ([PIC-58](#subagent-tools-allowlist-suppression) allowlist rule) and the `--no-session` ephemeral-transcript behaviour — are re-audited per item (am) and item (aj) of the editorial-review checklist under [Pi version bump procedure](./version-bump-intro.md#pi-version-bump-procedure) below. The `--no-skills` … `--no-approve` tail of that list is the Pi spelling of two of the four dialect-supplied intents (ambient isolation, and the project-trust pair); the other two — disable ambient extension discovery, spelled `-ne` on Pi, and its `-e` companion — are consumed only under the opt-in [extension pin](#subagent-extension-pin). The Oh-My-Pi spellings enumerated at [*Host CLI dialect*](#subagent-host-cli-dialect) (`--no-extensions`, `--no-rules`, and that host's two empty project-trust arms) are audited against that host at the same checkpoint, on the same editorial-review footing.
- **Consumed stdout wire surface:** the `--mode json` event stream (line-oriented JSON events on stdout) and the reserved-key `{"theta_result": …}` envelope line ([PIC-59](#pic-59)) — same-process write serialisation, stray-line tolerance, and reserved-key matching. The **stdin-EOF input-complete/start behaviour** the launch contract's [*Child stdio*](#subagent-child-stdio) disposition depends on — pi's json/`-p` startup reads any non-TTY stdin to EOF *before* the argv prompt is processed, so a child spawned with closed stdin (`"ignore"`) starts immediately while an open never-closed pipe blocks it at startup; EOF is a **start** gate, never an exit signal (bug 0002 corrected the former "stdin-EOF exit" pin, which was false) — joins the same version-bump audit item RFC 0005 pins for the RPC child, extended to `-p` mode. These are re-audited per the CLI/stdout-protocol editorial-review items enumerated under [Pi version bump procedure](./version-bump-intro.md#pi-version-bump-procedure) below.

<a id="subagent-state-isolation-matrix"></a>

**Subagent state-isolation matrix.** A subagent-mode invocation runs in an isolated child process whose state composition is fixed by the table below. The matrix is the canonical enumeration of what the child inherits from the theta's frontmatter, what is forwarded from the caller's `ExtensionCommandContext`, and what is *not* inherited. The middle column is deliberately **narrow**: under this design nothing of `ExtensionCommandContext` crosses into the child except `cwd` and the marshalled model reference. Everything else the child needs is **explicitly marshalled** on named channels — the enumeration is closed at four: **params** ([PIC-60](#pic-60)), the **model reference** ([PIC-62](#pic-62)), the **invoke-depth counter** ([Invocation — Invocation depth bound](../invocation.md#inv-4)), and the return **envelope** ([PIC-59](#pic-59)). A future widening of any cell is a spec-versioned change.

| Inherited from the theta's frontmatter | Forwarded from the caller's `ExtensionCommandContext` | Not inherited from the caller |
|---|---|---|
| `system:` prompt (with `${param}` interpolation resolved at conversation-creation time) → `--system-prompt` | `ctx.cwd` (child working directory) | caller's transcript (the child runs `--no-session`; transcript is ephemeral, private, and discarded when the theta returns) |
| `model` — marshalled as a **reference** (`--provider <p> --model <id>`), re-resolved and confirmed child-side ([PIC-62](#pic-62)); never a live object, never credentials | marshalled **model reference** (the resolved `--provider`/`--model`; `ctx.modelRegistry` does **not** cross the process boundary) | caller's system prompt (the child's `--system-prompt` is the *complete* prompt; no user/project context, files, skills, templates, or context files are inherited — the host dialect's ambient-isolation group, spelled `--no-skills --no-prompt-templates --no-themes --no-context-files` on Pi; a host that expresses only part of the group inherits the rest, per [*Host CLI dialect*](#subagent-host-cli-dialect)) |
| the theta's callable set (enforced child-side; optionally mirrored to `--tools` / `--no-tools`); `.theta` callables content-hash-verified child-side | (nothing else of `ExtensionCommandContext` crosses — in particular `ctx.getContextUsage` and `ctx.modelRegistry` do **not** cross the process boundary) | ambient Pi tool set (the child theta enforces its own callable set; installed extensions' contributions — tools, system-prompt appends, handlers, providers — **are** present in the child, as in any Pi session, a stated isolation weakening per [*Isolation and trust*](#subagent-isolation-and-trust)) |
| captured `params` — **explicitly marshalled** as canonical JSON ([PIC-60](#pic-60)) | | caller's `thetaAbort` controller (each invocation gets a fresh `AbortController`; cancellation forwards by killing the child — a process-tree kill on Windows, a direct `SIGKILL` elsewhere; see [PIC-66](#pic-66) — not via shared controller identity) |
| | | caller's `params` and variable bindings (the subagent runs a different theta file with its own `params`) |
| | | caller's `withActiveTools` snapshot scope (subagent-mode tool selection is the child session's own active-set protocol under [PIC-58](#pic-58), not the parent's `pi.setActiveTools`) |

**Explicitly-marshalled enumeration (closed).** Exactly four artefacts cross the process boundary as marshalled data, on named channels: (1) **params** — canonical JSON on `PI_THETA_PARAMS` / `PI_THETA_PARAMS_FILE` ([PIC-60](#pic-60)); (2) **model reference** — `--provider`/`--model` ([PIC-62](#pic-62)); (3) **invoke-depth counter** — an environment variable ([Invocation — Invocation depth bound](../invocation.md#inv-4)); (4) the return **envelope** — the `theta_result` stdout line ([PIC-59](#pic-59)). Adding a fifth marshalled artefact is a spec-versioned change.

The matrix is consumed by `spec.md`'s preamble forward-link and by [Overview — Scope of a Theta File](../overview.md#scope-of-a-theta-file)'s isolation prose. The restated isolation guarantee — *no user/project context is inherited; installed extensions' contributions are present, as in any Pi session* — is the canonical wording those consumers restate.

<a id="pic-65"></a> **PIC-65. Subagent child-process lifecycle and orphan prevention.** *(Successor of the retired [PIC-9](#retired-req-ids) — re-coined in the bug-0002 fix, which falsified PIC-9's stdin-EOF-exit premise.)* The runtime owns the spawned child process for exactly the duration of one subagent-mode theta invocation. Teardown is mandatory and runs in a `finally` block that wraps the entire parent-side invocation against that child, so it fires on:

- normal return (the child emitted its `Ok` envelope);
- any `Err` returned to the parent (envelope `err`, child-exit-without-envelope, validation failure, cancellation);
- any panic raised inside the parent-side invocation path;
- any unexpected exception thrown by the parent runtime or the Pi SDK.

**Teardown.** The per-invocation `finally` awaits child exit; if the child does not exit within the existing `SHUTDOWN_AWAIT_CAP_MS = 2000` budget, the runtime **kills** it (a process-tree kill on Windows; a direct `SIGKILL` to the child process elsewhere). On the normal path the child has already exited when teardown runs — one invocation per process: the child emits its envelope and self-exits — so the bounded await short-circuits on the recorded exit. The `finally` also releases any residual parent-held stdin handle, a structural no-op under the launch contract's [*Child stdio*](#subagent-child-stdio) disposition (the child's stdin is spawned closed; the release exists only so a non-production child handle with a live stdin is still released, and it is not a shutdown signal — stdin-EOF never made a `-p` child exit). `disposeBarrier` settles on **observed child exit**. Teardown is invoked at most once per child and treated as idempotent at the call site. The same `finally` also detaches the one-shot `thetaAbort.signal` listener registered at spawn (per [PIC-66](#pic-66)) and deletes any `PI_THETA_PARAMS_FILE` temp file as the [PIC-60](#pic-60) backstop. If a teardown step itself throws (the stdin release or the kill call), the runtime logs it via `theta/runtime/subagent-dispose-failure` (re-scoped from its former `AgentSession.dispose()`-throw trigger to any subagent-mode teardown-step throw, keeping the stable diagnostics-contract code name; see [Diagnostics](../diagnostics.md)) but does not alter the invocation result — the diagnostic is advisory only. On an `Err`/panic teardown the original error is not masked; on a normal-return teardown the parent still observes the theta's `Ok` final value. The `session_shutdown` handler's `SHUTDOWN_AWAIT_CAP_MS` budget covers the entire teardown phase, including the bounded await of child exit and the kill fallback.

<a id="subagent-orphan-prevention"></a>**Orphan prevention** — a layered guarantee for a hazard with no in-process counterpart (a child outliving a dead parent is an unattended agent with tool access):

1. *Controlled parent paths* (normal return, errors, `/reload`, session shutdown, catchable process exit): the runtime kills the child per the teardown rule above. **Hard obligation.**
2. *Uncontrolled parent death* (hard kill, OOM): **no implemented tether exists at theta 1.0** — a recorded behavioural gap, stated rather than hidden. The mechanism this layer formerly pinned — Pi's `-p` mode "exiting on stdin EOF" when the OS closes the parent-held pipe on parent death — was falsified empirically (bug 0002): a `-p` child *reads* stdin to EOF at startup, before its prompt is processed, so EOF is the input-complete/**start** gate and never an exit signal (an orphan whose stdin pipe broke would *begin or continue* its run, not stop); and with stdin now spawned closed per [*Child stdio*](#subagent-child-stdio) there is no parent-death pipe-close signal at all. The recorded fallback — now the layer's designed mechanism — is the **child-side parent-PID watchdog**, guaranteed wireable because the theta extension always loads in the child and the parent-launcher env marker carries the parent PID (`PI_THETA_SUBAGENT_PARENT_PID`, per [PIC-58](#pic-58)); it is **explicitly unimplemented**: the carriage is written by the launcher and read by nothing, so the wire is in place and implementing the watchdog needs no contract change. Recorded here, on the owning topic page, per [Future Considerations](../future-considerations.md)' known-gap convention.
3. *Residual exposure*, restated honestly for the gap above: a child orphaned by uncontrolled parent death runs its single invocation to completion unattended — including any in-flight and subsequent model turns of that invocation, with tool access — and then terminates on its own (one invocation per process; the child self-exits after emitting its envelope). The orphan window is bounded by one invocation, not unbounded lingering; shrinking it is what layer 2's watchdog is for. OS-level tethering (Job Objects / `PR_SET_PDEATHSIG`) remains **rejected** — platform-specific native dependencies contradict the codebase's dependency posture.

**Spawn failure** (ENOENT, EPERM, immediate exit) routes as an unanticipated SDK reject does: `theta/runtime/internal-error`, no child to tear down, plus a dedicated `theta/runtime/subagent-spawn-failed` for operator triage. The registry entry from **`ActiveInvocationRegistry`** is removed by the same `finally`.

Subagent-mode tool registration has no separate teardown step: the child registers its own tools at startup and they die with the child process; the parent never registers anything for the subagent. The per-invocation `finally` also settles the `disposeBarrier` promise the runtime registered with the **`ActiveInvocationRegistry`** — on observed child exit — and removes the registry entry. This is what lets the `session_shutdown` handler's `Promise.allSettled(...)` await observe completion of an in-flight subagent invocation that was cancelled by the teardown handler's `thetaAbort.abort()` call.

Edge cases:

- The `finally` block must run even when the parent's `AbortSignal` fires before the child's first turn — spawn-then-immediate-cancel still requires the child to be killed.
- For nested subagent invocations, each level owns its own child process and runs its own `finally`; teardown order is deepest-first, naturally produced by the call stack's `finally` unwinding.
- Teardown must precede the parent observing the result — the parent's `match`/`?` arm runs after the child has exited, so no child listener can leak into work the parent does next.

<a id="pic-66"></a> **PIC-66. Cancellation — abort → child kill.** *(Successor of the retired [PIC-63](#retired-req-ids) — re-coined in the bug-0002 fix, which falsified the stdin-close "grace signal".)* A `-p` child exposes **no RPC abort command**, and under the launch contract's [*Child stdio*](#subagent-child-stdio) disposition its stdin is spawned closed — there is no in-band signal channel into a running child. Cancellation of a subagent child is therefore effected by **killing it**: a process-tree kill (`taskkill /T`) on Windows; a direct `SIGKILL` to the child process elsewhere. Nested-descendant reaping on POSIX is **not promised** at theta 1.0 — `SIGKILL` runs none of the killed child's own `finally` teardown, so a nested grandchild that child had spawned is orphaned into the recorded [PIC-65](#pic-65) layer-2 gap, bounded by its own one-invocation window. Immediately after the child spawn is initiated and its stdio is wired, the runtime registers a one-shot listener on `thetaAbort.signal` that initiates the kill. The listener is the sole cancellation-forwarding mechanism in subagent mode. If `thetaAbort.signal.aborted` is already true at the moment the child stdio is ready, the runtime initiates the kill synchronously *before* the listener is registered, so the spawn-then-immediate-cancel path remains correct without depending on microtask ordering. The listener is detached in the same per-invocation `finally` that tears the child down (per [PIC-65](#pic-65)). The kill destroys the parent-held stdio pipes so the child's terminal close is observed deterministically; the drive then settles `Err(cancelled)` — the cancellation short-circuit wins over the exit-without-envelope map ([PIC-59](#pic-59)) — and teardown proceeds through [PIC-65](#pic-65), whose bounded-await → kill sequence bounds even a kill that failed to take effect within the `SHUTDOWN_AWAIT_CAP_MS` budget. If initiating the kill throws, the runtime traps the error and routes it through `theta/runtime/internal-error` (see [Diagnostics](../diagnostics.md)) but does not alter the invocation result — mirroring the teardown-throws rule. The runtime is re-entrancy-safe by construction: the one-shot listener and the one-shot guard on `thetaAbort.abort()` make a double-abort (e.g. operator presses Esc twice) a no-op. A *late failure* of the discarded kill initiation is one of the abandonable Promises governed by Cancellation's swallowing-handler rule and is silently absorbed (see [Cancellation](../cancellation.md)). *No grace step, deliberately:* the retired PIC-63 prescribed closing the child's stdin as a grace signal before the kill; empirically (bug 0002) that close never stopped anything — a startup-blocked child treats EOF as its *start* signal and would begin the whole run (real model turns included) only to be killed mid-flight, and a running child is not reading stdin — so the grace step is deleted, not preserved as a fiction, and no orderly-shutdown opportunity Pi does not itself provide is owed to the child.

<a id="concurrent-invocation-isolation"></a>**Concurrent-invocation isolation and concurrency disposition.** Concurrent theta invocations within an extension instance — tracked as entries in the **`ActiveInvocationRegistry`** above — carry mode-qualified isolation and a fixed theta 1.0 concurrency disposition. *Transcript and tool-table isolation are subagent-mode-only:* a subagent-mode invocation runs its own child process, so transcripts, captured `tools:` tables, and derived `AbortSignal`s are per-invocation and do not leak across siblings, while a prompt-mode invocation drives the user session's transcript by definition. <a id="no-invocation-cap"></a> theta 1.0 imposes no maximum on the number of in-flight theta invocations within an extension instance and no fairness or scheduling rule above Pi's event-loop ordering, interposing no admission cap, priority queue, or scheduler between sibling invocations and the event loop.

<a id="pic-22"></a> **PIC-22. Parallel subagent spawn initiation.** This disposition is observable at the parallel-tool-call surface (see [Tool Calls — Concurrency](../tool-calls.md#concurrency)): when the model emits N (for any fixed N ≥ 2) subagent-mode `.theta` callables as parallel tool calls in a single assistant turn, the runtime MUST, before any one of the N invocations returns, **initiate the child-process spawn** for all N invocations (reach the per-child spawn-initiated point). A conformance test witnesses the obligation with a **fake process launcher** whose spawned children block their exit-envelope emission until explicitly released: a conformant runtime has spawn-initiated all N children before any blocked child is released, whereas a runtime that admitted invocations behind a cap, queue, or scheduler would leave at least one child unspawned. The obligation carries over from the RFC 0005 driver unchanged except that "enter each child's first `prompt` command" is replaced by "spawn initiated". The test MUST tolerate real spawn times. The rule constrains the runtime only — Pi's own session-level serialisation is upstream and remains in force, and the rule does not promise resource unboundedness. Beyond the absence of an admission cap and scheduler, the theta adds no per-class threshold and no cross-sibling aggregation, throttling, or storm-detection over the resources concurrent theta invocations consume. Those resources — runtime-value heap, OS-level file descriptors / sockets / **child-process slots**, and provider-side rate-limit / quota — are owned by the host JavaScript runtime, the host OS, and the LLM provider respectively; a process tree's resource cost (each child a full Node runtime with extension discovery loaded) is an OS-owned quantity, not a governed one, and per-process memory footprint is a documented operator consideration, not a governed quantity. A process-count cap or throttle is **rejected** — it would contradict both the no-additional-ceilings invariant and the parallel-initiation conformance obligation, and the right value is machine-dependent, which is precisely why the spec assigns it to the OS layer. Simultaneous cold-boot resource contention among N freshly-spawned children falls under this same "resources are owned by the OS layer" disposition. The theta observes only the per-call surfacing of those limits through the existing routing it already pins: catchable host throws — the V8 `RangeError` family per `NOCEIL-3` at [Hard ceilings](../hard-ceilings/ceiling-invariants-and-audit.md#no-additional-ceilings), plus catchable OS-level descriptor / port / child-process-slot exhaustion surfaced as throws (a spawn that fails on child-process-slot exhaustion — `EAGAIN` / `EMFILE` — routes through the spawn-failure path of [PIC-65](#pic-65)) — route through `theta/runtime/internal-error` per [Errors and Results — Runtime panics](../errors-and-results/error-model.md#runtime-panics); per-query provider throttles (HTTP 429 and equivalents) surface as [`TransportError`](../errors-and-results/queryerror-variants.md#queryerror-variants) on the same page; uncatchable host fatals terminate the host process before any wrap can observe them and emit no `theta/runtime/internal-error` diagnostic. Widening or narrowing this rule is a major-version concern.

The prompt-mode counterpart to this subagent-mode concurrency — that prompt-mode bodies execute strictly sequentially within a single user session — is owned by [PIC-2 *Prompt-mode sequential execution*](./conversation-drive.md#pic-2) on the prompt-mode driver page.

<a id="subagent-performance-disposition"></a>
**Performance disposition.** Per-invocation process start (Node boot + extension discovery) replaces a cheap in-process construction, multiplied under `par for` fan-out and nested subagents. Bounding context: every subagent invocation also makes at least one LLM call, so the overhead is a fraction of typical wall time — but pure overhead. Disposition: ship as-is; benchmark spawn-to-first-envelope at the Pi pin and record the figure in the contract as an **expected-overhead note, not a guarantee**. **Process pooling is rejected**, and the rejection is recorded deliberately: a reused child carries state across invocations (extension module state, temp files, per-theta `--system-prompt`), trading the per-invocation isolation invariant — the property this design exists to guarantee — for latency. Startup-cost mitigation (e.g. trimming child startup work) is out of scope; if measurement ever shows the overhead to be a binding constraint, a mitigation is designed then, on its own record.
