# Theta run entries

The run-card entry channel ([RFC 0015](../../rfcs/0015-theta-run-card.md)): two further custom-*entry* types beside [Runtime event channel — PIC-71](./runtime-event-channel.md#pic-71)'s `theta-progress-entry`, carrying the per-drive run card and its gated terminal heat summary. Both ride the same `pi.appendEntry` / `pi.registerEntryRenderer` surface, the same optional-capability class ([Capability probe — PIC-73](./capability-probe.md#pic-73)), and the same durable, LLM-context-free posture ([Execution Status — EXST-1](../execution-status.md#exst-1)): nothing appended here is ever replayed to a provider. This page owns the two entry payload shapes, the summary gate, the outcome projection convention, the renderer degradation semantics, and the decision-4/5 supersession rows.

<a id="pic-75"></a> **PIC-75. `theta-run` entry.** The extension appends exactly one `theta-run` custom entry per **top-level** theta drive (nested `invoke` callees append nothing — one card per top-level drive, RFC 0015 decision 6; the child-process subagent regime appends nothing either, its transcript being private and ephemeral), at drive start, in **TUI compositions only** (`ctx.mode === "tui"` — the RFC's "Modes and degradation"; print/json compositions construct no publisher and their RFC 0007 surfaces are byte-unchanged). The entry `data` is the STATIC seed, exactly five fields:

```ts
type ThetaRunSeed = {
  invocationId: string;   // the ActiveInvocationRegistry entry's invocationId
  theta: string;          // bare slash name
  argsSummary: string;    // one-line display string, whitespace-collapsed, clamped (RUN_CARD_ARGS_CLAMP_CHARS = 200)
  startedAtMs: number;    // wall-clock epoch ms (Clock.wallNow) — must render after a restart
  sourcePath?: string;    // the theta's source file; omitted when the drive has none
};
```

Registration and degrade discipline are PIC-71's, extended: the `theta-run` and `theta-run-summary` ([PIC-76](#pic-76)) entry renderers register **in the same guarded factory-time block** as the `theta-progress-entry` renderer, sharing one dead flag — a throwing registration of ANY of the three marks the whole entry channel absent for the session, so an appended entry is never renderer-less. A failed or degraded append of a run entry is a **silent skip** — the milestone discipline, never a `pi.sendMessage` fallback (a card is a rendering surface, not a note; the [PIC-72](./runtime-event-channel.md#pic-72) message-channel fallback covers the three operator note classes only). This widens PIC-71's original one-`customType` ownership to exactly **three** entry types, all `theta-<purpose>`-named; the `theta-system-note` five-shape `details` partition is untouched.

*Renderer semantics (live → static degradation).* While the execution-status bus still tracks `invocationId`, the registered `theta-run` renderer draws the LIVE card — lexer-highlighted sticky viewport, heat fade, running-subagent markers, children roster, author-message row — off bus state, invalidating on the [EXST-6](../execution-status.md#exst-6) coalesced tick. When the bus no longer knows the invocation (drive ended and the node evicted, session restarted, `MAX_TRACKED_INVOCATIONS` overflow) the renderer degrades to the **static compact form** rendered purely from the seed: `theta /<name>[ <argsSummary>] · started <HH:MM:SS>` (local wall clock). The degradation is a renderer behaviour, not a payload change — the entry's stored `data` is the seed either way.

*Ended-children limitation (recorded).* The live card's children roster renders every ended child `✓ done` uniformly: the bus's `invocationEnded(id)` ingest (and the `agent_end` tap arm) are liveness-only and carry **no outcome**, so `✗` is not derivable from any snapshot. The feasible extension is an optional outcome on the end publication — `invocationEnded(id, outcome?)` — sourced at the producer's callee-result site; until an RFC adopts it, `✓`-only is the specified rendering, not a defect.

<a id="pic-76"></a> **PIC-76. `theta-run-summary` entry.** When a top-level drive that appended a `theta-run` entry ends after **`RUN_SUMMARY_GATE_MS = 30 000` ms** of elapsed wall time (RFC 0015 decision 7 — the "≥ ~30 s" magnitude is ratified, the exact value is tuning), the extension appends exactly one `theta-run-summary` entry; a shorter drive appends **nothing** (short utility drives leave no summary row). The entry `data`:

```ts
type ThetaRunSummary = {
  invocationId: string;
  theta: string;
  outcome: "ok" | "err" | "cancelled";      // closed vocabulary — see the projection convention below
  elapsedMs: number;
  counters: { checkpoints: number; loopIters: number };
  childrenSpawned: number;                   // CUMULATIVE invocationBound count under the node (incl. subagent-fn) — child NODES evict after linger and would undercount
  heatProfile?: ThetaRunHeatProfileLine[];   // dwell-descending, capped at RUN_SUMMARY_PROFILE_MAX_LINES = 10; OMITTED (never invented) when the bus no longer holds the node's heat ring at drive end
};
type ThetaRunHeatProfileLine = { file: string; line: number; hits: number; dwellMs: number; kind: HeatLineKind };
```

<a id="run-outcome-projection"></a> *Outcome projection convention (normative, part of [PIC-76](#pic-76)).* `outcome` is a closed three-value vocabulary and every drive ending MUST project onto it: `"ok"` for an `Ok` terminal, `"err"` for an unhandled top-level `Err` and for a runtime-defect abort (the framed-note path), and `"cancelled"` for a terminal `Err(CancelledError)` **and for every binder short-circuit** — including `needs_info` and `ambiguous` endings, where the body never ran. The `needs-info`/`ambiguous` → `"cancelled"` projection is deliberate lossy compression, not a bug: the card's outcome answers "did the body run to a result", and the binder's own failure note ([Runtime event channel](./runtime-event-channel.md), group-A binder rows) already carries the precise reason on the message channel — the summary row does not duplicate it.

<a id="pic-77"></a> **PIC-77. Supersession (RFC 0015 decisions 4 and 5).** The run card supersedes the RFC 0010 transient TUI surfaces:

- *Retired — footer and widget sinks (decision 4).* The composition constructs **no** `ctx.ui.setStatus` / `ctx.ui.setWorkingMessage` footer sink and **no** string-array `ctx.ui.setWidget` status-tree widget sink, in any mode: nothing is pinned below the editor while a theta runs. The **scroll-away gap is ACCEPTED** by the ratified decision — new turns push the card off-view and nothing then signals a running theta; at the tail the live turns are themselves the signal, and the operator scrolls up for the card. The `/theta-status` command stays registered with its EXST-11 semantics (it adjusts bus view-shape state; the retired sinks were that axis's only renderers, so the shape currently changes no rendering), the `theta.progress` verbosity ceiling ([EXST-10](../execution-status.md#exst-10)) still gates whether the bus ticks at all, and the non-TUI surfaces (RFC 0007 print/json observability, the PIC-59/PIC-74 wire) are byte-unchanged. `ctx.ui.setWidget` itself remains a consumed surface: the card's TUI-handle capture uses its factory overload (a zero-line component registered and removed in one call, under the extension's own capture key) — retiring the widget *sink* did not retire the *member*. `ctx.ui.setStatus` and `ctx.ui.setWorkingMessage` left the consumed surface set entirely ([Capability probe — PIC-73](./capability-probe.md#pic-73)'s class is now three members).
- *Hidden — the `Running /<name>` binder echo (decision 5).* The `theta-system-note` **message renderer** returns a **zero-output component** (a `Component` whose `render` yields zero lines) for the binder success echo, so the note draws no content in TUI. Returning `undefined` would NOT hide it: the pinned host's `CustomMessageComponent` (pi `dist/modes/interactive/components/custom-message.js`) treats a falsy renderer return as "no custom rendering" and falls through to its default purple box with a `[theta-system-note]` label and the raw content. Accepted residual: the host constructor adds an unconditional `Spacer(1)` sibling that its `rebuild()` never removes, so a hidden note still occupies exactly **one blank line** in the transcript — no content, no label. ONLY this note class is hidden — err notes, cancelled notes, panic framings, binder failure notes, diagnostics batches and every other class render unchanged. The note's **emission is untouched**: it is still sent on the channel with byte-identical `content`, `display: true`, and the details-ABSENT wire shape, so its LLM-context entry, its print/json observability, and the live suite's note-channel content assertions are all unchanged. The renderer's discriminator is content-shape + class: `content` starting with the verbatim `Running /` template prefix (owned solely by the argument-echo renderer) **and** `details` absent (the informational-note class per [Runtime event channel — Informational notes](./runtime-event-channel.md)); a `details`-carrying note is never hidden regardless of its text. A future informational note MUST NOT adopt the `Running /` content prefix without revisiting this rule.

Cross-references: the [Execution Status — EXST-8](../execution-status.md#exst-8) sink set defers to this rule for its post-RFC-0015 shape; [EXST-1](../execution-status.md#exst-1)'s permitted-surface enumeration includes these two entry types.
