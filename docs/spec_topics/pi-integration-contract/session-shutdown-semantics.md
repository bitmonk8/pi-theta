# Session shutdown semantics

   <a id="session-shutdown-semantics"></a>

   *Session-swap behaviour for in-flight invocations.* The five-sub-step sequence below defines the abort-and-await sequence; this paragraph closes the three obligations the sequence does not by itself state — per-invocation operator visibility on the cancellation path, partial-append fate during teardown, and the `invoke`-parent observation rule.

   The handler runs in fixed order regardless of `event.reason`:

   1. **Stop accepting new work.** <a id="substep-1-drain-flag"></a>Mark the extension-scoped `ThetaRegistry` as drained <a id="substep-1-init-drain-state-tag"></a>and initialise its drain-state tag to `"shutting-down"`. <a id="substep-1-act-order"></a>The two acts run in fixed normative order — `ThetaRegistry.drain()` first, then `ThetaRegistry.initDrainStateTag()` — so downstream sites that key on which act threw and which succeeded (the **Per-step isolation** paragraph below, which routes the two throws to distinct `(code, details.step, details.call)` dedup buckets; the [**idempotent**](./drain-state-contract.md#idempotent-handler-clause) clause's enumeration of the prior-state combinations a follow-up `session_shutdown` may observe; the `ThetaRegistry.initDrainStateTag` method-contract clause below that pins it as called *immediately after* `ThetaRegistry.drain`; and any acceptance criterion that distinguishes between the first and second sub-step-1 act) can refer to "the second sub-step-1 act" unambiguously; the per-call **Per-step isolation** rule continues to apply independently to each of the two calls regardless of the order pin. <a id="substep-1-shutting-down-arm"></a>On entry into a drained registry the slash-command `handler` registered in step 3 returns a `theta-system-note` (`display: true`) — without dispatching the theta — carrying the cancelled-binder-style content `"theta /<name>: extension shutting down"` shared with binder cancellation; this is the sole non-dispatch drain-state note in theta 1.0 (the session-only degraded-state branch and its `"degraded; /reload to recover"` note are retired under the `governed-by-rebind` resolution — see the [Session-swap fail-fast tripwire](./session-only-degraded-state.md#session-swap-fail-fast-tripwire)). <a id="substep-1-unset-tag-fallback"></a>The slash-handler reader MUST also treat an *unset* drain-state tag (a runtime *state* of the field, distinct from the single `"shutting-down"` *value* the tag may hold in theta 1.0.0 — the runtime state of the field may additionally be unset, reachable when sub-step 1's `ThetaRegistry.initDrainStateTag` per-call site threw and was caught by the **Per-step isolation** paragraph below, leaving the registry drained but tag-less) as the `"shutting-down"` arm and emit the same template, so a tag-init throw degrades safely to the cancelled-binder-style content rather than producing undefined slash-handler short-circuit behaviour. The tag *value* set is closed at the single literal `"shutting-down"` in theta 1.0.0 (no other literal value may be written to the field without a spec edit); the unset runtime state called out above is an implementation-side artefact of the **Per-step isolation** swallow rule, not a second literal value, and the slash-handler reader's unset → `"shutting-down"` mapping above ensures the closed value set is preserved in the observable behaviour of the slash note.
   2. **Cancel in-flight invocations.** For every entry in the **`ActiveInvocationRegistry`** (introduced below), first stamp the handler-scoped captured `event.reason` string (per the **Unknown-reason rule** above — the closed-set member, the `String(event.reason)` unknown-reason coercion, the throwing-access `"<unreadable>"`, or the snapshot-failure `"<unreadable>"`) onto the entry's `shutdownReason` field, then call `thetaAbort.abort(reason)` where `reason` is the synthesised teardown value pinned by [Cancellation — Abort-reason propagation](../cancellation.md). The stamp MUST happen before `thetaAbort.abort()` on the same entry so the per-invocation `finally` (which is what reads `entry.shutdownReason` per the **Per-invocation operator visibility (clean-cancel path)** rule below) observes a populated field by the time the abort propagates and the `finally` runs; the per-entry `try`/`catch` (per the registry contract below) wraps both the stamp and the `abort()` call — on a stamp throw (frozen entry, proxied entry, write-rejecting setter, OOM during property assignment) the per-entry `catch` arm proceeds to the next entry (the `abort()` for this entry is skipped, since the stamp failed) so a per-entry write failure cannot escape sub-step 2's loop and defeat the no-throw-escapes-the-handler invariant; on an `abort()` throw, behaviour is unchanged from the registry-contract rule below. No diagnostic is emitted on a stamp-throw catch, symmetric to the existing `abort()`-throw rule. The `abort()` call propagates through the [`Checkpoint` seam](./host-interfaces-services.md#checkpoint-seam) and, in subagent mode, through the one-shot `thetaAbort.signal` listener that the runtime registered at spawn time and that initiates the child's cancellation kill — a process-tree kill on Windows, a direct `SIGKILL` elsewhere (the RFC 0006 `-p` child exposes no RPC abort command and its stdin is spawned closed, so no in-band stop channel exists) — per [Cancellation — Forwarding into `thetaAbort`](../cancellation.md) and [Subagent — Cancellation (PIC-66)](./subagent.md#pic-66). The listener is detached in the same per-invocation `finally` that tears the child down (bounded await → kill fallback; see **Subagent child-process lifecycle** ([PIC-65](./subagent.md#pic-65)) below).
   3. **Await subagent child exit.** `await Promise.allSettled(activeInvocations.map(inv => inv.disposeBarrier))`, where `disposeBarrier` is the promise that the **Subagent child-process lifecycle** ([PIC-65](./subagent.md#pic-65)) `finally` block below settles on **observed child exit** (subagent mode — typically already recorded, the child having self-exited after its envelope or been killed by the sub-step-2 abort forward; else after the bounded `SHUTDOWN_AWAIT_CAP_MS` await and kill) or settles immediately (prompt mode). A `/reload` issued mid-turn therefore kills the still-talking subagent children as part of this bounded await, releasing their provider connections before Pi calls `ExtensionRuntime.invalidate(...)`. The await is bounded by the constant `SHUTDOWN_AWAIT_CAP_MS = 2000` measured against the runtime's injected [`Clock`](./host-interfaces-services.md#clock--fakeclock-interface) seam: at handler entry the runtime captures `deadline = Clock.now() + SHUTDOWN_AWAIT_CAP_MS`, and the await resolves on the earlier of `Promise.allSettled(...)` settling or `Clock.setTimeout(SHUTDOWN_AWAIT_CAP_MS, ...)` firing. The deadline is absolute, not a refreshing slide — a slow `thetaAbort.abort()` propagation in sub-step 2 does not extend the await. The pending `Clock.setTimeout` handle is cleared on the success path so a reload that completes early does not leak a timer onto the about-to-be-invalidated runtime. On timeout the runtime emits one `theta/runtime/reload-teardown-timeout` diagnostic naming the still-in-flight invocations and proceeds to step 4. The `SHUTDOWN_AWAIT_CAP_MS` constant lives in the same source-of-truth pinned-constants block as the Step 0 capability-probe constants so the build-time literal-read assertions can assert it.
   4. **Close watchers.** Call `discoveryWatcher.close()` (the chokidar watcher established in step 5 above) and `settingsWatcher.close()` (the settings-file watcher per [Discovery — Settings file reads](../discovery/package-and-settings.md#settings-file-reads)); cancel any pending debounce timer handles via `Clock.clearTimeout`. Then quiesce the hot-reload debouncer so no watcher-driven registry rebuild survives into the about-to-be-invalidated runtime (the governing invariant is [PIC-57](#pic-57) below): (a) mark the debouncer **torn-down** so that no *new* rebuild starts and any rebuild deferred under the [PIC-49](./registration-steps.md#pic-49) cross-window serialization rule is cleared rather than re-armed; and (b) `await debouncer.whenIdle(...)` to let an already-in-flight watcher rebuild quiesce — either running its single synchronous publish per [PIC-36](./registration-steps.md#pic-36) or becoming a no-op under the torn-down flag — before the handler returns and Pi invalidates the runtime. This quiesce await is bounded by the **same absolute `deadline = Clock.now() + SHUTDOWN_AWAIT_CAP_MS` captured at handler entry** for sub-step 3 above — **not** a fresh `SHUTDOWN_AWAIT_CAP_MS` budget — so total teardown await stays bounded by the single shared 2000 ms deadline; the await resolves on the earlier of `debouncer.whenIdle(...)` settling or that shared deadline. If the shared deadline has already elapsed by the time sub-step 4 is reached (e.g. sub-step 3's bounded await consumed it), sub-step 4 MUST skip the quiesce await and proceed (**degrade-to-skip**), symmetric to how sub-step 3 degrades to a skipped await when its `Clock` seam throws. A rebuild still in flight at the shared deadline does **not** emit a diagnostic: the torn-down flag makes an un-awaited rebuild safe (a no-op on resume) per [PIC-57](#pic-57), so no `theta/runtime/reload-teardown-timeout` (whose `<list>` renders `ActiveInvocationRegistry` invocations, not rebuilds) is emitted and no new teardown-handler code is registered — only a *throw* from the quiesce-await call site emits `theta/host/session-shutdown-teardown-step-failed` per the **Per-step isolation** paragraph below.
   5. **Detach forwarding listeners.** Remove every listener the runtime attached to Pi-side `ctx.signal`, tool `execute(signal)`, and parent-`invoke` signals — the same listeners [Cancellation](../cancellation.md) requires the per-invocation `finally` to remove, duplicated here for the reload-during-invocation path where Pi tears the runtime down before that `finally` ever reaches its forwarding-listener cleanup.

   **Per-step isolation.** Sub-steps 1, 3, 4, and 5 each run inside their own `try`/`catch`; a throw from any of them MUST be caught, MUST emit exactly one `theta/host/session-shutdown-teardown-step-failed` (severity `warning`, phase `runtime` — the `(W, runtime)` shorthand used for the teardown-handler diagnostics throughout these PIC pages is defined by the column legend in [Diagnostic shape — column legend](../diagnostics/diagnostic-shape.md#column-legend)) diagnostic via `console.error` with `details: { step: 1 | 3 | 4 | 5, call: <static call-site label>, error: <error.message> }`, and MUST NOT prevent the remaining sub-steps from running. Within sub-step 1 the rule applies independently to each of `ThetaRegistry.drain` (the drain-flag set) and `ThetaRegistry.initDrainStateTag` (the `"shutting-down"` tag-init write — the two acts sub-step 1 now performs per the prose above, two potential emissions, one per failing call); a drain-flag throw and a tag-init throw therefore occupy distinct `(code, details.step, details.call)` dedup buckets in operator logs and a future addition of a third sub-step-1 act MUST be added here on the same footing rather than collapsed into one of the existing labels. Within sub-step 3 the rule applies independently to each of the three bounded-await `Clock` calls — the deadline capture `Clock.now()`, the cap-arming `Clock.setTimeout(SHUTDOWN_AWAIT_CAP_MS, ...)`, and the success-path `Clock.clearTimeout(...)` (three potential emissions, one per failing call); a throw from any of the three MUST be caught, MUST emit exactly one `theta/host/session-shutdown-teardown-step-failed` with `details.step: 3`, and MUST NOT prevent sub-steps 4 and 5 from running. When the cap cannot be armed — the deadline capture `Clock.now()` or the cap-arming `Clock.setTimeout(...)` throws — the handler MUST NOT enter the bounded await unbounded: it skips the `Promise.allSettled(...)` await for this teardown and proceeds directly to sub-step 4, so a `Clock`-seam throw degrades to a skipped await rather than an unbounded one (a success-path `Clock.clearTimeout(...)` throw fires after the await has already resolved, so no degradation is needed beyond emitting and continuing). Within sub-step 4 the rule applies independently to each of `discoveryWatcher.close()`, `settingsWatcher.close()`, the debounce-handle `Clock.clearTimeout(...)` call, and the debouncer quiesce-await `debouncer.whenIdle(...)` call (four potential emissions, one per failing call); a throw from the quiesce-await MUST be caught, MUST emit exactly one `theta/host/session-shutdown-teardown-step-failed` with `details.step: 4` and `details.call: "debouncer.whenIdle(awaitCap)"`, and MUST NOT prevent sub-step 5 from running. Within sub-step 5 the rule applies independently to each enumerated listener-detach call. Sub-step 2 retains its existing per-entry isolation rule (per-entry `try`/`catch` around `thetaAbort.abort()`) and does not emit `teardown-step-failed`; sub-step 3's `Promise.allSettled` over `disposeBarrier`s likewise retains its per-entry settle semantics without emitting `teardown-step-failed` — only sub-step 3's three bounded-await `Clock` calls above emit it. The static call-site label in `details.call` is a fixed string per call site, drawn from a **closed normative set per `(code, details.step)`** so operator dedup on `(code, details.step, details.call)` is meaningful both across runs and across independent implementations of this contract — the labels are wire contract, not implementation-chosen stable-per-impl strings. The closed set is: sub-step 1: `"thetaRegistry.drain"`, `"thetaRegistry.initDrainStateTag"`; sub-step 3: `"Clock.now()"`, `"Clock.setTimeout(awaitCap)"`, `"Clock.clearTimeout(awaitCap)"`; sub-step 4: `"discoveryWatcher.close"`, `"settingsWatcher.close"`, `"Clock.clearTimeout(debounce)"`, `"debouncer.whenIdle(awaitCap)"`; sub-step 5: `"ctx.signal.removeEventListener"`, `"toolSignal.removeEventListener"`, `"parentInvokeSignal.removeEventListener"` (one label per inbound Pi-side signal source sub-step 5 enumerates by name — Pi-side `ctx.signal`, the tool-exposed adapter's `signal` parameter, and the `invoke`-parent signal respectively). Adding a new call site under any of these sub-steps requires a spec edit to extend this closed set in the same commit; an implementation MUST NOT introduce a `details.call` value outside this enumeration. When the captured throw is not an `Error` instance, `details.error` is `String(error)`, falling back to the literal string `"<unreadable>"` if that coercion itself throws — symmetric with the `details.observed` convention pinned by the **Unknown-reason rule** above. The `console.error` call this paragraph mandates is itself wrapped per the **Diagnostic-emission isolation** rule defined under *Edge cases* below; a throw from `console.error` MUST be swallowed and MUST NOT prevent the remaining sub-steps from running. The new code is **not** added to the always-log set defined under **Runtime event channel** below, matching the existing `reload-teardown-timeout` and `session-shutdown-reason-unknown` exclusions.

   *Reason-set pin (co-located with the consuming handler).* The closed set of reason values Pi delivers to the runtime's teardown handler on session-end matches the `SessionShutdownEvent['reason']` union declared at `dist/core/extensions/types.d.ts` in `@earendil-works/pi-coding-agent` (the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin)); the closed reason set itself is owned by sub-step 4's [Unknown-reason rule](./unknown-reason-rule.md#unknown-reason-rule) and is pinned at build time by the bidirectional `SessionShutdownEvent['reason']` type-equality assertion described at [Pi version bump procedure — step 5](./version-bump-intro.md#pi-version-bump-procedure). The single-active-session binding under which this reason set is delivered is [PIC-7 *Session-binding contract*](./host-prerequisites.md#pic-7).

   - **Per-invocation operator visibility (clean-cancel path).** For each `ActiveInvocationRegistry` entry whose `disposeBarrier` settles (whether inside the `SHUTDOWN_AWAIT_CAP_MS` window of sub-step 3 — i.e., the invocation cancelled cleanly within the bounded await — OR, on the [*Accepted theta 1.0 residual gap — sub-step-2 stamp-throw case*](./session-only-degraded-state.md#substep-2-stamp-throw-residual-gap) above, after the deadline via a downstream cancellation per the EXCEPT clause below) — the cancellation path inside that invocation's own `finally` block emits exactly one `theta/runtime/cancelled-by-session-shutdown` (E, runtime) note on `theta-system-note` with `display: false`, `details.event.reason` carrying the handler-captured `event.reason` string typed as `"quit" | "reload" | "new" | "resume" | "fork" | string`: a closed-set member when Pi delivered one of the five literals, otherwise the `String(event.reason)` coercion captured by the **Unknown-reason rule** above (or the literal string `"<unreadable>"` when the property-access read threw, or the same `"<unreadable>"` sentinel — overloaded per the **Unknown-reason rule**'s captured-value enumeration above — when the snapshot-side read failed before sub-step 1's `event.reason` read was reached and the handler-scoped variable retained its `"<unreadable>"` pre-initialisation; on this snapshot-failure path the same-string reuse with `details.observed` does not apply because the co-emitted teardown diagnostic is `theta/host/session-shutdown-pinned-constant-unreadable` carrying `details.failure` rather than `theta/host/session-shutdown-reason-unknown` carrying `details.observed`). The per-invocation `finally` reads this string from the entry's `shutdownReason` field (stamped by sub-step 2 of the `session_shutdown` handler above immediately before that entry's `thetaAbort.abort()` call, per all four captured-value cases enumerated by the **Unknown-reason rule**) rather than re-reading `event.reason` — the `event.reason` read is handler-scoped and the `finally` runs in a different async context, so `entry.shutdownReason` is the spec-pinned channel by which all four captured-value cases reach this emission site. On the post-deadline arm of the widened opening precondition above (the [*Accepted theta 1.0 residual gap — sub-step-2 stamp-throw case*](./session-only-degraded-state.md#substep-2-stamp-throw-residual-gap)), the per-invocation `finally` STILL reads `entry.shutdownReason` by the same channel and emits the row; on that arm the field carries the literal `"<unreadable>"` sentinel per the residual-gap paragraph (sub-step 2's stamp threw before populating it, and the residual-gap paragraph pins payload-construction substitution of the sentinel for the otherwise-unset field), so the type pinned for `details.event.reason` (`"quit" | "reload" | "new" | "resume" | "fork" | string`) is preserved on the post-deadline arm on the same footing as the four `Unknown-reason rule` captured-value cases above. The wider `string` arm is the unknown-reason path; the value is always a string. The handler-captured string is the same single coerced value the **Unknown-reason rule** populates `details.observed` with — both diagnostics surface byte-identical reason strings for the same shutdown event, and `details.event.theta` carrying the invocation's canonical-key name (post-`pi.theta` mapping, post-`as` rename, no leading `/`) per the [`ActiveInvocationRegistry`](./active-invocation-registry.md#active-invocation-registry) `theta`-field source-of-truth above. The same `finally` also populates `details.event.invocation_id` by reading the registry entry's `invocationId` field (the same channel by which `details.event.theta` is read, per the [`ActiveInvocationRegistry`](./active-invocation-registry.md#active-invocation-registry) registry-insertion-site source-of-truth above), rendered as the per-invocation UUID in canonical lowercase 8-4-4-4-12 hex form per the [§7 `<invocation-id>` placeholder convention](../diagnostics/placeholder-rendering-b.md#7-identifier--descriptor--and-closed-enum-placeholders); the field is not re-derived at the emission site, so concurrent siblings of the same theta carry distinct `details.event.invocation_id` values on the operator-visible row. The note is emitted from the invocation's own teardown — not from the `session_shutdown` handler itself — so the "`sendSystemNote` MUST NOT be invoked from the teardown handler" edge-case bullet above does not apply to it; the note routes through the standard `sendSystemNote` fallback chain (`pi.sendMessage` → `ctx.ui.notify` → `theta/runtime/system-note-delivery-failed` → `console.error`) defined under **System notes** below. The chain degrades only on a live runtime: if `ExtensionRuntime.invalidate(...)` has already invalidated `pi.sendMessage` by emission time, the send throw is the stale-ctx error and the channel marks itself permanently dead and rethrows instead of degrading (per [PIC-67](#pic-67) clause (c) — the `ctx.ui.notify` and diagnostic fallback arms ride the same invalidated runtime, so no arm can deliver); the note is undelivered and the throw unwinds out of the emitting per-invocation code to the host, whose command dispatch surfaces it as a command-level error at the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin). The chain's terminal `console.error` is wrapped per the [**Diagnostic-emission isolation**](./diagnostic-emission-isolation.md#diagnostic-emission-isolation) rule above: a throw from that terminal `console.error` MUST be swallowed and MUST NOT propagate out of the per-invocation `finally`. An invocation either emits `cancelled-by-session-shutdown` (cleanly cancelled within the window) or contributes to the single `theta/runtime/reload-teardown-timeout` `<list>` of sub-step 3 (still in flight at the deadline), never both — the per-invocation note is the operator-visibility counterpart to the timeout diagnostic — EXCEPT on the [*Accepted theta 1.0 residual gap — sub-step-2 stamp-throw case*](./session-only-degraded-state.md#substep-2-stamp-throw-residual-gap) above, where an affected invocation MAY both contribute to the `reload-teardown-timeout` `<list>` (because sub-step 2's `abort()` was skipped) AND later emit `cancelled-by-session-shutdown` from this rule (if its per-invocation `finally` settles via a downstream cancellation after the deadline); the [`theta/runtime/cancelled-by-session-shutdown` row's mutual-exclusion clause](../diagnostics/code-registry-runtime.md#cancelled-by-session-shutdown-mutual-exclusion) restates this carve-out and pins the operator-tooling consumer guidance for the dual appearance. The `cancelled-by-session-shutdown` code is **not** in the always-log set defined under **Runtime event channel** below; the exclusion mirrors the existing `cancelled` exclusion (operator-initiated, self-explanatory in context) and so the per-invocation note does not produce a `details: { event: RuntimeEvent }` group-A emission in addition to itself.

   - **Partial-append fate during teardown.** Conversation turns the runtime had already appended into the user session (prompt mode) or the spawned subagent child conversation (subagent mode) before sub-step 2's `thetaAbort.abort()` fired remain in whatever conversation the respective session assigns them to under the swap's `event.reason`; the runtime makes no rollback, migration, or compensation attempt. This is the `event.reason`-scoped restatement of the [Errors and Results — Partial-append contract](../errors-and-results/error-model.md#partial-append-contract): `?`-propagation, panic, and steady-state cancellation already preserve appended turns, and a `session_shutdown`-driven cancellation preserves them on the same rule. The outgoing user session (when Pi tears it down on `reason: "new" | "resume" | "fork"`) carries the partial appends Pi assigns to it under the swap; the theta runtime makes no attempt to discard them, migrate them to the incoming session, or surface a manifest of what was appended. Authors who need teardown-safe append semantics must use [Errors and Results — No rollback](../errors-and-results/error-model.md#no-rollback)'s steady-state author obligations (idempotency, compensation in `match` arms before re-`Err`-ing).

   - **`invoke`-parent observation rule.** Parent and child invocations are aborted in the same iteration of sub-step 2: the registry is iterated once and `thetaAbort.abort()` is called on every entry, parents and children alike. The parent's `?` / `match` arms covering the child's `Err(QueryError { kind: "cancelled" })` (or `kind: "invoke_callee"` wrapping it, per [Cancellation — Surfacing](../cancellation.md)) do **not** run inside the bounded-await window of sub-step 3: the parent's own `thetaAbort` has already fired in the same iteration, its next [`Checkpoint` seam](./host-interfaces-services.md#checkpoint-seam) await observes the abort, and the parent unwinds without re-entering interpreter dispatch. The parent's `disposeBarrier` settles independently of whether its child surfaced an `Err` to it — the registry treats every entry symmetrically. The downward-only propagation rule of [Cancellation — Propagation](../cancellation.md) is not contradicted: parent and child are not propagating into each other, they are both aborted by the same external `session_shutdown` trigger, and the parent's `Err`-handling arms remain inert during teardown for the same checkpoint reason that any cancelled invocation's post-abort code is inert.

   <a id="factory-ordering-pin"></a>**Factory-ordering pin.** The `session_shutdown` handler MUST be subscribed (step 4 above) only after the `ThetaRegistry` and watcher handles the handler reads are constructed (the [watcher / hot-reload registration step](./registration-steps.md#watcher-hot-reload-registration) — step 5 of the **Extension entry point** sequence, above). The implementation MAY reorder steps 4 and 5 internally provided that subscription happens after registry/watcher construction; a `session_shutdown` MUST NOT be reachable against a partially-constructed extension state, so the closure-captured `ThetaRegistry` handle the handler reads at handler entry (per step (I) of the *Handler control-flow ordering* clause in the [**idempotent**](./drain-state-contract.md#idempotent-handler-clause) clause above) is never `undefined` and `ThetaRegistry.readDrainState()` cannot throw a `TypeError` against a missing dispatch in the gap between step 4 returning and registry/watcher construction completing.

   The watcher / hot-reload lifecycle this ordering pin protects — the chokidar file watcher, the 250 ms debounce, the build-aside-then-publish registry swap, the in-flight-invocation rule, and the structural-change note — is specified at the [watcher / hot-reload registration step](./registration-steps.md#watcher-hot-reload-registration) (step 5 of the **Extension entry point** sequence, above), not under this heading.

   <a id="pic-57"></a> **PIC-57. No watcher-driven rebuild against an invalidated runtime.** No watcher-driven registry rebuild may run against an invalidated extension runtime. Once teardown has quiesced the watcher — sub-step 4 above has closed `discoveryWatcher`/`settingsWatcher`, cancelled the pending debounce timer, and marked the hot-reload debouncer torn-down — the runtime MUST NOT start or continue a *new* watcher-driven rebuild: the torn-down flag suppresses any fresh rebuild and clears any rebuild deferred under the [PIC-49](./registration-steps.md#pic-49) cross-window serialization rule, so a debounce timer that would otherwise fire (or a deferred re-arm that would otherwise run) after teardown does nothing. Any *already-in-flight* rebuild — one that entered its asynchronous re-parse / AJV-recompile / `pi.registerTool` steps before teardown — MUST be awaited during the `session_shutdown` handler while the ctx is still active, before the handler returns and Pi calls `ExtensionRuntime.invalidate(...)` (per the [watcher / hot-reload registration step](./registration-steps.md#watcher-hot-reload-registration) and the [`ExtensionRuntime` invalidate teardown pin](./registration-steps.md#extension-runtime-invalidate-teardown)), so that it either completes its single synchronous publish per [PIC-36](./registration-steps.md#pic-36) or is a no-op before Pi invalidates the runtime. The mechanism is sub-step 4's (a) torn-down mark and (b) bounded `debouncer.whenIdle(...)` quiesce await above, which shares sub-step 3's single absolute `deadline = Clock.now() + SHUTDOWN_AWAIT_CAP_MS` — not a fresh budget — so PIC-57's guarantee never extends total teardown beyond the single shared 2000 ms cap. This closes the ordering gap whereby a debounced rebuild resuming after runtime invalidation would drive re-registration or diagnostic emission through a stale `pi.*` surface and throw against Pi's `assertActive()`. PIC-57 layers on top of [PIC-36](./registration-steps.md#pic-36) (swap atomicity), [PIC-49](./registration-steps.md#pic-49) (at most one rebuild at a time / deferral), and [PIC-54](./runtime-event-channel.md#pic-54) (system-note fallback chain): it neither relaxes the single-synchronous-publish guarantee nor permits a concurrent rebuild, and where a torn-down rebuild's would-be system-note emission is suppressed the residual emission still degrades through the same fallback chain PIC-54 governs. The bounded quiesce reuses sub-step 3's `SHUTDOWN_AWAIT_CAP_MS` deadline only for its *bound*, not its diagnostic: a rebuild still in flight at the shared deadline is abandoned safely under the torn-down flag and emits **no** new diagnostic code (per sub-step 4's degrade-to-skip and no-diagnostic rules above), so the closed teardown-handler `console.error` code set is unchanged and `theta/runtime/reload-teardown-timeout` — whose `<list>` renders `ActiveInvocationRegistry` invocations, not rebuilds — is not reused for the rebuild-quiesce timeout. PIC-57's mechanism above presupposes that a `session_shutdown` reached the teardown handler before the invalidation; the shutdown-less case — reachable at the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin) — is governed by [PIC-67](#pic-67) below.

   <a id="pic-67"></a> **PIC-67. Shutdown-less runtime invalidation — stale-probe posture.** A bare `AgentSession.dispose()` — a public host SDK API (`dist/core/agent-session.js` at the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin)) — invalidates the extension runtime (`_extensionRunner.invalidate(...)`) **without** emitting `session_shutdown` first, unlike every host replacement path (`newSession` / `switchSession` / `fork` / `reload` / quit), so the step-4 teardown of [PIC-57](#pic-57) never runs and an armed watcher outlives the runtime with its debouncer never marked torn-down. The host exposes **no** non-throwing staleness probe for this state — the runner's `staleMessage` is private, there is no `isStale` / `isActive` / `isDisposed` member, and no event fires on the bare dispose — so the only way the runtime can learn of the invalidation is to touch a guarded `pi.*` / `ctx.*` surface and recognise the thrown stale-ctx error. Recognition keys on the stable message prefix `This extension ctx is stale after session replacement or reload` (byte-identical across every host `invalidate(...)` call site at the pin; only the prefix is normative — the guidance tail may vary). PIC-67 therefore pins the reactive posture: (a) each watcher-driven reload pass performs **exactly one** deliberate, side-effect-free guarded touch at pass entry (the *stale probe*; a `ctx.cwd` read is the reference choice) before any other surface is reached; (b) on **first evidence** of a shutdown-less invalidation — the entry probe throwing the recognised stale-ctx error, the same error escaping a pass already in flight when the invalidation lands mid-pass, or the [PIC-55](./registration-steps.md#pic-55) terminal-signal recovery's `watcher-terminated` note delivery throwing it — the runtime MUST emit exactly one designed stderr line (prefix `theta hot-reload quiesced:`) for the whole extension-instance lifetime, one latch shared across all three evidence sites; on the two reload-pass sites the watcher MUST additionally quiesce permanently (mark the debouncer torn-down per [PIC-57](#pic-57), detach the watcher), while on the terminal-signal site the watcher is already torn down by the PIC-55 posture and delivers no further events, so the debouncer is left unmarked — a debounce window already pending when the terminal signal fired quiesces at its own boundary through the entry probe of (a), one further probe touch and no second stderr line under the shared latch; (c) the quiesced path MUST NOT attempt system-note delivery — neither the ERR-7 `theta/runtime/registry-swap-failed` nor any load-phase re-emission — through the invalidated runtime: the `theta-system-note` channel and the `ctx.ui.notify` fallback arm ride the same invalidated runtime and are equally stale, so quiescence is the only reachable posture (no valid delivery surface remains), and the [PIC-54](./runtime-event-channel.md#pic-54) fallback chain applies only to a live runtime; (d) a caught error NOT matching the documented prefix is rethrown — the stale-probe posture narrows no other failure handling. The single stderr line is a designed fail-loud-once outcome, distinct from the PIC-54 terminal `system-note delivery failed:` cascade, which MUST NOT be produced by this path; the `console.error` emitting it is itself wrapped and a throw from it swallowed (the same defended-sink footing as [PIC-54](./runtime-event-channel.md#pic-54)), so a failing stderr sink cannot unwind the evidence site that observed the stale runtime. Zero guarded touches remain the requirement wherever the runtime can know of the teardown without touching: a `session_shutdown` consumed while an asynchronous `session_start` compose is still in flight (the arm-after-teardown race — the teardown's lazy watcher-handle read observes nothing to detach) MUST suppress the whole post-compose continuation when the compose settles — the publication of the composed generation's live teardown resources, the registration pass (on the success arm and equally on the compose-throw catch arm's static-fixture fallback), any diagnostic construction (the delivery channel rides the same invalidated runtime per clause (c), or — before the invalidation lands — would deliver into the outgoing session), and the arming of the step-5 watcher — without any probe touch and without a stderr line, since doing nothing is the posture this sentence and [PIC-57](#pic-57) jointly pin: not arming is already PIC-57-correct there; the suppression takes effect at the compose-settle boundary: a compose pass already in flight when the shutdown lands is not cancelled — once the invalidation has landed, its next guarded read dies reactively, and that swallowed in-flight read is not a violation of this sentence.

   <a id="pic-68"></a> **PIC-68. Repeat-`session_start` supersession — compose-generation staleness evidence, the supersession fold, and one-shutdown teardown reach across generations.** A `session_start` delivered to an extension instance that already completed one, with no intervening `session_shutdown`, is a supersession pass rather than a second arming; the arming posture, the supersede-before-publish ordering (detach the prior generation's teardown handle, drain its `ThetaRegistry`), and the one-line repeat-start system note are pinned at the [watcher / hot-reload registration step](./registration-steps.md#watcher-hot-reload-registration), and PIC-68 pins the three runtime obligations that make that posture hold across the asynchronous compose. **(Compose-generation evidence.)** The count of `session_start` compose passes entered joins the consumed-shutdown count of [PIC-67](#pic-67)'s final sentence as a second kind of touch-free staleness evidence at the SAME compose-settle boundary with the SAME zero-touch continuation suppression: a compose pass that observes when it settles — on the success arm and equally on the compose-throw catch arm — that a newer compose started during its own flight is already superseded (the newest-started pass owns all publication, registration, and arming) and MUST publish no live teardown resources, run no registration pass, construct no diagnostic, and arm no watcher, exactly as PIC-67's suppression sentence pins for the consumed-shutdown evidence; this closes the overlap inversion in which the LAST completer — possibly the older start — would otherwise own the single-occupancy live-resource slots, stranding the newest generation's armed watcher and undrained registry. **(Supersession fold.)** A completing supersession pass MUST — alongside the step-5 detach and drain, and before overwriting the live-resource slots — fold that generation's in-flight `ActiveInvocationRegistry` and forwarding-signal list into a factory-scoped supersession list, so the resources the detach/drain cannot settle — invocations still in flight under a superseded generation, and their still-attached forwarding listeners — remain reachable by the step-4 teardown above. **(Teardown reach.)** One `session_shutdown`'s sub-steps 2/3 (reason-stamp + cancel, bounded dispose-await) and 5 (forwarding-listener detach) MUST reach every generation the extension instance has published — the supersession list's generations in supersession order followed by the latest — not only the generation the live slots name at teardown time; sub-steps 1 and 4 operate on the LATEST generation only, because each superseded generation's registry was already drained and its watcher already detached at supersession time, so re-draining or re-detaching them from the teardown would tear a generation down twice. The teardown consumes the supersession list and the latest generation's teardown inputs synchronously at handler time, making a subsequent start-after-shutdown supersession pass a structural no-op (nothing left to fold, drain idempotent, no handle to detach), and a re-delivered `session_shutdown` (a permitted multi-delivery per [host-prerequisites clause (b)](./host-prerequisites.md#degraded-state-host-prerequisites)) short-circuits on the retained latest registry's drain state per the [**idempotent**](./drain-state-contract.md#idempotent-handler-clause) clause and cannot tear any generation down twice.
