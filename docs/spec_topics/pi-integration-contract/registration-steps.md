# Registration steps

**Discovery API.** The extension owns enumeration; it subscribes to `resources_discover` solely as a re-discovery trigger and returns the empty result `{}` (`ResourcesDiscoverResult` has no `thetaPaths` field — thetas reach Pi through `pi.registerCommand`, not as a Pi-managed resource type). The five sources, their priority order, the package-root walk, and the failure-mode table are all in [Directory Convention](../discovery.md). Cross-format collision detection consults `pi.getCommands()` on `session_start` (per the **Extension entry point** numbered list below); the call would throw if invoked during the extension factory itself (per the pre-bind action-method rule in **Extension entry point** step 2), which is why discovery is split across the factory (parse + pending list) and the `session_start` handler (collision check + `pi.registerCommand`).

1. Registers the `--theta` CLI flag via `pi.registerFlag('theta', { type: 'string', description: … })` **before** subscribing to `resources_discover`, so the value is readable from inside the discovery handler via `pi.getFlag('theta')`. `pi.getFlag` is declared on `ExtensionAPI` as `getFlag(name): boolean | string | undefined` at `dist/core/extensions/types.d.ts` in `@earendil-works/pi-coding-agent` (non-capability status pinned at [Non-capability `pi.<member>` surfaces](./inventory-audit-intro.md#non-capability-pi-members)); because theta registers `'theta'` with `type: 'string'` and no `default`, theta's own read narrows to `string | undefined`, yielding `undefined` when no `--theta` flag was passed on the CLI. An `undefined` (absent-flag) read contributes no `--theta` paths to the walk; the `path.delimiter` split below applies only to a present string value. The `'theta'` flag name's cross-extension namespace clearance — and the first-load-wins behaviour of `pi.registerFlag` on a name overlap — is recorded in [Discovery — File-extension namespace](../discovery/discovery-sources.md#theta-flag-namespace). The flag name `'theta'`, `type: 'string'`, the presence of a `description`, and the registration ordering relative to `resources_discover` are the observable pins; the exact `description` string is non-normative — Pi renders it only in `--help`, where it keys no theta surface — and `'Theta file or directory paths, joined with the OS path-list separator'` is an illustrative example. Walks the five discovery sources defined in [Directory Convention](../discovery.md) directly — the global directory `~/.pi/agent/theta/`, the project directory `.pi/theta/`, every installed package's `pi.theta` entry or conventional `theta/` directory (per [Package discovery](../discovery/package-and-settings.md#package-discovery)), the `thetaPaths` settings array (per [Settings file reads](../discovery/package-and-settings.md#settings-file-reads)), and the `--theta` CLI flag (whose `pi.getFlag('theta')` value is split on `path.delimiter` per [Directory Convention](../discovery.md)) — at factory time and again on every `resources_discover` event. The event payload (`{ cwd, reason }`) supplies the project root used for the project-local source (the factory-time scan resolves the project root from the [`FileSystem.cwd()` seam member](./host-interfaces-services.md#pic-13); on every `resources_discover` event `event.cwd` is preferred over that seam value, so a future per-session cwd change is honoured on reload) and distinguishes initial scan (`reason: "startup"`) from reload (`reason: "reload"`); Pi delivers no paths to the handler — `ResourcesDiscoverResult` has no `thetaPaths` slot — and Pi's `resources_discover` resource-discovery namespace does not itself enumerate `pi.theta`: the theta extension reads each installed package's theta-owned `pi.theta` key directly during its own package-root walk above (per [Package discovery](../discovery/package-and-settings.md#package-discovery)), so the contents of `pi.theta` reach theta through that walk, not through Pi's manifest namespace. The theta extension owns the walk for all five sources; the event is purely a re-trigger, and the handler returns the empty result `{}` to satisfy the typed return.
2. Parses each discovered `.theta` file and builds a *pending registration list* keyed by slash name. The factory does **not** call `pi.registerCommand` synchronously — Pi's prompt templates and other extensions' commands are not yet enumerable at factory time, so cross-format collision detection cannot run here. Concretely, on the pre-bind runtime returned to the extension factory by `createExtensionRuntime()`, every action method that reads or mutates session-bound state — including `getCommands`, `getActiveTools`, `getAllTools`, `setActiveTools`, `sendMessage`, `sendUserMessage`, `setModel`, `getThinkingLevel`, `setThinkingLevel`, and the rest of the `notInitialized`-tagged slots in `@earendil-works/pi-coding-agent`'s `dist/core/extensions/loader.js` — is bound to a throwing closure (`Error("Extension runtime not initialized. Action methods cannot be called during extension loading.")`) that `Runner.bindCore()` later overwrites with the real implementation alongside `session_start`. The token `notInitialized` is the internal variable name of that throwing closure inside Pi's loader source; it is **not** an observable sentinel value an extension can compare against or switch on. Calling any of these methods from inside the factory raises an unhandled exception that aborts factory load. <a id="pre-bind-throw-closure-evidence"></a>The `dist/core/extensions/loader.js` path, the `notInitialized` internal variable name, the private `Runner.bindCore()` overwrite step, and the verbatim throw-string text above are **known-fragile evidence** at the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin) — diffable artefacts witnessing that the pre-bind action-method slots throw at the pin, not load-bearing claims about their stable shape across patches (a Pi patch may rename the `_`-prefixed loader internals, re-bundle the `dist/` tree, or reword the throw string). The observable rules in this step — that calling a session-state action method pre-bind aborts factory load, while the registration sinks and `refreshTools` are safe before bind — hold independent of that evidence trail, which is re-audited on each Pi minor bump via [item (q) of the *Editorial-review checklist for unpinned host presuppositions*](./version-bump-step2.md#bump-checklist-pre-bind-and-renderer-resolution) under [Pi version bump procedure](./version-bump-intro.md#pi-version-bump-procedure) below. The methods Pi documents as safe before bind are `pi.registerCommand` / `pi.registerTool` / `pi.registerFlag` / `pi.registerMessageRenderer` (registration sinks) and `refreshTools` (a no-op on the pre-bind runtime). Every other reach for session state is deferred to a `session_start` (or later) handler. The signature pinned by theta 1.0 is `pi.getCommands(): SlashCommandInfo[]` (synchronous, returns the current registered-commands snapshot, where `SlashCommandInfo` is the interface exported from `@earendil-works/pi-coding-agent`'s `core/slash-commands.d.ts` with fields `{ name, description?, source: SlashCommandSource, sourceInfo }`); the snapshot is only meaningful on or after `session_start` (its read-only-by-convention treatment is pinned by [PIC-39](#pic-39) below). The build-time SDK surface inventory (per *Host prerequisites*) MUST list `SlashCommandInfo` and the three-arm `SlashCommandSource = "extension" | "prompt" | "skill"` explicitly so a Pi minor that renames either fails the build.

   <a id="pic-39"></a> **PIC-39. `pi.getCommands()` snapshot read-only-by-convention.** The `SlashCommandInfo[]` array `pi.getCommands()` returns is mutable in the type system but MUST be treated as read-only by convention: the theta 1.0 cross-format collision check (step 3) is a single forward pass and never mutates it.

3. Subscribes a `session_start` handler that consults `pi.getCommands()` (a throw from this read is handled per the [`pi.getCommands()` read-failure rule](./extension-bootstrap-and-per-theta.md#getcommands-read-failure) under **Extension-bootstrap SDK failures**: the handler swallows it, drops the pending-registration list for this pass, and emits one `theta/load/extension-bootstrap-failed`), drops any pending theta whose slash name collides with an existing entry whose `source` is in the [theta 1.0 cross-format collision source set](#theta-1-0-seam-pi-owned-subagents-collision-source-set) defined below — the three arms of Pi's `SlashCommandSource` union (`"prompt"`, `"extension"`, `"skill"`), per `@earendil-works/pi-coding-agent`'s `core/slash-commands.d.ts` and per [Discovery — Slash-name collisions across formats](../discovery.md) — minus the entries this extension instance itself registered, which [PIC-69](#pic-69) below excludes from the source set on every pass — <a id="slash-handler-registration"></a>registers each survivor via `pi.registerCommand(name, { description, handler })` — one slash command per theta — and emits a `theta/load/cross-format-collision` diagnostic for each drop through the channel defined in [Diagnostics](../diagnostics.md). The `description` field passed to `pi.registerCommand` carries `frontmatter.description` verbatim and only that — `argument-hint` is **not** concatenated, since Pi's extension-command autocomplete UI has no `argumentHint` slot and the binder is the only theta 1.0 consumer of `argument-hint` (see [Slash-Command Argument Binding](../binder.md)). theta 1.0 passes only the two keys `description` and `handler`; the optional `getArgumentCompletions` key is omitted, since Pi's `RegisteredCommand` interface types it as optional and theta 1.0 exposes no autocomplete-completion surface (a deferred `argumentHint`-style upstream is tracked in [Future Considerations](../future-considerations/surface-extensions.md#surface-extensions-without-a-dedicated-topic-page-seam)). The same handler also drops the `ThetaRegistry` entry of any previously-registered theta whose name now collides with a newly-appeared `.md` prompt template or `.md` skill (e.g. after a settings reload), emitting the same diagnostic. A newly-appeared *foreign* extension command under that name does NOT reach this drop: the name is by construction one this instance already passed to `pi.registerCommand`, so [PIC-69](#pic-69) excludes every `source: "extension"` entry under it — self and sibling alike — which is the sibling indistinguishability that pin records as a known limitation. This drop is a `ThetaRegistry`-side entry-table removal only — Pi exposes no symmetric `pi.unregisterCommand` (see the [*Structural changes*](#structural-changes-no-unregister) paragraph in the **Hot-reload subsystem** section below), so the theta's `pi.registerCommand` registration survives and a dispatch of the orphaned `/<name>` returns the fixed superseded note per the [superseded-entry dispatch](#superseded-entry-dispatch) sub-case of arm (a). *Drain-state-gated dispatch.* The `handler` value passed as the `handler` field of every `pi.registerCommand(name, { description, handler })` call above MUST, on every slash dispatch, invoke `ThetaRegistry.readDrainState()` as its first action and route through the closed two-arm enumeration (a)/(b) pinned by the **`ThetaRegistry` drain-state contract**'s *Methods* paragraph below — including that paragraph's *Read-failure fallback* clause, which pins arm (b) (the `"theta /<name>: extension shutting down"` system note) as the conservative non-dispatch fail-safe when the `readDrainState` call itself throws. This obligation is normative at this registration site; the arm enumeration and the read-failure routing are owned by the *Methods* paragraph below and are not restated here.

   <a id="superseded-entry-dispatch"></a>*Superseded-entry dispatch.* Arm (a) of the [`ThetaRegistry` drain-state contract](./drain-state-contract.md#theta-registry-drain-state-contract)'s two-arm dispatch enumeration (introduced by the *Drain-state-gated dispatch* clause above) dispatches the theta by looking the dispatched slash name up in the entry-table `Map<slashName, parsedTheta>` (the lookup step 5 below establishes). When a `session_start` supersession pass has dropped that entry — the `ThetaRegistry`-side entry removal [Discovery — DISC-4](../discovery/discovery-sources.md#disc-4) performs when a later-appearing Pi prompt template or skill collides with an already-registered theta (a later-appearing *sibling-extension* command under that name does not reach the drop, per [PIC-69](#pic-69)'s known limitation) — the theta's `pi.registerCommand` registration still survives (Pi exposes no `pi.unregisterCommand`, per the [*Structural changes*](#structural-changes-no-unregister) paragraph in the **Hot-reload subsystem** section), so `/<name>` still reaches this handler but the entry-table lookup finds nothing. On that miss the handler returns the fixed superseded system note `"theta /<name>: superseded; /reload to refresh"` — modelled on the drain-state short-circuit notes' `/reload`-prompt form, with `<name>` the dispatched slash name and `/reload` the operator action that re-runs the extension factory and refreshes the slash command list — rather than dispatching. This miss path is a sub-case of arm (a)'s steady-state dispatch: it is reached only after `readDrainState` returns the steady-state tuple `(drained: false, tag: undefined)` and arm (a) is selected, so it reads the same tuple and introduces no third `readDrainState` arm — the two-arm enumeration above stays closed.

   Step 3's first `session_start` collision pass additionally relies on a Pi *behavioural* precondition the `SlashCommandInfo[]` snapshot does not encode — that by the time Pi emits the first `session_start`, `pi.getCommands()` already enumerates every command Pi registers from prompt templates, skills, and load-order-earlier sibling extensions — specified as the [`pi.getCommands()` first-`session_start` completeness presupposition](./host-prerequisites.md#getcommands-completeness-presupposition) under **Host prerequisites**.

   <a id="pic-69"></a> **PIC-69. Own-registration exclusion from the cross-format collision source set.** The collision source set is keyed on an entry's `source`, and Pi reports every command an extension registered — including the theta extension's own `pi.registerCommand(name, …)` registrations — as `source: "extension"`, so a source-keyed read taken literally makes an extension instance collide with itself on every pass after the one that registered the name. On EVERY pass that consults `pi.getCommands()` for the cross-format collision check — the first `session_start` pass, each hot-reload pass (per the **Hot-reload subsystem** below), each repeat-`session_start` supersession pass (per [*repeat-`session_start` supersession*](#repeat-start-supersession)), and each start-after-shutdown rebind pass (a `session_start` delivered after a COMPLETED `session_shutdown`: it supersedes nothing, so that clause's no-intervening-shutdown definition puts it outside supersession, yet its `pi.getCommands()` snapshot still carries the prior generation's registrations) — the extension instance MUST exclude from the collision source set every entry that both carries `source: "extension"` and bears a `name` this instance itself passed to `pi.registerCommand`. The excluded set is the instance's own registration ledger — every name this instance has ever passed to `pi.registerCommand`, not the names its current `ThetaRegistry` holds: Pi exposes no `pi.unregisterCommand` (per the [*Structural changes*](#structural-changes-no-unregister) paragraph below), so a name registered by an earlier pass and since dropped from the registry is still reported back by `pi.getCommands()` and would still self-collide. The exclusion is conditioned on `source`, never on the name alone: a `"prompt"` or `"skill"` entry that has appeared under a name this instance registered is NOT excluded and still drops the theta per step 3 above — that newly-appeared-`.md`-template drop is a rule the exclusion MUST NOT weaken. *Known limitation — sibling indistinguishability.* An entry a DIFFERENT extension registered under a name this instance also registered carries the same `source: "extension"` and is excluded by this rule too, so that one cross-format collision goes undetected and the theta registers alongside the sibling's command instead of dropping; at the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin) Pi then derives distinct invocation names for the two registrations, so neither is lost. `SlashCommandSource` cannot separate self from sibling, and theta 1.0 does not read `SlashCommandInfo.sourceInfo` to try; the ambiguity is accepted, because the alternative — self-collision on every re-bind — drops every one of the instance's own slash names.

   <a id="surviving-name-re-ownership"></a>*Surviving-name re-ownership.* Because [PIC-69](#pic-69) removes this instance's own prior registrations from the collision source set, a supersession pass (and a start-after-shutdown rebind pass) RE-OWNS every slash name whose `.theta` still resolves in that pass's discovery: the name survives the collision check, registers again through `pi.registerCommand(name, { description, handler })` — rebinding the live `/<name>` to the new generation's drain-gated handler over the new generation's `ThetaRegistry` — and emits no `theta/load/cross-format-collision` diagnostic (there is no collision to report; a diagnostic naming a Pi-owned survivor would misdescribe the instance's own registration). At the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin) that repeat registration overwrites the extension's existing entry for the name in place rather than minting a second command, which is what makes the rebind observable to the operator; that overwrite behaviour is known-fragile host evidence of the same class as the [pre-bind throw-closure evidence](#pre-bind-throw-closure-evidence) above, not a claim about stable host shape. A name whose `.theta` no longer resolves in that pass is NOT re-registered: its handler stays bound to the superseded, drained `ThetaRegistry` and dispatch fails safe on arm (b) with the `"theta /<name>: extension shutting down"` note, exactly as [*repeat-`session_start` supersession*](#repeat-start-supersession) pins.

   > **theta 1.0 seam — Pi-owned subagents collision source set.** <a id="theta-1-0-seam-pi-owned-subagents-collision-source-set"></a> A pending theta collides — and is dropped by the `session_start` handler — when an existing entry's `source` is one of `"prompt"`, `"extension"`, `"skill"` (the three arms of `SlashCommandSource` under `@earendil-works/pi-coding-agent` at the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin)); a `source` outside that set is not a collision candidate. Whether the runtime expresses that membership rule as a single named set consulted by membership test or as open-coded comparisons is an unobservable implementation choice, not a normative requirement — the named-set form is suggested only because it localises the one edit the future-widening invariant below needs. The deferred *Pi-owned subagents exposed as enumerable slash commands* extension in [Future Considerations](../future-considerations.md) lands by widening that set to four arms (adding a `"subagent"` entry) when a future Pi minor extends `SlashCommandSource` accordingly; widening the set is the only theta 1.0 surface that perturbs, and the asymmetric loser-drops collision rule defined in [Discovery](../discovery.md) is preserved by construction.
4. Subscribes a `session_shutdown` handler (`pi.on("session_shutdown", handler)`) that owns disposing every resource the extension instance holds. The Pi SDK documents `session_shutdown` as fired before an extension runtime is torn down due to quit, reload, or session replacement, with `event.reason: "quit" | "reload" | "new" | "resume" | "fork"`; theta uses it as the single teardown contract for the outgoing extension instance so that Pi's subsequent `ExtensionRuntime.invalidate(...)` call does not strand subagent provider connections, chokidar file handles, debounce timer handles, or `AbortController` listeners across `/reload`, `/new`, fork, or quit. Disposing the debounce timer handles also cancels any rebuild deferred under the cross-window serialization rule [PIC-49](#pic-49) and marks the hot-reload debouncer torn-down so no new rebuild starts; teardown then bounded-awaits any *already-in-flight* rebuild to quiesce (rather than leaving it to resume against the invalidated runtime) per [PIC-57](./session-shutdown-semantics.md#pic-57), bounded by the single shared `SHUTDOWN_AWAIT_CAP_MS` teardown deadline so shutdown stays bounded. <a id="extension-runtime-invalidate-teardown"></a>This step is the canonical owner of the `ExtensionRuntime` pin: the `ExtensionRuntime` interface — and the `invalidate(...)` member the teardown contract names — is declared at `dist/core/extensions/types.d.ts` in `@earendil-works/pi-coding-agent` (the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin) from **Host prerequisites** above); theta redefines neither and consumes neither (it never calls `invalidate(...)` — Pi does). The teardown contract presupposes that Pi fires `session_shutdown` on the outgoing instance before it calls `ExtensionRuntime.invalidate(...)` — a presupposition that holds on the host's replacement and quit paths (`newSession` / `switchSession` / `fork` / `reload` / quit) but **not** universally: a bare `AgentSession.dispose()` (a public host SDK API) invalidates the runtime without any preceding `session_shutdown`, so the teardown above never runs on that path and the runtime learns of the invalidation only reactively, per the stale-probe posture [PIC-67](./session-shutdown-semantics.md#pic-67) under **Session shutdown semantics**. The contract further presupposes that a `pi.*` call reaching an already-invalidated runtime throws (the stale-ctx error whose stable message prefix PIC-67 keys detection on). Neither the member nor that post-invalidation throw behaviour is factory-probed or enumerated by step 2(a)'s seven-capability literal-read assertion, so a silent rename or behavioural change surfaces as a runtime error mid-teardown rather than at load time, and is re-audited on each Pi minor bump via [item (t) of the *Editorial-review checklist for unpinned host presuppositions*](./version-bump-step2.md#bump-checklist-extension-runtime-invalidate) under [Pi version bump procedure](./version-bump-intro.md#pi-version-bump-procedure) below.
5. <a id="watcher-hot-reload-registration"></a>Registers a chokidar file watcher over the discovered roots and maintains an internal mutable `ThetaRegistry` (a `Map<slashName, parsedTheta>`) plus a `.thetalib` import graph. <a id="watch-scope-import-closure"></a>The watched set additionally covers the parent directory of every `.thetalib` file the import graph resolves, including one that resolves outside every discovered root (bug 0312); when a reload pass changes that resolved closure, the runtime re-arms the single watcher — tearing down the prior subscription and arming a fresh one over the updated set — rather than holding a second, supplementary watcher, so at most one watcher is ever armed through re-arm — the same single-armed-watcher invariant the repeat-`session_start` case below preserves. This re-arm is subject to the [PIC-55](#pic-55) terminal posture: once a terminal *stopped-delivering* signal has left the watcher torn down until the operator runs `/reload`, a reload pass whose closure differs MUST NOT re-arm it — the terminal posture governs, and the watcher stays torn-down-until-`/reload` rather than resurrected by a pending reload. The slash-command `handler` registered in step 3 closes over the registry and dispatches by slash name on every invocation, so a registry swap takes effect on the next call without a `pi.registerCommand` re-registration. The hot-reload behaviour this watcher drives — debounced re-parse, the build-aside-then-publish registry swap, the in-flight-invocation rule, cross-window serialization, watcher recovery, and the structural-change note — is specified in the [**Hot-reload subsystem**](#hot-reload-subsystem) section below. The ordering constraint requiring step 4's `session_shutdown` subscription to follow this registry/watcher construction is the [**Factory-ordering pin**](./session-shutdown-semantics.md#factory-ordering-pin) under **Session shutdown semantics** below. <a id="repeat-start-supersession"></a>A repeat `session_start` delivered to an extension instance that already completed one — with no intervening `session_shutdown` — is a supersession pass, not a second arming: at the [theta 1.0 Pi-SDK pin](./host-prerequisites.md#pi-sdk-pin) the host's public `AgentSession.bindExtensions()` re-emits the stored `session_start` to the same extension instance on every call, and step 3's supersession-pass language already treats a later `session_start` as a contemplated re-registration input, so the runtime MUST survive the repeat delivery with the single-armed-watcher invariant intact — the extension instance arms at most ONE hot-reload watcher across repeat `session_start` deliveries. A completing supersession pass MUST, BEFORE publishing its own live resources (its `ThetaRegistry`, teardown handle, and teardown inputs), detach the prior generation's step-4 teardown handle — closing that generation's watcher and quiescing its debouncer, so no superseded-generation reload can rebuild or re-register after the supersession (the same no-rebuild-after-teardown posture [PIC-57](./session-shutdown-semantics.md#pic-57) pins for shutdown) — and drain the outgoing generation's `ThetaRegistry`, so any slash name whose registered `handler` is still bound to the superseded registry (Pi exposes no `pi.unregisterCommand`, per the [*Structural changes*](#structural-changes-no-unregister) paragraph below) fails safe at dispatch on arm (b) of the [`ThetaRegistry` drain-state contract](./drain-state-contract.md#theta-registry-drain-state-contract)'s two-arm enumeration with the `"theta /<name>: extension shutting down"` note. A throwing detach MUST be caught — it MUST NOT escape into the host `session_start` dispatch or abort the superseding pass — MUST leave the containment above in place (the torn-down marks applied before the one fallible watcher-close step), and MUST emit exactly one `theta/host/session-start-supersession-detach-failed` diagnostic (see [Diagnostics — Code registry host](../diagnostics/code-registry-host.md)). Before that publish the pass MUST additionally (a) mark the outgoing generation's debouncer torn-down and (b) bounded-await any already-in-flight superseded-generation rebuild — the same two acts [PIC-57](./session-shutdown-semantics.md#pic-57) pins for `session_shutdown` sub-step 4 — so a rebuild that entered `runReload` before this pass's own supersession step either completes its single synchronous publish per [PIC-36](#pic-36) against the still-undrained outgoing registry, or is a no-op, or is abandoned once the bound elapses, closing the gap the detach-and-drain acts above leave open for a rebuild already past its entry guard. The bound is owned by the supersession pass, not by the `session_shutdown` deadline sub-step 4 shares with its own sub-step 3; theta 1.0 contracts only the bound's existence, on the same footing as the 250 ms debounce window below ("The specific `250 ms` figure is an implementer tuning choice, not part of theta's observable contract"), not its value. A rebuild still in flight when the bound elapses is abandoned under the torn-down mark and emits no diagnostic, the same posture [PIC-57](./session-shutdown-semantics.md#pic-57) pins for its own cap; a throw out of either act is caught under the posture the detach throw above already carries and emits the same `theta/host/session-start-supersession-detach-failed` diagnostic, and leaves an already-in-flight rebuild unawaited, on the same footing as the bound elapsing. A repeat `session_start` delivery is therefore bounded-blocking on the superseded generation's in-flight rebuild. A compose pass that observes a NEWER compose started during its own flight MUST publish, register, and arm nothing — the zero-touch posture pinned by [PIC-68](./session-shutdown-semantics.md#pic-68), which joins the compose-generation evidence to [PIC-67](./session-shutdown-semantics.md#pic-67)'s compose-settle continuation suppression. Each shutdown-less repeat delivery additionally emits exactly one informational `theta-system-note` whose `content` is byte-exact `theta: repeat session_start without session_shutdown; superseding prior hot-reload generation` (`display: true`, `triggerTurn: false` — the standard system-note envelope), emitted at delivery time, before the compose runs, so the overlapping-starts case still yields exactly one note; a start-after-shutdown rebind emits none and supersedes nothing (its prior generation was already torn down). The superseded generation's in-flight invocation registry and forwarding-signal list are folded into the factory-scoped supersession list for the step-4 teardown's cross-generation reach, per [PIC-68](./session-shutdown-semantics.md#pic-68).

## Hot-reload subsystem

On a chokidar event for an **existing** theta or `.thetalib` file the watcher debounces (a default 250 ms window, to coalesce editor `change` + `rename` bursts; the window is measured against the runtime's injected `Clock` seam (per the runtime's DI skeleton — see [`Clock` / `FakeClock` interface](./host-interfaces-services.md#clock--fakeclock-interface) below), the seam exists to make burst-coalescing assertions deterministic and is not a tunable runtime knob. The specific `250 ms` figure is an implementer tuning choice, not part of theta's observable contract: what is contracted is the burst-coalescing behaviour under the injected `Clock` seam — coalescing an editor `change` + `rename` burst into one rebuild — not the literal millisecond value, so a window of, say, 200 ms or 300 ms is equally conformant), re-parses just the changed file plus every transitive `.thetalib` importer reached through the import graph, and atomically swaps the affected entries in `ThetaRegistry` via build-aside-then-publish: the runtime re-parses the changed file plus every transitive `.thetalib` importer into a staging set, recompiles their AJV validators into a staging cache, and re-registers the tools synthesised from prompt-mode `.theta` callables through `pi.registerTool` for every newly-distinct schema slug the staged rebuild produces (that `pi.registerTool` accepts registration calls after startup is the [`pi.registerTool` post-startup registration acceptance presupposition](./host-prerequisites.md#register-tool-post-startup-presupposition) under **Host prerequisites**; existing cached registrations under unchanged slugs are reused, so no `pi.registerTool` call is issued for them) — and only after every step, including the `pi.registerTool` re-registration, succeeds installs the staged registry, the staged validator cache, and the staged prompt-mode registration-cache entries into `ThetaRegistry`, the validator cache, and the registration cache in a single synchronous publish step. If any rebuild step throws — including a `pi.registerTool` throw for a newly-distinct schema slug, which is sequenced before publish — the staging set is discarded and the prior `ThetaRegistry` snapshot, AJV validator cache, and prompt-mode registration cache all remain live; the failure surfaces as a single `theta/runtime/registry-swap-failed` diagnostic (see [Diagnostics](../diagnostics.md)). Because Pi exposes no `pi.unregisterTool` (per [Tool-registration lifetime and visibility](./tool-registration-lifetime.md#tool-registration-lifetime-and-visibility)), any `pi.registerTool` call that already succeeded before the throw leaves an orphaned entry in Pi's global tool registry — the cosmetic accumulation that section already accepts — while theta-side rollback is limited to discarding the never-published staged registry snapshot and staged registration-cache entries. Compiled AJV validators for swapped entries are dropped from the per-theta cache as part of the publish step (not before). The runtime does **not** call `ctx.reload()` for content edits — doing so would tear down every Pi extension, skill, prompt, and theme in the session for a single keystroke and would also race the post-`await` runtime-deadness rule that `ctx.reload()` documents.

<a id="pic-55"></a> **PIC-55. Watcher post-`error`/post-throw continuation and recovery posture.** The chokidar adapter's own `error` route (per [PIC-14](./host-interfaces-services.md#pic-14)) and a synchronous throw out of the watcher are governed by a single posture with two cases. The operational criterion distinguishing the two cases is whether the chokidar adapter's underlying watcher keeps emitting filesystem events (`add`/`change`/`unlink`) on each watched root after the error or throw: a root that still emits is *continues-delivering*, while a root for which the adapter's watcher has torn down or otherwise ceased emitting is *stopped-delivering — terminal*. **(Continues-delivering.)** When the watcher keeps delivering events on the watched roots after the error, hot-reload survives; the error is surfaced as a transient informational `ctx.ui.notify` toast (the already-named chokidar-error case under [Diagnostics — Transient toasts](../diagnostics/diagnostic-shape.md#transient-toasts)) and no further recovery action is taken. **(Stopped-delivering — terminal.)** When the error or throw leaves one or more watched roots no longer delivering events, the adapter leaves the watcher torn down rather than re-armed, so hot-reload can no longer fire for the affected roots until the operator reloads. The adapter conveys this terminal condition to the runtime through an enumerated *terminal-signal channel* on the [`FileWatcher` seam](./host-interfaces-services.md#pic-14) — distinct from the seam's `add`/`change`/`unlink` event stream and from the `ctx.ui.notify` toast route used for the continues-delivering case — and the runtime's persistent-note emission point below is reached only through that channel; the member/API shape carrying the signal (an added event kind, a separate terminal callback, or equivalent) is left to the implementer per [GOV-18 arm (a)](../governance/corpus-direction-and-scope.md#gov-18-arm-a). In this case the runtime MUST emit a single persistent `theta-system-note` carrying the `theta/runtime/watcher-terminated` diagnostic (see [Diagnostics](../diagnostics.md)) — using the persistent `theta-system-note` channel as its primary sink, NOT `ctx.ui.notify` — prompting the operator to run `/reload`, mirroring the [structural-change `/reload` system-note pattern](#structural-changes-no-unregister) above. The `ThetaRegistry` stays live and dispatchable: subsequent slash dispatches continue to route through arm (a) of [`ThetaRegistry.readDrainState`](./drain-state-contract.md#theta-registry-drain-state-contract)'s two-arm enumeration against the last-published registry snapshot (now potentially stale until `/reload`), and the runtime MUST NOT write the `ThetaRegistry` drain-state tag from this path — a tag write here would trip the `session_shutdown` handler-entry short-circuit predicate (per the [**idempotent** clause](./drain-state-contract.md#idempotent-handler-clause)), which assumes the tag is written only by the teardown path, and skip teardown, stranding resources across the subsequent `/reload`. Operator recovery is one `/reload` away (which re-executes the extension factory and re-arms the watcher), on the same theta 1.0 footing as the structural-change note; unlike the prior posture, this dispatch into a watcher-dead runtime is surfaced by the persistent note rather than left silent. The persistent-note emission presupposes a live extension runtime: when the emission throws the stale-ctx invalidation error (a shutdown-less invalidation preceded the terminal signal), the note is undeliverable and the recovery posture instead emits the single latched `theta hot-reload quiesced:` stderr line per [PIC-67](./session-shutdown-semantics.md#pic-67) clause (b).

<a id="pic-36"></a> **PIC-36. Registry-swap atomicity.** The watcher MUST install the staged `ThetaRegistry`, AJV validator cache, and prompt-mode registration-cache entries in a single synchronous publish step that runs only after every staged re-parse / recompile / re-register step succeeds; if any step throws, the staging set is discarded, the prior `ThetaRegistry` snapshot, AJV validator cache, and prompt-mode registration cache all remain live, and the failure surfaces as a single `theta/runtime/registry-swap-failed` diagnostic (see [Diagnostics](../diagnostics.md)). The build-aside-then-publish mechanism that satisfies this contract is described in the subsystem paragraph above.

**In-flight invocation rule.** The slash-handler closure registered in step 3 (which calls `ThetaRegistry.readDrainState()` per the [*Drain-state-gated dispatch*](#slash-handler-registration) clause and routes through the entry table for the dispatch arm) reads the entry exactly once at handler entry; a swap mid-execution does not affect a running invocation. Slash-command dispatch is gated by the two-arm `ThetaRegistry.readDrainState()` enumeration pinned in the [*Drain-state-gated dispatch*](#slash-handler-registration) clause appended to step 3 above and the [`ThetaRegistry` drain-state contract](./drain-state-contract.md#theta-registry-drain-state-contract) below (including that contract's *Methods* paragraph's [*Read-failure fallback*](./drain-state-contract.md#read-failure-fallback) clause); that contract supersedes the prior single-arm `drained`-keyed short-circuit and is the sole authority on which behaviour (the `"shutting-down"` arm's `"theta /<name>: extension shutting down"` note, or arm (a) dispatch) the handler returns. The next invocation sees the post-swap version. In-flight invocations therefore complete against the pre-swap snapshot and any tool calls or queries they have already committed remain final, consistent with [Errors and Results — No rollback](../errors-and-results.md).

<a id="pic-49"></a> **PIC-49. Cross-window rebuild serialization.** At most one rebuild runs against the live `ThetaRegistry`, AJV validator cache, and prompt-mode registration cache at a time. The drop-and-reschedule coalescing within a single debounce window (the default 250 ms per the subsystem paragraph above, whose value is an implementer tuning choice rather than a contracted boundary) is unchanged; this rule governs only the across-window case. A debounce timer that fires while a prior window's rebuild is still awaiting its asynchronous steps (re-parse, AJV recompilation, `pi.registerTool`) MUST NOT start a concurrent rebuild against the live `ThetaRegistry`, validator cache, and registration cache; instead the runtime defers it until the in-flight rebuild's single synchronous publish — or its `theta/runtime/registry-swap-failed` discard (per [PIC-36](#pic-36)) — completes, then runs the deferred rebuild against the now-current live state. No edit is lost across the deferral: the deferred rebuild re-parses the changed-file set observed up to its own debounce close, so the latest on-disk content is the one published. Serialization makes the publish order well-defined — a stale older rebuild cannot publish over a newer one, staged-validator construction cannot interleave with another rebuild's validator-cache eviction, and a `theta/runtime/registry-swap-failed` outcome is attributed to exactly one rebuild. The **In-flight invocation rule** above is unchanged: running invocations continue against their pre-swap snapshot and each publish remains a single synchronous write. The `session_shutdown` teardown interaction with a deferred or in-flight rebuild — cancelling the deferral, marking the debouncer torn-down so no new rebuild starts, and bounded-awaiting an in-flight rebuild to quiesce before Pi invalidates the runtime — is pinned by [PIC-57](./session-shutdown-semantics.md#pic-57).

<a id="structural-changes-no-unregister"></a>**Structural changes.** Adding a brand-new `.theta` file or removing an existing one cannot register / unregister a slash command after extension load (Pi exposes no symmetric `pi.unregisterCommand` for the removal case, and adding a new command after the extension factory has run is not a documented post-startup mutation). When the watcher observes such an event, it emits a single `theta-system-note` with `content` formatted as `theta watcher: <N> file(s) added or removed; run /reload to refresh the slash command list`, `display: true`, and the `details` payload defined under System notes. The substitution rule is fixed: only `<N>` is substituted; every other character of the template — including the literal token `file(s)` (always rendered with the parenthesised `s`, never pluralised), the literal slash-command name `/reload` (not substituted from any registered command), and the trailing `; run /reload to refresh the slash command list` clause — ships verbatim regardless of `N`. `<N>` is rendered in base 10 with no thousands separator, no leading zero, and no sign, and equals `details.structural.added.length + details.structural.removed.length` (a path that appears in both arrays — e.g., a rename observed as removal-then-addition within the same debounce window — counts twice, since the two arrays are disjoint by role and not deduplicated against each other). Worked examples: with `added.length = 1, removed.length = 0`, the rendered content is `theta watcher: 1 file(s) added or removed; run /reload to refresh the slash command list`; with `added.length = 3, removed.length = 2`, it is `theta watcher: 5 file(s) added or removed; run /reload to refresh the slash command list`. The note is not emitted when `added.length + removed.length === 0` (the empty-window suppression contract is [PIC-37](#pic-37) below). A debounce window that closes with no resolved add or remove paths produces no `theta-system-note` — including a settings-file edit whose post-merge `thetaPaths` array is byte-identical to the previous resolved set, an edit that touches only `theta.binderModel` or unrelated keys, and a chokidar burst over discovery roots that does not net any added or removed `.theta` / `.thetalib` files. The watcher's other obligations for the window (validator-cache invalidation per the **In-flight invocation rule** above, settings-file cache invalidation per the settings-file watcher path) still run; only the note is suppressed. A rename observed within the same debounce window as `removed` of path P followed by `added` of path P still has `added.length + removed.length === 2` and emits the note (the same-window-rename emission contract is [PIC-38](#pic-38) below); the suppression applies only to the strictly-empty case. The note prompts the user to run `/reload` (which invokes Pi's `ctx.reload()` and re-executes the entire extension factory). Multiple structural events observed within a single debounce window (the default 250 ms per the subsystem paragraph above, an implementer tuning choice rather than a contracted boundary) coalesce into one note; events in distinct windows fire separately. The note is informational, not a diagnostic; no `theta/load/*` code is registered for it. Settings-file edits affecting the `thetaPaths` array are treated as structural changes and routed through the same prompt; per-`.theta`-file content edits are not.

<a id="pic-37"></a> **PIC-37. Structural-change note empty-window suppression.** The structural-change `theta-system-note` MUST NOT be emitted when `added.length + removed.length === 0`: a debounce window that closes with no resolved add or remove path produces no note, while the window's other obligations (validator-cache and settings-file-cache invalidation) still run, per the [*Structural changes*](#structural-changes-no-unregister) paragraph above.

<a id="pic-38"></a> **PIC-38. Structural-change note same-window-rename emission.** A rename observed within one debounce window as `removed` of path P followed by `added` of path P has `added.length + removed.length === 2` — the two arrays are disjoint by role and not deduplicated against each other — and the note MUST be emitted; the empty-window suppression of [PIC-37](#pic-37) applies only to the strictly-empty case, per the [*Structural changes*](#structural-changes-no-unregister) paragraph above.
