# Lexical Structure

**Source files.** `.theta` and `.thetalib` files are decoded and normalised before lexing; every other rule on this page (and every other spec rule mentioning "newline") operates on the post-normalisation stream.

- **Encoding.** Source files are UTF-8. A leading UTF-8 BOM (`EF BB BF`) is consumed and ignored. Any other BOM, or any byte sequence that is not valid UTF-8 (including lone surrogates), is a load-time error `theta/load/invalid-encoding` reporting the file path and the zero-based byte offset of the first invalid byte in the original (pre-normalisation) file content; for a non-UTF-8 BOM the reported offset is `0` (the BOM's leading byte, not the byte at which the UTF-8 state machine first faults). The runtime performs no transcoding from other encodings (Latin-1, UTF-16, etc.); a Notepad-style UTF-16 save fails fast rather than producing mojibake. Source files are obtained as raw bytes through PIC-13's [`FileSystem.readBytes`](./pi-integration-contract/host-interfaces-services.md#pic-13-readbytes) seam and UTF-8-validated by the runtime before decoding, which is what makes the pre-decode byte sequence — and hence the first-invalid-byte offset above — observable.
- **Newline normalisation.** Before lexing, line endings are normalised: `\r\n` → `\n` and bare `\r` → `\n`. Every spec rule that mentions "newline" — statement separation below, the "literal newline in regular string is a parse error" rule below, `@`...`` query newline-trim and dedent (see [Query](./query.md)), and `///` doc-comment joining (see [Descriptions](./descriptions.md)) — operates on the normalised stream. A `.theta` checked in with CRLF line endings therefore tokenises and dedents byte-identically to the same file with LF endings; this is observable behaviour, not an implementation detail.
- <a id="rest-of-line"></a>**`RestOfLine` terminal.** A grammar terminal — used by the `DocComment` production in [Grammar Appendix — `///` placement](./grammar.md#-placement) — denoting a possibly-empty maximal run of characters on the normalised stream that contains no `\n` (and therefore, after the normalisation above, no `\r`). No escape processing is applied: the run is the verbatim remainder of the source line. An empty `RestOfLine` (a bare `///` with nothing after the sigil) is admitted, so an empty `///` line carries an empty description fragment (see [Descriptions](./descriptions.md)).
- **Path literals.** Every path literal in source — `import "..."`, `invoke("...", ...)`, and `.theta` entries inside `tools:` (see [Imports](./imports.md), [Invocation](./invocation.md), [Parameters and Frontmatter](./frontmatter.md)) — uses forward-slash separators only. A backslash inside a path literal is a parse error `theta/parse/invalid-path-separator`. (Path literals are otherwise ordinary string literals; `\\` already lowers to a single backslash via the standard escape table below, so the parse error is unambiguous — there is no "did the author mean an escape" interpretation.) Discovery roots and the `--theta <path>` CLI flag accept OS-native paths with no syntactic restriction; their resolved targets are compared in normalised forward-slash form for the discovery collision rule (see [Directory Convention](./discovery.md)).
- <a id="stray-backslash"></a>**Stray backslash.** A backslash byte at a source position that is not inside a string literal, path literal, or `@`...`` query-template body is a parse error `theta/parse/stray-backslash`. theta has no line-continuation marker (see [Grammar Appendix — Newline continuation](./grammar.md#newline-continuation)), so a backslash immediately preceding a newline at top level is this error, not a continuation.
- <a id="extension-matching"></a>**Extension matching.** The `.theta` and `.thetalib` file extensions are matched **byte-exact in lowercase ASCII** wherever they appear: in the discovery glob (`*.theta` per [Directory Convention](./discovery.md)), in path literals consumed by `import`, `invoke`, and `.theta` entries inside `tools:` (per the parse-time checks `theta/parse/import-non-thetalib-extension`, `theta/parse/invoke-non-theta-extension`, and the `tools:` `.theta`-path rule in [Parameters and Frontmatter](./frontmatter.md)), and in the settings/CLI extension check (`theta/load/invalid-extension` per [Directory Convention — `thetaPaths` entry schema](./discovery/package-and-settings.md#thetapaths-entry-schema)). No case-folding is performed at any of these sites: a file saved as `Plan.THETA`, an `invoke("./mod.THETA", ...)` literal, an `import { X } from "./lib.THETALIB"`, a `tools: [./helper.THETA]` entry, and a `thetaPaths` settings entry pointing at `foo.THETA` all behave identically across operating systems — the lowercase-extension check fails, regardless of whether the host filesystem is case-sensitive. The rule composes with the per-source case-collision rule on stems (see [Directory Convention — Case-insensitive filesystem collisions](./discovery.md)) without contradiction: `Plan.THETA` is not a `.theta` file at all, so the question of whether it collides with `plan.theta` does not arise.
- **Diagnostic spans.** BOM consumption and newline normalisation both happen *before* span recording, so diagnostic line/column numbers refer to logical lines on the normalised stream — column 1 of line 1 starts after the BOM, and a CRLF source line counts as one newline, not two.

**Identifiers.** `[A-Za-z_][A-Za-z0-9_]*`, case-sensitive. The **first letter's case is enforced** by the parser — it is what makes case-based pattern disambiguation in `match` work without additional grammar:

- **PascalCase** (uppercase first letter) is required for: `schema` names, `enum` names, `enum` variant names, and any user identifier introduced as a type-like binding. The built-in `Ok`, `Err`, and `Result` follow the same rule.
- **lowercase-first** (a lowercase letter, or `_`) is required for: `let` and `let mut` bindings, function parameters, function names, and schema field names. Both `snake_case` (`experience_years`) and `lowerCamelCase` (`experienceYears`) are accepted; the parser only cares about the first letter. The lowercase-first rule applies to the **theta-side** field identifier; the field's *wire* name (what appears in JSON sent to and received from the model) may be any string via the `as "WireName"` rename clause described in [Schema Declarations](./schemas.md), a schema-declaration-only clause the inline `Field` form does not admit.

Violating either rule is a parse error: `theta/parse/schema-case-mismatch` ("schema name must start with an uppercase letter") or `theta/parse/binding-case-mismatch` ("binding name must start with a lowercase letter or `_`"); see [Diagnostics](./diagnostics.md). Inside `match` patterns the same first-letter rule then disambiguates without ambiguity: a lowercase identifier introduces a fresh binding, an uppercase identifier refers to an existing schema, enum, or constructor in scope (see [Expression Sublanguage — Pattern grammar](./expressions.md#pattern-grammar)). The casing rule and the import-specifier synthesised-name reservation are the only enforced naming constraints; identifier length, internal casing, and underscore use are otherwise free. A parsed `import` / `export` specifier's local binding — the `as` alias where present, else the source name (see [Imports](./imports.md)) — MUST NOT match one of [Schema Subset — Synthesised names](./schema-subset.md#synthesised-names)'s four forms exactly: `__inline_<slug>`, `__theta_respond_<slug>`, `__theta_bind_<slug>`, or `__theta_callee_<slug>__<post-rename-name>`, with `<slug>` exactly 16 lowercase hex characters. The rule binds every parsed specifier on either statement kind, with or without a trailing `from` clause. A binding matching one of those forms is `theta/parse/import-reserved-synthesised-name`; the reservation is scoped to that one name-introducing position — a `schema` / `enum` declaration of the same name is already refused by the PascalCase rule above, at a different diagnostic.

**Reserved keywords.** Cannot be used as identifiers: `let`, `mut`, `fn`, `if`, `else`, `for`, `in`, `while`, `break`, `continue`, `return`, `match`, `schema`, `enum`, `import`, `export`, `from`, `as`, `by`, `invoke`, `true`, `false`, `null`, `Ok`, `Err`, `Result`, `string`, `number`, `integer`, `boolean`, `array`, `void`. Using one of these in identifier position is `theta/parse/reserved-keyword-as-identifier`. The discard binding `_` is also reserved (it is not a regular identifier and cannot be referenced after binding). `array` and `Result` remain reserved as identifiers, but double as the closed set of generic-type constructor keywords in type position: keeping them reserved is what stops them matching `NamedType ::= Ident`, while the generic-application production in [Grammar Appendix — Type grammar](./grammar.md#type-grammar) makes each reachable as a parameterised type.

**Statement terminators.** Statements are separated by newlines; semicolons are not part of the grammar. A statement implicitly continues across newlines only when the parser cannot otherwise close it — open `(` / `{` / `[`, a trailing binary or ternary operator, a trailing comma, or a leading binary or ternary operator on the next non-blank line. The continuation-trigger set is closed and is normatively tabulated in [Grammar Appendix — Newline continuation](./grammar.md#newline-continuation). **Blank lines do not break a continuation:** when a trigger holds, the parser continues across one or more newlines regardless of how many of them are blank (`let x =\n\n  foo` is one statement equivalent to `let x = foo`). The same rule means single-line `if (x) stmt` does not exist; bodies of `if` / `for` / `while` / `fn` are always braced blocks. Violations are `theta/parse/single-line-if`.

**Comments.** Line comments only. `//` is a regular comment; `///` is a doc comment that lowers to a JSON Schema `description:` (see [Descriptions](./descriptions.md)). Block comments (`/* ... */`) are not supported and surface as `theta/parse/block-comment`. Comments inside the *text* of a `@`...`` query template are not comments — they are part of the rendered prompt. Comments inside a `${...}` interpolation behave exactly as in any other expression position.

<a id="string-literals"></a>**String literals.** Single- (`'...'`) and double-quoted (`"..."`) forms are equivalent. Escape sequences: `\"`, `\'`, `\\`, `\n`, `\t`, `\r`, `\u{XXXX}` (Unicode scalar value, 1–6 hex digits). The escaped value `v` is well-formed iff `v ≤ 0x10FFFF` and `v` is outside the UTF-16 surrogate range `0xD800`–`0xDFFF`; a recognised `\u{...}` form whose value is out of range or names a surrogate is `theta/parse/invalid-unicode-escape`. A backslash followed by any other character is `theta/parse/illegal-escape`. EOF inside an unterminated string literal is `theta/parse/unterminated-string`. **Single-line only** — a literal newline inside a regular string is `theta/parse/literal-newline-in-string`. **No interpolation** — the sequence `${` inside a regular string is plain text. Multi-line text and interpolation belong inside `@`...`` query templates; for non-query multi-line text, build via `+` concatenation with `\n` escapes, or factor the text into a query.

**Number literals.** Decimal only: `42`, `3.14`, `1e10`, `1.5e-3`, `0`, `0.5`. The literal carries no sign — negation is the unary `-` operator applied at parse time. No hex / octal / binary forms and no underscore separators in theta 1.0 (those forms surface as `theta/parse/unsupported-feature`). See [Future Considerations](./future-considerations.md). A literal with no fractional or exponent part has type `integer`; otherwise `number`. `integer` widens implicitly to `number` in arithmetic and assignment positions; the reverse is `theta/parse/integer-narrowing`. The magnitude of a number literal is judged on each lexed token individually, before the parse-time unary-`-` fold (per the no-sign rule above): an `integer`-typed literal token whose value exceeds the safe-integer range (`|value| > 2^53 - 1`) is `theta/parse/integer-literal-out-of-range`, and a `number`-typed literal token whose parsed value is not a finite IEEE-754 double (e.g. `1e400`, which would otherwise parse to `Infinity`) is `theta/parse/number-literal-not-finite`. Both reject at parse time rather than silently rounding to the nearest representable double or yielding `Infinity`, consistent with the `theta/parse/integer-narrowing` treatment of `integer`/`number` boundary violations. Because the bound is per-token, `-12345678901234567890` is rejected — the unary `-` does not bring the magnitude back into range — whereas an out-of-range value reached only through arithmetic on in-range literals is governed by the runtime `number` rules in [Expressions](./expressions.md), not by this parse-time rule.
