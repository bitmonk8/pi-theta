# Frontmatter fields a

```yaml
---
description: Programmatic, parameterised code review
argument-hint: "<language> <focus_areas...>"
mode: subagent              # prompt | subagent
model: claude-sonnet-4-5    # model used for every query in this theta
bind_model: claude-haiku    # model used to bind slash-command args to params (default: theta.binderModel in settings.json)
bind_context: none          # none | session — see Slash-Command Argument Binding
bind_echo: true             # echo bound args before execution (default: true)
tools: read, grep, bash     # tools available to the model during query-time tool loops
system: |                   # system prompt for the conversation (subagent-only)
  You are an expert ${language} reviewer.
  Reviewer context: ${author.name} (${author.role}, ${author.experience_years}y).
respond_repair:
  attempts: 3                  # max respond-repair follow-ups per typed query (default: 3)
  methodology: validator_error # how to phrase respond-repair turns (default: validator_error)
tool_loop:
  max_rounds: 25               # max free-phase tool-call rounds per query; the typed-query forced respond turn is exempt (default: 25)
params:
  language: string
  focus_areas: array<string>
  author: Author
---
```

### Field contract

The table below is normative: for each recognised theta 1.0 field it pins down whether the field is required, what the runtime substitutes when the field is absent, and what observable behaviour the absent case produces. Fields not listed here are not part of the theta 1.0 vocabulary and surface as `theta/load/unknown-frontmatter-field` (or `theta/load/deferred-frontmatter-field` for reserved names); see [Diagnostics](../diagnostics.md).

**Unknown-key policy.** Unknown keys at the top level of the frontmatter mapping are tolerated for forward compatibility: they are ignored at the value level (the runtime does not propagate them into `params`, the binder, or any other surface) and surface as a single warning per key — `theta/load/unknown-frontmatter-field` for unrecognised keys, or `theta/load/deferred-frontmatter-field` for keys reserved for deferred theta 1.0 features named in [Future Considerations](../future-considerations.md). The theta continues to load and register in both cases. The current theta 1.0 vocabulary is the table below; future minor versions extend it additively. The warning-not-error posture is deliberate: an author who hand-edits frontmatter to set a key from a newer theta minor than the runtime supports must still see their theta load (with a visible warning), so that downgrading the runtime never silently breaks slash commands. The seam is what allows the deferred `binder_temperature` and user-overridable binder-prompt extensions in [Future Considerations](../future-considerations.md) to land additively without a frontmatter-schema bump.

| Field | Required? | Default when absent | Behaviour when absent |
|---|---|---|---|
| `mode` | yes | — | `theta/load/missing-mode` load-time error; the theta is not registered. An unrecognised value (e.g. `mode: agent`) is the separate `theta/load/unknown-mode-value` — "missing" and "present-but-bad" do not collapse into one code, because the authoring intent differs. |
| `description` | no | `null` | The slash-command entry registers without description text; the binder prompt omits the `Description:` line. No warning — internal-only thetas legitimately omit this. |
| `argument-hint` | no | `null` | The binder prompt omits the `Argument hint:` line; no autocomplete surface exists for the field in theta 1.0 (Pi's extension-registered commands have no `argumentHint` slot; the owning definition of the autocomplete contract is the [`argument-hint` autocomplete contract](#argument-hint-binder-only) prose below). Declaring `argument-hint` without `description` emits the advisory `theta/load/argument-hint-not-displayed` so authors are not surprised by an empty-looking dropdown entry. Legal even when `params:` is non-empty; the binder simply has one fewer grounding signal. |
| `model` | no | Pi session's model at invocation time | The theta inherits the caller's model at invocation time and pins it for the duration of that one invocation; a later invocation of the same theta re-inherits the session model afresh, so a session-model change between two invocations is observed. Documented in the `model` prose below. A present `model:` value that resolves to no available model (a non-string scalar, a malformed reference, a reference matching no available model, or a bare `modelId` ambiguous across providers) is the load-time error `theta/load/model-unresolved` and the theta is not registered — "absent" and "present-but-unresolvable" do not collapse into one behaviour, because the absent case has no load-time registry call. In `mode: subagent`, if the inherited model is itself `undefined` at invocation time (frontmatter `model:` absent and no session model to inherit), the spawn is refused per the [Pre-spawn model guard](../pi-integration-contract/subagent.md#subagent-pre-spawn-model-guard). |
| `bind_model` | no | `theta.binderModel` setting (no further fallback) | Slash-command argument binding uses the fallback model. When neither `bind_model:` nor `theta.binderModel` resolves and the theta is not [bypass-eligible](../binder/binder-bypass-and-envelope.md#binder-bypass), load fails with `theta/load/binder-model-unresolved`. The configured string is matched to a model per the [binder-model parse rule](../binder/binder-model-and-context.md#binder-model-parse-rule). The resolved model is then run through the three-valued [strict-capability requirement](../binder/binder-model-and-context.md#strict-capability-requirement): an explicit `false` strict-capability indicator fails the load with `theta/load/binder-model-not-strict-capable` (E), while an absent indicator (absent on every Pi-supplied `Model<Api>` under the theta 1.0 Pi-SDK pin, gated per [PIC — Strict-capability absence under the pin](../pi-integration-contract/audit-target-categories.md#strict-capability-absence-pin)) emits `theta/load/binder-model-strict-capability-unknown` (W) and the theta still registers. The load-time refusal above does not apply to the marked root theta of a spawned subagent child; see the [subagent-root exemption](../binder/binder-model-and-context.md#binder-model-subagent-root-exemption). Documented under [Slash-Command Argument Binding](../binder.md). |
| `bind_context` | no | `none` | The binder runs with no caller-session context; documented under [Slash-Command Argument Binding — Binder context](../binder.md). A present value other than `none` or `session` (including non-string scalars) is the separate `theta/load/unknown-bind-context-value` load-time error and the theta is not registered — mirroring the `mode:` recognised-key / unrecognised-value split. |
| `bind_echo` | no | `true` | Bound args are echoed before execution, except auto-suppressed on the binder bypass; documented under [Slash-Command Argument Binding — Echo policy](../binder.md). |
| `tools` | no | empty callable set | The model cannot make tool calls and theta code has no `<name>(...)` callables; documented in the `tools` prose below. `tools: []` and an absent `tools:` field are equivalent, both yielding the empty callable set; a value outside the two admitted spellings (a mapping, an alias, or a key with no value node — only `? tools` and a flow-mapping `{tools}` carry no value node; a bare `tools:` parses as a null scalar and keeps `theta/load/unknown-tool`) is `theta/load/malformed-tools-field` and the theta does not register — "absent" and "present-but-the-wrong-shape" do not collapse into one behaviour. The same refusal covers any `tools:` scalar whose comma split yields no entry, in whatever YAML style — the quoted short form (`tools: ""`, `tools: " , "`), a block scalar over commas or blank content, and a plain scalar an explicit tag carries to the empty string (`tools: !!str`): the field is an admitted spelling that declares nothing, not the equivalent-to-absent `tools: []`. An UNTAGGED plain scalar does not reach this rule — an empty or whitespace-only one parses as a null scalar and keeps `theta/load/unknown-tool` instead, and a comma-leading one is a YAML parse error. |
| `system` | no | no system prompt (the spawned conversation runs under the model's training defaults) | Subagent-mode only; presence on a `mode: prompt` theta is `theta/parse/system-on-prompt-mode`. Documented under the `system` prose below. |
| `respond_repair` | no | `{ attempts: 3, methodology: validator_error }` | Typed queries get the default respond-repair budget; documented under the `respond_repair` prose below. `respond_repair: {}` (block present, sub-keys absent) is equivalent to omitting `respond_repair:` entirely; the defaults apply. |
| `tool_loop` | no | `{ max_rounds: 25 }` | Every query (untyped, typed, and any respond-repair follow-up) runs its tool-call loop under the default cap; documented under the `tool_loop` prose below. `tool_loop: {}` (block present, `max_rounds` absent) is equivalent to omitting `tool_loop:` entirely; the default `25` applies. |
| `params` | no | no parameters | The theta takes no parameters; the binder does not run regardless of how the theta is invoked. Slash-argument overflow against a no-params theta is governed by [Slash-Command Invocation — No-params overflow](../slash-invocation.md#slsh-1) (cross-referenced from [Slash-Command Argument Binding](../binder.md)). `params:` absent and `params: {}` are equivalent; the redundant `params: null` is `theta/load/params-null` (use absent or `{}` instead). An explicit `bind_echo: true` on a no-params theta is `theta/load/bind-echo-without-params` (warning) and produces no echo regardless. |

`mode:` is the only required field. The blast-radius asymmetry between `prompt` (turns inject into the user's live Pi session) and `subagent` (a private spawned conversation) is exactly the kind of decision that must not be silent: defaulting one way would either route private thetas into the user's session or vice versa, and there is no implementer-neutral choice. An explicit-only rule also lets every load-phase enforcement point (the slash-command entry, frontmatter parsing, and subagent spawn) converge on the same diagnostic.

<a id="argument-hint-binder-only"></a>Frontmatter mirrors Pi's prompt-template frontmatter (`description`, `argument-hint`) plus theta-specific fields. The two shared fields are not behaviourally identical to Pi's prompt-template versions: `description` populates the autocomplete entry as expected, but `argument-hint` is currently used internally only (binder grounding) because Pi's `RegisteredCommand` API has no `argumentHint` slot for extension-registered commands — the field exists only on Pi's built-in `.md` prompt templates. The autocomplete dropdown therefore shows only the registered `description`; authors who want hint-like text visible in the dropdown must include it in `description:`. This extension-API gap is tracked in [Future Considerations](../future-considerations.md). This paragraph is the owning definition of the `argument-hint` autocomplete contract; [Slash-Command Invocation](../slash-invocation.md) and [Pi Extension Integration](../pi-integration.md) forward-link here rather than restating it.

**Naming convention.** `description` and `argument-hint` retain Pi's prompt-template spellings verbatim — Pi's loader keys off the literal YAML string `argument-hint`, so theta inherits the hyphen unchanged rather than forking the spelling or maintaining a second alias. Every theta-defined multi-word field uses underscore separators instead (`bind_model`, `bind_context`, `bind_echo`, `tool_loop`, and the nested `*.max_rounds` / `*.attempts` / `*.methodology` keys). A frontmatter key of `argument_hint:` is therefore unrecognised and surfaces as `theta/load/unknown-frontmatter-field` (the theta still registers, but no `Argument hint:` line reaches the binder grounding payload). **No `name` field** — the filename is canonical, exactly as for Pi prompts (`code-review.theta` is invoked as `/code-review`); see [Discovery — Filename validity](../discovery.md) for the accepted stem regex and the `theta/load/invalid-slash-name` rejection rule. Frontmatter fields outside the theta 1.0 vocabulary surface as `theta/load/unknown-frontmatter-field` (warning); fields reserved for deferred theta 1.0 features surface as `theta/load/deferred-frontmatter-field` (warning). Both keep loading the theta; see [Diagnostics](../diagnostics.md). For the binder-model concept's root-word convention across frontmatter, settings, diagnostic, anchor, and prose surfaces, see the [*Binder-model root-word convention*](#binder-model-root-word-convention) sub-paragraph.

<a id="binder-model-root-word-convention"></a>**Binder-model root-word convention.** The binder-model concept uses the short root `bind_` in its frontmatter field name (`bind_model`) and the long root `binder` in its settings key (`theta.binderModel`), diagnostic codes (e.g. `theta/load/binder-model-unresolved`), section anchors (e.g. `## Binder model` in [Slash-Command Argument Binding](../binder/binder-model-and-context.md#binder-model)), and running prose ("binder model").

- `params` are validated with AJV at invocation time and exposed as typed variables in the theta body. When invoked from a slash command, the runtime binds free-form slash arguments to `params` via an LLM call (see [Slash-Command Argument Binding](../binder.md)); when invoked from `invoke(...)` or as a registered tool, arguments arrive already typed and are validated directly.
  - **Type side.** Each `params:` field's right-hand side is a type expression parsed by the theta type grammar — the same grammar used in every other type-annotation position (see [Type System](../type-system.md) and [Grammar Appendix — Type grammar](../grammar.md#type-grammar)). A `NamedType` on the right-hand side (e.g. `Author`, `Severity`) resolves against the file's body-level `schema` / `enum` declarations and any symbols imported from `.thetalib` files. Resolution is whole-file: a forward reference from frontmatter to a `schema` or `enum` declared later in the body resolves, because — although frontmatter is parsed before the body — name resolution runs once the file's top-level declarations are all known. A `params:` named type that resolves to no such declaration is the parse-time diagnostic `theta/parse/unresolved-named-type`. The type expression is inline text, not a YAML structure: a field whose YAML value is neither a scalar nor a flow mapping — a block mapping or a block sequence nested under the field name, a flow sequence, an alias or any other node kind, or no value node at all (an explicit key `? p`, or a value-less entry in a flow-mapping `params:` such as `params: {p}`) — declares no type expression and is the load-time diagnostic `theta/load/params-type-not-expression`, and the theta is not registered. A value-less key written `p:` (or `params: {p: }`) parses as a null scalar and is admitted. A type text whose first character is a quote character (`"` or `'`) must itself be spelled as a quoted YAML scalar — the authored form is `p: '"a" | "b"'` — because the unwrapped spelling `p: "a" | "b"` is not valid YAML and refuses the whole frontmatter block with `theta/load/malformed-frontmatter-yaml` rather than reaching the type-expression judgement described above. The inline object type (`{a: Triage}`) is a YAML flow mapping and is admitted. A scalar's recovered text must itself spell a `Type`, and the unit judged is each fragment of that text the source itself spells, rather than the right-hand side as a whole: a fragment is judged at the type's own top level, inside a union arm at any depth, inside a generic type argument, and inside an inline object type's field type at any depth, because hoisting an inline object lowers every field it declares through the same per-field path. Excluded from that judged set is a fragment the generic type argument's own split MANUFACTURES by cutting a `{...}`/`[...]` group the author wrote as one unit — `array<{a: string, b: integer, c: boolean}>`'s middle shard, `b: integer`, is one field of an object type the split cut in two, not a fragment the source spells on its own, and reaches no judgement. That exclusion is per SEGMENT of the split, not per argument list: a segment both of whose delimiting comma boundaries sat at `{...}`/`[...]` depth 0 and whose own groups balance is whole in the source and keeps its judgement, so `p: 'array<{a: string, b: integer, c: boolean}, ???>'` refuses the field on the whole argument `???` beside three pieces it does not judge. Junk the author did write is UNDER-refused in the other direction, deliberately: when a manufactured shard carries it, nothing is drawn — `p: 'array<{a: Cat +, b: integer, c: boolean}>'` and `p: 'array<{a: string, b: integer, c: boolean} | Cat +>'` are admitted, because the fragment carrying `Cat +` is a piece cut out of the brace group rather than text the source spells on its own. A fragment that every admitted form — a primitive, a `NamedType`, a `GenericType`, an inline object type, or a literal — has been tried on and declined is the same load-time diagnostic, `theta/load/params-type-not-expression`: text carrying a YAML mapping or sequence shape, prose, punctuation, a comment-shaped text, two space-separated identifiers, or an empty or whitespace-only string, whatever quoted or block-scalar spelling delivers it and at whatever depth it sits — `p: 'a: Tirage'`, `p: 'string | a: Tirage'`, `p: 'array<a: Tirage>'`, `p: '{a: ???}'` and `p: '{a: {b: ???}}'` are one refusal each. Literal-shaped text — recognised by the same literal recogniser the right-hand side's default half uses — is exempt, and so is every fragment carrying a `{` or `}` PROVIDED that fragment carries no string literal that never closes ([bug 0232](../../bugs/0232-unterminated-literal-params-type-drops-inline-fields.md) §Fix (b)): the brace frame owns the brace-carrying fragments whose quotes all close, and this rule owns the brace-free ones plus a brace-carrying fragment whose own string literal is left open (`{a as "w: integer}` — the author's own braces balance, but the wire-name literal never closes; the narrowing is asked of the fragment's WHOLE recovered text, so a nested (`{q: {a as "w: integer}}`) or generic-argument (`array<{a as "w: integer}>`) spelling is refused too), so a fragment reaching the judgement whole with a brace in it and every quote closed — `{junk}`, the unterminated-BRACE `{a: string` (a genuinely unbalanced brace group carrying no unterminated literal), and an inline object type nested in a generic argument or a union arm (`array<{a: ???}>`, `string | {a: ???}`) — keeps its own (possibly permissive) lowering. The exemption is the fragment's own and not its enclosure's: a brace-free fragment reached through a hoisted inline object's field type is refused like any other. A field already carrying an error-severity diagnostic of its own — a reserved keyword, an unresolved name, or the node-shape refusal above — draws no text-level diagnostic on top of it, and a field refused this way draws none of its own default's literal-sublanguage diagnostics either.
- `bind_model`, `bind_context`, and `bind_echo` configure slash-command argument binding. All three are optional with sensible defaults; see [Slash-Command Argument Binding](../binder.md).
  - **Defaults.** A param may declare a default with `field: type = literal`. The RHS is parsed by the **Theta literal sublanguage** — the same notation Theta uses for value construction in body code, restricted to the production set normatively defined in [Grammar Appendix — Theta literal sublanguage](../grammar.md#theta-literal-sublanguage). Primitive literals (including unary-`-` on numeric literals), `null`, array literals, bare-key object literals (the param's declared type supplies the schema), `Enum.Variant` access, and variant-schema construction (`Cat { ... }`) are all admitted. Operators, function calls, identifier references other than `Enum.Variant`, `${...}` interpolation, and `@`...`` query templates are not; violations are `theta/parse/default-not-literal` and the diagnostic names the offending sub-expression. `theta/parse/default-not-literal` owns exactly the shape violations enumerated above; `NamedValueLit`'s tail condition — the tail is a declared variant — is a name-resolution condition, not shape, so an undeclared variant of a declared enum draws the body expression grammar's own code here instead, `theta/parse/unknown-variant`. The head condition — head is an enum name in scope — splits on what the head resolves to: a head that resolves to nothing leaves the intended form undetermined and is the same name-resolution code, `theta/parse/unknown-identifier`; a head that resolves to a declaration that is not an enum determines the form completely — the RHS is an identifier reference that is not an `Enum.Variant` access, one of the shape violations already enumerated — and is `theta/parse/default-not-literal`. An RHS that is empty or whitespace-only after trim admits no arm of `Literal` at all and is `theta/parse/default-without-literal`, naming the field. A string literal's raw line break is refused the same way body code refuses one — `theta/parse/literal-newline-in-string`; use the `\n` escape, or move the value into body code. The RHS must close every string literal it opens; one that never closes spells no `Literal` and is refused too — `theta/parse/unterminated-string`, ranged on the offending field. When a slash-command invocation omits the corresponding positional argument, the default is filled in before AJV validation. The default literal's static type must be compatible with the param's declared type per [Type System — Type compatibility](../type-system.md#type-compatibility) (e.g. an `integer` literal is admissible for a `number` param; the reverse is `theta/parse/integer-narrowing`; any other incompatibility is `theta/parse/params-default-type-mismatch`). The same default-vs-non-default partition is what `invoke(...)` and `.theta` callable calls use to compute argument arity — see [Invocation — Argument arity](../invocation.md#argument-binding) for the parse-time vs runtime split. To keep that positional binding unambiguous, no non-defaulted field may follow a defaulted field in `params:` declaration order; a `params:` list that places a non-defaulted field after any defaulted field is `theta/parse/non-trailing-default`, and the diagnostic names the first offending non-defaulted field. Defaults are the only place where literal-valued defaulting exists in theta 1.0; schema field declarations do not support defaults (JSON Schema's `default:` is advisory metadata, not provider-enforced, and would mislead authors about what the model emits).

    ```yaml
    params:
      language: string = "TypeScript"
      focus_areas: array<string> = []
      author: Author = { name: "anon", role: "developer", experience_years: 0 }
      severity: Severity = Severity.Medium
      pet: Animal = Cat { name: "Whiskers" }
    ```

    Because the literal sublanguage *is* a subset of the body expression grammar, `Enum.Variant` defaults preserve the runtime enum brand (see [Runtime Value Model](../runtime-value-model.md)): no *separate* restoration pass exists, and the tag is re-established by the binder-`args` inbound boundary the runtime already runs on every inbound record. Discriminated-union variant defaults are written via the variant schema name (`Cat { ... }`) just as they are in body code — there is no second "wire-form" dialect for authors to learn.
- `model` and `tools` follow the same shape as Pi subagent frontmatter and apply to **every** query in the theta — a single theta file shares one model and one callable set across all of its turns.
  - **`model`**: if frontmatter omits `model`, the theta inherits Pi's session default at invocation time (no load-time registry call). The inherited model is fixed for the duration of that one invocation and does not re-resolve per query within that invocation; a later invocation of the same theta re-inherits `ctx.model` afresh, so a session-model change between two invocations is observed. A *present* `model:` value is resolved at theta-load time via the [binder-model parse rule](../binder/binder-model-and-context.md#binder-model-parse-rule) (theta's own exact-match resolution over the available models from `ctx.modelRegistry.getAvailable()`); a non-string scalar, a malformed reference, a reference that matches no available model, or a bare `modelId` ambiguous across providers fails to load with `theta/load/model-unresolved` and the slash command is not registered.
  - <a id="tools"></a>**`tools`**: declares the theta's **callable set** — a unified list of Pi tools and `.theta` paths, callable from both the model (during a query's tool-call loop) and from theta code (via the bare `<name>(...)` call form; see [Tool Calls](../tool-calls.md)). If frontmatter omits `tools`, the theta runs with an **empty callable set** (the model cannot make tool calls and theta code has no `<name>(...)` callables to resolve). The Pi session's ambient tools are deliberately *not* inherited — tools have side effects, and silent inheritance produces "why did my theta touch the filesystem?" surprises. To opt in, list each callable explicitly. `tools: []` and an absent `tools:` field are equivalent, both declaring the empty callable set silently; a `tools:` value that is neither the comma-separated short form nor a YAML sequence — a mapping (flow or block, including the empty flow mapping `tools: {}`), an alias, or a key carrying no value node at all — is `theta/load/malformed-tools-field` and the theta does not register. The same code refuses a `tools:` value that IS the comma-separated short form but whose comma split yields no entry, in whatever YAML style the author reached for: the quoted spellings (`tools: ""`, `tools: " , "`), a block scalar over a lone comma or blank content, and a plain scalar an explicit tag carries to the empty string instead of to null (`tools: !!str`, `tools: !<tag:yaml.org,2002:str>`, either of those under an anchor). The field is present and declares nothing, which is a distinct authoring intent from `tools: []` or an absent field. Two neighbouring plain spellings stay outside the rule: an UNTAGGED empty or whitespace-only plain scalar parses as a null scalar and keeps `theta/load/unknown-tool`, and a comma-leading plain scalar — tagged or not — fails YAML parsing outright, taking `mode:` down with the block. An alias never reaches the split at all: it is refused one step earlier by the same code on its node kind. The runtime mechanism that *enforces* the no-inheritance rule (the explicit `--tools` host-tool allowlist / `--no-tools` on the spawned child `pi` process for subagent mode; `pi.setActiveTools` snapshot/restore around each query for prompt mode) is specified in [Pi Integration Contract — Tool-registration lifetime and visibility](../pi-integration-contract.md).

    Two kinds of entry are accepted:

    - **Pi tool names** (`read`, `bash`, `grep`, ...) resolve against Pi's tool registry at theta-load time, exactly as for Pi subagents. The registry snapshot is `pi.getAllTools()`, so a name an installed extension registered (`finding_store`, `projection`, …) resolves on the same footing as a host built-in — the list above is an open example, not a fixed set — in **both** prompt mode and subagent mode. Each resolved entry carries the tool's `parameters` schema (enough for the RFC-0002 argument/field disjointness check and the model tool spec). A `tools:` **Pi-tool-name** entry (a bare name, not a `.theta` path) that names neither a host built-in nor an entry in the registry snapshot fails load with `theta/load/unknown-tool` and the theta is not registered — the same rule in prompt and subagent mode. How each admitted name reaches the model and theta code is mode-specific: the model-facing and code-side reach of an extension-supplied Pi tool is pinned in [Pi Integration Contract — Code-side extension-tool dispatch (PIC-64)](../pi-integration-contract/subagent.md#pic-64) and the [Resolution snapshot](./frontmatter-fields-b-and-templates.md#resolution-snapshot).
    - **`.theta` paths** (`./summarise.theta`, `../shared/classify.theta`) resolve relative to the calling theta's directory, use forward-slash separators only (a backslash is a parse error per the "Path literals" rule in [Lexical Structure](../lexical.md)), must end in `.theta` — the extension match is byte-exact lowercase per [Lexical — Extension matching](../lexical.md#extension-matching) (otherwise `theta/parse/invoke-non-theta-extension` for the parse-time literal check, or `theta/load/unresolvable-theta-path` for a literal that ends in `.theta` but resolves to no file) — and must point at **subagent-mode** theta files — a prompt-mode callee in `tools:` is `theta/load/prompt-mode-callable` (interleaving the child's user turns inside a parent's tool-call loop is a semantic mess that theta 1.0 rejects outright).

    Each entry is exposed under a single name in the theta's top-level scope (and to the model as a tool of the same name). Naming rules:

    - For a Pi tool, the entry's name is the Pi tool name verbatim. That verbatim name IS the presented name, so it must itself obey the lowercase-first identifier rule; a registry name outside that rule is `theta/load/invalid-pi-tool-name`, remedied by an `as <name>` clause (a host tool has no file to rename), judged before the collision rule in the bullet below.
    - For a `.theta` path, the default name is the file's basename without the `.theta` extension, with **hyphens replaced by underscores** (`./code-review.theta` → `code_review`). The remap exists because theta-file naming convention favours hyphens while theta identifiers must be lowercase-first identifier-shaped. A derived name outside that rule is `theta/load/invalid-derived-tool-name` (`./2fast.theta` → `2fast`), remedied by renaming the file or adding an `as <name>` clause; the check is judged before the collision rule in the bullet below, so a derived-name rejection is never reported as a collision.
    - The `as <name>` clause overrides the default for either kind: `read as file_read`, `./summarise.theta as my_summariser`. The override target must obey theta's lowercase-first identifier rule (`./summarise.theta as MyTool` is `theta/load/invalid-tool-rename`).
    - Two entries resolving to the same final name are `theta/load/tool-name-collision`; use `as` to disambiguate. A name that collides with a top-level `fn` declaration or an imported symbol in the same file is also `theta/load/tool-name-collision`.

    The per-entry grammar is closed: an entry is exactly a Pi tool name or a `.theta` path, optionally followed by an `as <name>` clause. Any other token sequence in an entry, and any `tools:` sequence item that is not a YAML scalar, is `theta/load/malformed-tool-entry` and the theta does not register.

    <a id="frnt-2"></a> **FRNT-2.** *Callable-set terminology.* Authors and implementers MUST use the term `callable set` (or, with an explicit scoping modifier, `frontmatter callable set` / `theta's declared callable set`) for the per-theta resolved tool list; the bare phrases `tools: set`, `tool set`, `theta's tools`, and `available tools` are spec-prose synonyms to be avoided because they erode the no-inheritance invariant. The one distinct concept that does use the bare phrase `ambient tool set` is the host Pi session's tools, which a callable set deliberately excludes.

    <a id="frnt-3"></a> **FRNT-3.** *`.theta`-callable terminology.* Authors and implementers MUST use the canonical term `.theta callable` (or, in running prose, `` `.theta` callable ``) for a `.theta` entry in `tools:`; the synonyms `registered theta`, `registered subagent theta`, `registered-theta call`, and `theta callee` are spec-prose drift to be avoided. The rename does NOT affect any code identifiers, file extensions, diagnostic codes, frontmatter field names, or wire formats — it is purely terminology.
