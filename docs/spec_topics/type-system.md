# Type System

The type system is JSON-native. Type expressions are built from:

- **Primitive types**: `string`, `number`, `integer`, `boolean`, `null`
- **Named types**: any schema or enum identifier in scope (`Author`, `ReviewScore`)
- **Generic types**: `array<T>`, `Result<T, E>` (and any future parameterised type) — angle-bracket type parameters are the uniform Theta convention
- **Union types**: `T | U | ...` — the `|` operator is the lowest-precedence type operator and is legal anywhere a type is
- **Literal types**: `"..."`, `42`, `true`, `false`, `null` — string, number, and boolean literals are valid type expressions (single-arm "unions" are how `kind: "validation"`-style const fields are expressed)
- **Inline anonymous objects**: `{ field: T, ... }` — legal in any type position, but named schemas are preferred for reuse and for getting a name in error messages
- **Inline arrays**: not a separate form — use `array<T>` (no `T[]`, no `[T]`)

`void` is **not** a primitive value type and is deliberately absent from the list above: it is admitted only as a function- or theta-**return** annotation meaning "intentionally produces no value", never in a value-bearing type position (see [Grammar Appendix — Type grammar](./grammar.md#type-grammar) and [Function Definitions — Empty-tail body](./functions.md#empty-tail-body)). A `void` in any other type position is `theta/parse/void-in-non-return-position`, and `void` does not participate in type compatibility ([below](#type-compatibility)).

The same type grammar applies in every type-annotation position: schema fields, frontmatter `params:`, `let x: T`, function parameters, and `@<T>`...`` explicit query schemas; the function- and theta-return position additionally admits the return-only `void` annotation. Text that derives from none of the forms above is refused at load or parse time rather than admitted as a nominal reference: `theta/parse/annotation-type-not-expression` at a `let` annotation, an `fn` parameter type, or an `fn` return type; `theta/parse/schema-type-not-expression` at a schema field or a `schema X = ...` alias/union arm; `theta/load/params-type-not-expression` at a `params:` field; `theta/parse/query-annotation-type-not-expression` at an author-written `@<T>`...`` explicit query schema.

Subsections of the type system are split into their own pages:

- [Schema Declarations](./schemas.md) — `schema X { ... }`, `schema X = ...`, `enum`, discriminated unions, recursion, wire-name renaming.
- [Descriptions](./descriptions.md) — `///` doc comments and field separator rules.
- [Schema Subset](./schema-subset.md) — the JSON-Schema subset Theta targets, plus the lowering algorithm.

## Type compatibility

Wherever the spec asks whether a value of static type `T₁` may be used in a position that expects type `T₂` — the RHS of a typed `let`, a function-argument slot, an `invoke<T>` return annotation, the common type of `match` arms or ternary branches, an `array<T>` element against its sink, the `+` operator's mixed-numeric case, a frontmatter `params:` default, a schema-constructor field value against its declared field type, or a reassignment RHS against the target binding's declared or inferred type — the answer is governed by the single relation `T₁ ⊑ T₂` (read "`T₁` is compatible with `T₂`"). The relation is normative; every site that previously phrased itself as "the same rules as `let`" or "a common type" cites this section by anchor.

**Operational definition.** Whenever `T₁ ⊑ T₂` holds, every value statically typed as `T₁` AJV-validates against the lowering of `T₂` (see [Schema Subset — Lowering Algorithm](./schema-subset.md#lowering-algorithm)); AJV-validation is thus a *necessary* condition for compatibility, not a sufficient one. The AJV reading is the safety net at runtime; the parser is required to recognise the structural cases enumerated below without falling back to it, so that compatibility failures surface as parse errors at the offending source span rather than as runtime validation errors at a downstream call site. Because object-schema named types are nominal ([TYPE-10](#type-10)), the parser admits *fewer* pairs than AJV alone would: a pair the parser rejects is `T₁ ⋢ T₂` even when the two lowered fragments are AJV-interchangeable (e.g. a named schema and an inline object with identical fields). The parser's rejection is authoritative; AJV admitting the lowered pair at runtime does not retroactively make the pair `⊑`.

**Structural cases the parser must recognise.** The following hold without invoking AJV. The list is closed for V1 — anything outside it that the parser cannot decide statically is reported as a type mismatch (`theta/parse/*-type-mismatch` at the call site, e.g. `theta/parse/invoke-return-type-mismatch`, `theta/parse/invoke-arg-type-mismatch`, `theta/parse/array-element-type-mismatch`, `theta/parse/match-arm-type-mismatch`), unless the position is one where a runtime AJV check is documented as the safety net (e.g. an `invoke` against a callee that is not statically resolvable). The *Unresolvable operands* paragraph below takes precedence over the type-mismatch disposition of this sentence when either side is past the parser's static view.

| ID | Rule | Notes |
|---|---|---|
| <a id="type-1"></a> **TYPE-1.** | Reflexivity: `T ⊑ T` for every type. | Identical primitives, identical named schemas, identical inline objects. |
| <a id="type-2"></a> **TYPE-2.** | `integer ⊑ number`. | One-way only; the reverse is `theta/parse/integer-narrowing` (see [Lexical — Number literals](./lexical.md)). |
| <a id="type-3"></a> **TYPE-3.** | Literal-to-primitive: `L ⊑ T` when `L` is a literal type and the value `L` would be statically typed `T` in expression position. | E.g. `"validation" ⊑ string`, `42 ⊑ integer`, `42 ⊑ number`, `true ⊑ boolean`, `null ⊑ null`. |
| <a id="type-4"></a> **TYPE-4.** | Variant-to-union: for any discriminated union `schema U = A \| B \| ...`, every variant satisfies `A ⊑ U`. | The "narrower callee under wider annotation" case (`Cat ⊑ Animal`). |
| <a id="type-5"></a> **TYPE-5.** | Union-widening: `T ⊑ T \| U` for any `U`. | Combined with [TYPE-4](#type-4), `A ⊑ A \| B` even when the union is anonymous. |
| <a id="type-6"></a> **TYPE-6.** | Union-distributive: `T₁ \| T₂ ⊑ T₃` iff `T₁ ⊑ T₃` and `T₂ ⊑ T₃`. | Each arm must individually satisfy the target. |
| <a id="type-7"></a> **TYPE-7.** | Element-wise on arrays: `array<T₁> ⊑ array<T₂>` iff `T₁ ⊑ T₂`. | Covariant — `array<Cat> ⊑ array<Animal>`. Already implied by the array-LUB rule in [Expressions — array construction](./expressions.md#object-construction-array-construction-and-operator-rules); restated here so it can be cited from non-array sites. |
| <a id="type-8"></a> **TYPE-8.** | Field-wise on inline object types: an inline object type (`ObjectType`, `{ f₁: T₁, ... }`; see [Grammar — Type grammar](./grammar.md#type-grammar)) is `⊑` another inline object type with the same declared field set `{ f₁: U₁, ... }` iff `Tᵢ ⊑ Uᵢ` for every `i`. This rule covers inline object types only; a `NamedType` resolving to an object schema is nominal — see [TYPE-10](#type-10). | Field sets must match exactly: every Theta-lowered object schema carries `additionalProperties: false` (see [Schema Subset](./schema-subset.md)), so excess properties never widen — there is no TS-style structural-subtyping admission of extra fields, and an object with even one extra declared field is not compatible. Field order is irrelevant. The field-wise admission here never crosses the inline/named boundary: name identity governs named schemas ([TYPE-10](#type-10)). |

Rules outside this list are deliberately **not** part of theta 1.0 compatibility: function-parameter contravariance, optional-field widening, excess-property tolerance on objects, and `number ⊑ integer` are all rejected. A future widening of the relation is non-breaking iff it only admits new pairs.

**`void` does not participate in `⊑`.** `void` is a return-only annotation, not a value-bearing type (see [Grammar Appendix — Type grammar](./grammar.md#type-grammar)); no value is ever statically typed `void`, so `void` appears on neither side of a `T₁ ⊑ T₂` check. A `void` in any non-return type position is rejected at parse time as `theta/parse/void-in-non-return-position` before any compatibility question arises.

**A written `NamedType` head that resolves to no declaration does not participate in `⊑` either.** A `let` annotation, an `fn` parameter type, an `fn` return type, an `invoke<T>` ascription, and every other reference position [Diagnostics — code registry](./diagnostics/code-registry-parse.md#code-registry) names, naming a `NamedType` that resolves to no visible declaration is rejected at parse time as `theta/parse/unresolved-named-type` before any compatibility question arises.

**Unresolvable operands.** When either side of a compatibility check is past the parser's static view (e.g. an inferred binding whose RHS depends on a Pi-tool call whose registered schema is not visible at parse time, or an `invoke` against a callee that produced `theta/load/callee-has-errors`) — a type the source WITHHOLDS or that sits outside the parser's static view, never a name the author WROTE and got wrong, which is refused upstream instead by the sentence above — the parse-time check is skipped and the runtime AJV check is the safety net. The skipping is the same posture documented for the unresolvable-callee case in [Invocation — Typed return](./invocation.md) and the unresolvable-tool case in [Tool Calls](./tool-calls.md); cite this paragraph rather than restating it. The skip is unconditional on the target's kind: a structural target (`array<T>`, an inline object type) skips exactly as a primitive, union or named target does, because the target's shape is a fact about the position and never evidence about the unresolvable operand, so no `T₁ ⋢ T₂` verdict is available at either. The skip is likewise unconditional on whether the position documents a runtime AJV net of its own — a plain `fn`-argument slot, whose registered row states none, still skips the check, because every code named for these sites registers a *Trigger* requiring a static failure ([Diagnostics — DIAG-2](./diagnostics/diagnostic-shape.md#diag-2)), and emitting where the relation reached no verdict would emit outside the code's registered *Trigger*, which DIAG-2 forbids. The `for` iterand's `array<T>` precondition and `join`'s element precondition are not on the check-site list above, are not compatibility checks and are outside this paragraph, and take their own dispositions. `join`'s element precondition takes the judging disposition: an element type the parser provably cannot resolve — a `named` that no visible declaration defines, as distinct from a read whose type is merely withheld — is a non-`string` element type and is refused as `theta/parse/non-string-array-join`, because the elements are what `join` consumes and a provably-unresolvable element list is a provable author error at that call even where the receiver as a whole would defer. The `join` receiver is outside that judgement and keeps this paragraph's deferring disposition: a receiver past the parser's static view is not statically an `array<T>`, so it draws no `join` diagnostic and defers, which makes the two levels of the one gate asymmetric by rule — the element judges and refuses, the receiver defers.

> **Requalification (2026-08-24, v0.266.0).** The element-judging sentence above is SUBSUMED, not reversed, by [bug 0262](../bugs/0262-unresolved-named-type-silent-at-nine-reference-positions.md)'s widening of `theta/parse/unresolved-named-type` to the full `NamedType`-reference position set: a `named` element type the author WROTE at one of those ten reference positions and that resolves to no visible declaration is now refused UPSTREAM, at the position it is written, before it ever reaches this element check. The input class this sentence names is unreachable through those routes now, not judged differently by them; an element type reached PAST the parser's static view (a Pi-tool-derived binding, an unresolvable callee) is the distinct WITHHELD class the paragraph above this one covers, still reaches this element check exactly as before, and this sentence's own judging disposition for that surviving class is unchanged. The receiver clause that follows and the rest of this paragraph are unaffected and stay verbatim.

**Absent operands.** An unannotated `fn` parameter ([Grammar Appendix — `fn` declarations](./grammar.md#fn-declarations)) is a different case from the above: its argument is not past the parser's static view, it has no declared type to compare against, so an unannotated `fn` parameter's argument is checked at neither phase. The usual safety net does not fill the gap — no runtime AJV safety net applies, because [TYPE-9](#type-9)'s `fn`-argument row (`theta/parse/fn-arg-type-mismatch`) covers only a top-level `fn` call, and top-level `fn` declarations are hoisted and always statically resolvable, so no call to one is ever the unresolvable-callee case a runtime check would cover ([Diagnostics — code registry](./diagnostics/code-registry-parse.md#code-registry)).

<a id="type-9"></a> **TYPE-9.** Five of the compatibility check sites listed at the top of this section are not covered by the invoke / array / match codes named under *Structural cases* above; four of them report their own parse-time diagnostic on a static failure (`T₁ ⋢ T₂`, both operands statically resolvable), and the fifth — a ternary — reduces its branches and defers to the enclosing site's code. The RHS of a typed `let x: T = expr` reports `theta/parse/let-rhs-type-mismatch`. A plain function-argument slot — an argument to a top-level `fn` call that is neither an `invoke(...)` nor a `.theta`-callable call — reports `theta/parse/fn-arg-type-mismatch`. A ternary `cond ? a : b` reports no code of its own: its branches reduce to their common type under rule 2's least-upper-bound computation ([Expressions — Array construction](./expressions.md#object-construction-array-construction-and-operator-rules)), and the enclosing site reports through its own registered code against that reduced type, on the same footing as the other four sites in this paragraph. When the two branches are named object schemas with no dominating member (the set rule 3 refuses for an array literal), the reduction is the first branch; the resulting branch-order dependence and the un-narrowed second branch are accepted by rule, not diagnosed, because that rule is array-literal-only. A frontmatter `params:` default against its declared type reports `theta/parse/params-default-type-mismatch` (or `theta/parse/integer-narrowing` for the one-way `number`-under-`integer` case). The RHS of a reassignment statement (the plain form and the five compound forms `+=`, `-=`, `*=`, `/=`, `%=`; [Bindings — Reassignment](./bindings.md)) against the target binding's declared or inferred type reports `theta/parse/reassign-rhs-type-mismatch` (or `theta/parse/integer-narrowing` for the same one-way `number`-under-`integer` case). The `let`-, `fn`-, `params:`-default-, and reassignment-site rows are registered in [Diagnostics — code registry](./diagnostics/code-registry-parse.md#code-registry).

<a id="type-10"></a> **TYPE-10.** Object-schema named types are nominal. A `NamedType` whose declaration is an object schema `schema X { ... }` (see [Schema Declarations — Object schema](./schemas.md#object-schema)) participates in `⊑` only through reflexivity against the same named schema ([TYPE-1](#type-1)), variant-to-union membership ([TYPE-4](#type-4)), and union widening / distribution ([TYPE-5](#type-5)/[TYPE-6](#type-6)). (A `NamedType` whose declaration is a type-alias schema `schema X = R` is **not** nominal; it is transparent in `⊑` — see [TYPE-11](#type-11).) A named-schema value is **not** `⊑` an inline object type with the same field shape, and an inline-object value is **not** `⊑` a named schema with the same field shape — the cross-form pair is `T₁ ⋢ T₂` regardless of field shape. Two *distinct* named schemas with byte-identical lowered fragments are likewise incompatible: name identity, not lowered identity, drives `⊑`, so any canonical-hash slug coincidence between them is irrelevant. A cross-form or cross-named-schema mismatch is reported at parse time on the offending site through that site's own diagnostic (`theta/parse/let-rhs-type-mismatch`, `theta/parse/fn-arg-type-mismatch`, or `theta/parse/invoke-arg-type-mismatch`; see [TYPE-9](#type-9)), not deferred to a runtime AJV failure. To move a value across the boundary, assign through an explicit construction or a typed `let` that names the target schema.

<a id="type-11"></a> **TYPE-11.** Alias-schema transparency. A `NamedType` whose declaration is a type-alias schema `schema X = R` (the `=` form; see [Schema Declarations — Type-alias / union schema](./schemas.md#type-alias--union-schema)) is **transparent** in `⊑`: on whichever side of a `T₁ ⊑ T₂` check it appears, it is replaced by its right-hand side `R` and the check re-evaluated, recursing through nested aliases until a non-alias form is reached. So `"low" ⊑ Severity` holds for `schema Severity = "low" | "medium" | "high"` (the literal unfolds against the literal union via [TYPE-3](#type-3)/[TYPE-5](#type-5)/[TYPE-6](#type-6)), and `StringOrNumber ⊑ string | number` holds for `schema StringOrNumber = string | number`. The alias is identified solely by the `schema X = R` `=` form — **not** by what `R` resolves to: aliasing an object schema (`schema Y = SomeObjectSchema`) unfolds to that object schema, which then participates under the nominal rules of [TYPE-10](#type-10), so alias transparency never reopens TYPE-10's nominal case. Because unfolding replaces the alias with its lowered right-hand side, the pairs admitted here remain within AJV's admit set per the **Operational definition.** above. Alias cycles are rejected before any compatibility question arises (`theta/parse/type-alias-cycle`; see [Schema Declarations — Type-alias / union schema](./schemas.md#type-alias--union-schema)).
