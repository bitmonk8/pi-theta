| `theta/load/params-type-not-expression` | E | load | A `params:` field's right-hand side does not spell a type expression in the theta type grammar ([Grammar Appendix — Type grammar](../grammar.md#type-grammar)), judged in two stages. **The node's shape**, at the frontmatter read where the field's YAML is still in hand: the value node is neither a scalar nor a **flow** mapping, or the field carries no value node at all. Refused are a block mapping (`p:` over an indented `a: Triage`) and a block sequence written under the field name, a flow sequence (`p: [a, b]`), every other node kind (an alias, for instance), and a field written with no value node — an explicit key (`? p`) or a value-less entry in a flow-mapping `params:` (`params: {p}`). The ordinary value-less key — `p:` in block form, `params: {p: }` in flow form — is not in that set: it parses as a null *scalar* and is admitted. The inline object type is a YAML flow mapping and is admitted. **The recovered text**, at a scalar the node-shape stage admitted. The unit judged at this stage is a single FRAGMENT of that text the source itself spells, not the right-hand side as a whole: a fragment is judged at the type's own top level, inside a union arm at any depth, inside a `GenericType` argument, and inside an inline `ObjectType`'s field type at any depth — hoisting an inline object lowers each field it declares through the same per-field path, so the judgement re-enters at every nesting level. Excluded from the judged set is a fragment the generic-argument split itself MANUFACTURES by cutting a `{...}`/`[...]` group the author wrote as one unit (`p: 'array<{a: string, b: integer, c: boolean}>'`'s middle shard, `b: integer`): such a shard never reaches this stage's sink (`LowerCtx.unspellable`), because the generic-argument recursion that produced it carries none ([bug 0204](../../bugs/0204-bracket-blind-split-shreds-inline-object-in-generic.md) §Fix (b)(3)). The exclusion is decided per SEGMENT of that split and never for the argument list: a segment is whole in the source when both comma boundaries delimiting it sat at `{...}`/`[...]` depth 0 (the interior's start and end count as such boundaries) and its own groups balance, and a whole segment keeps its judgement beside the manufactured ones — `p: 'array<{a: string, b: integer, c: boolean}, ???>'` refuses the field, on the whole argument `???`, where the three pieces of the cut `{...}` group beside it refuse nothing. In the other direction the exclusion is a deliberate UNDER-refusal, stated here rather than left to be discovered: junk the author did write draws nothing when a manufactured shard CARRIES it, because the shard is not text the source spells on its own — `p: 'array<{a: Cat +, b: integer, c: boolean}>'` and `p: 'array<{a: string, b: integer, c: boolean} | Cat +>'` are both admitted, the first with `Cat +` inside the piece `{a: Cat +` and the second with it inside the piece `c: boolean} | Cat +`. A cut group is under-refused only when it is itself DERIVABLE — an `ObjectType` (`{...}`, one of the `Type` grammar's six alternatives): a CLOSED `[...]` bracket group the split cuts derives from none of them at any depth ([schemas.md:93](../schemas.md), stated with no depth qualifier), so that group is not under-refused with its pieces — [bug 0217](../../bugs/0217-nested-inline-enum-in-generic-argument-draws-nothing.md) §Fix (b)(2) pushes its own source text into this stage's sink exactly once, as a last resort when nothing the argument list's own segment recursion contributed to that sink is itself refusable, so `p: 'array<enum["a", "b"]>'` refuses the field on the group the author wrote, `enum["a", "b"]`, and never on either piece the split cut it into. The last resort is measured against the refusal, not the sink's contents: a whole argument beside the group that IS refusable keeps the field's single refusal and the group adds none (`p: 'array<enum["a", "b"], ???>'`, refused on `???`), while a whole brace-carrying argument beside it — text the brace exemption below declines — earns no refusal and suppresses none either (`p: 'pair<{a: string}, enum["x", "y"]>'` is refused on `enum["x", "y"]`). A bracket group the source never CLOSES (`p: 'array<enum["a", "b">'`) is outside that push and stays under-refused with its pieces: its extent is unknown, so no source text names the group, and the field keeps whatever this stage's judgement of its own recovered text makes of it — for that spelling, admission and registration with the permissive `{}`. Refused is a fragment every arm of the `Type` grammar's own recognisers — a `PrimitiveType`, a `NamedType`, a `GenericType`, an inline `ObjectType`, or a `LiteralType` — has declined: text carrying a YAML mapping or sequence shape (`a: Triage`, `[a, b]`, `- a`), prose, punctuation, a comment-shaped text, two space-separated identifiers, or an empty or whitespace-only string, at whatever depth it sits — `p: 'a: Triage'`, `p: 'string \| a: Triage'`, `p: 'array<a: Triage>'`, `p: '{a: ???}'` and `p: '{a: {b: ???}}'` are one refusal each. The spelling that delivers the text does not matter: a quoted scalar, either block-scalar form, a folded multi-line, and a double-quoted escape sequence all reach this stage carrying the identical recovered bytes. Excluded from the judged set, at the field's own TOP LEVEL only: text matching the inline-enum anchored predicate (`checkInlineEnumForm`'s `/^\s*enum\s*\[/`, src/parser/schema-declarations.ts) draws `theta/parse/inline-enum` instead, ahead of this stage's judgement and notwithstanding the brace exemption below — `p: 'enum[{a: string}]'` is refused by that row, not this one, even though the brace exemption would otherwise admit it ([bug 0162](../../bugs/0162-inline-enum-trigger-misses-params-position.md) §Fix route (a)). A nested `enum[…]` one level down, inside a `GenericType` argument or an inline `ObjectType` field, is NOT excluded by this and keeps this stage's own last-resort push exactly as it stood ([bug 0217](../../bugs/0217-nested-inline-enum-in-generic-argument-draws-nothing.md) §Fix (b)(2)). Not this text is any `LiteralType` atom or union arm — it lowers under its own emission and draws no diagnostic here — nor is any FRAGMENT carrying a `{` or `}` anywhere, balanced or not, PROVIDED that fragment carries no string literal that never closes ([bug 0232](../../bugs/0232-unterminated-literal-params-type-drops-inline-fields.md) §Fix (b)): the brace frame owns every brace-carrying fragment whose quotes all close, and this stage owns the brace-free ones plus a brace-carrying fragment that itself carries an unterminated string literal (`p: '{a as "w: integer}'` — the braces the author wrote balance, but the wire-name literal never closes), so a fragment that reaches the judgement WHOLE with a brace in it and every quote closed stays admitted with its own (possibly permissive) lowering — `p: '{junk}'`, the unterminated-BRACE `p: '{a: string'` (a genuinely unbalanced brace group carrying no unterminated literal), and an inline `ObjectType` nested inside a `GenericType` argument or a union arm (`p: 'array<{a: ???}>'`, `p: 'string \| {a: ???}'`), which reach this stage exactly as they do at every other `Type` position. The exemption is the fragment's own, not its enclosure's: a brace-free fragment reached through a hoisted inline object's field type is refused like any other, and the unterminated-string-literal narrowing applies to the fragment's WHOLE recovered text so a nested (`p: '{q: {a as "w: integer}}'`) or generic-argument (`p: 'array<{a as "w: integer}>'`) spelling is refused too. Three precedence rules keep the two stages to one diagnostic per field: a field already carrying an error-severity diagnostic from its own type-side parse or lowering — a reserved keyword, an unresolved name, or one of the type grammar's own registered rejections — keeps that diagnostic and draws no text refusal; a field refused by the node-shape stage draws no additional diagnostic from the text stage; and a field refused by the text stage draws no default-RHS literal-sublanguage diagnostic (`theta/parse/default-not-literal`, `theta/parse/literal-newline-in-string`) for the same field.
